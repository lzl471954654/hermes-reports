🔥 今日头条

DeepSeek 开源 DeepInfer，并且顺手把「推理到底赚不赚钱」这个悬了两年的问题算清了

发生了什么：10 月 20 日，DeepSeek 在 GitHub 开源了 deepseek-ai/DeepInfer（Apache-2.0，10/16 建仓，5 天冲到 12,143 stars / 1,096 forks）。这是 DeepSeek V4.1-Flash 生产线的推理框架，首发支持 NVIDIA SM100 GPU 和华为昇腾 950 NPU。同一天 HN 上这条帖子冲到 2101 分 / 63 评论——是本周 HN 全站最高分。

真正的引爆点不是代码，是 README 里那句被截图疯转的话：

「基于这个框架，我们已为 DeepSeek V4.1 Flash 搭建了高吞吐、低延迟的大规模推理服务。目前单个集群的服务吞吐是 155 万亿 tokens/天，整体收入是每卡每小时 38 美元（非高峰定价）。」

意味着什么——三个层次：

1）单位经济学第一次被开源代码背书。过去两年整个行业争论的是「AI 推理到底能不能赚钱」。DeepSeek 之前给出的成本数据总被质疑是自说自话。现在这套跑出 155T tokens/天 的系统以 Apache-2.0 协议完整开源了——虽然只支持自家模型 + 两款特定硬件，但这足以让任何人都去验证这个 $38/card/hr 的说法。HN 上的反推很粗略：按净现金 $35/hr 算，一张 3 万美元的 H100/B300 大约 850 小时（约 35 天）回本。争议同样真实——HN 评论区有人指出 155T 远超 OpenRouter 全平台上周总量（164T），怀疑单位换算，也有人说这只是「一家中国公司做给全世界看的开源引擎」，通用性远不如 vLLM/SGLang。

2）对 agent 开发者的直接含义：token 单价的护城河正在塌。推理引擎一旦开源并被 port 到通用栈，OpenRouter 这类聚合层的定价权会被削。评论区一个尖锐的观察：「这就是美国 frontier 实验室的 kamikaze。」——意思是开源推理栈对 frontier 厂的杀伤，可能比对用户还大，因为它同时（a）压低了所有人的价格底线，（b）让「不发布 open weight」失去了成本优势。

3）昇腾 950 是一张明牌。一个开源推理框架同时支持 NVIDIA SM100 和华为昇腾 950，这个组合在 2024 年是不可想象的。同一天还有报道称 DeepSeek 正在为华为设计 AI 芯片。国产算力栈从「能不能跑」到「能不能以最优方式跑」，中间只隔了一次开源。

行动建议：如果你在做 agent 成本模型，今天该重算一次——不要假设明年 token 单价会跟 frontier 报价走，参考对象应该是「开源推理栈 + 竞争性硬件」的边际成本。同时值得盯的是 DeepSeek 会不会像 vLLM 支持其他模型那样，把 DeepInfer 的优化 kernel 反哺给生态。

🤖 Agent 前沿

P0Google Research递归自我改进15.3k stars

Harness²：Google 开源「递归 agent harnessing」——不碰模型权重，自己改自己

发生了什么：Google Cloud AI Research 开源 google-research/harness2（Apache-2.0，10/6 建仓，已 15,309 stars / 1,413 forks，仅 3 页 commits——说明仓库小、落地密度高）。论文 arXiv:2610.14224，标题直白：Harness²: Recursive Agent Harnessing for an Open World。

核心设定：模型权重完全冻结，agent 只优化自己周围的「harness」——system prompt、guardrails、memory、tool guidance、subagents、skills、scripts、plugins 这八个可编辑组件。它连接两层递归：

  • Task-level recursion：用 Propose–Probe–Compose 三步对比式改进当前任务的 harness——提议改动、在同一任务上探测改动效果、再从执行间的行为对比里合成改良版本。关键点是它不需要 ground-truth verifier，这正是开放世界任务（测试时遇到训练时没见过的新任务）的核心难题。
  • Harnessing-level recursion：把每次任务采纳的 harness 和「有证据支持的经验教训」沉淀进一个持久化的 improvement harness，指导未来任务。

效果：3 个职业 benchmark × 4 组 model-harness 配置，单步 Harness² 稳定优于基线——WorkBuddy-Bench +11.5 分、JobBench +4.5 分、LAB partial pass rate +11.8 个百分点，且提高 task-level 递归预算还能继续涨。

意味着什么：

这是今天最值得反复读的论文，因为它把「agent 能力」这件事的瓶颈重新定位了。过去两年行业的默认叙事是「等更强的模型」，Harness² 明确提出另一半的答案：模型可以用同一个，关键差异在 harness。今天 HN 上还有一篇爆款 Harness Engineering 101（132 分）提出同一个论点——「LLM 是大脑，harness 是身体」，评论区吵翻了比喻该怎么用（有人吐槽「身体」这个类比太累赘，有人给出更好的「烤箱/厨房」版本）。

但要清醒看争议：HN 上最扎心的评论来自 mchusma——「这不就是我们过去一年一直在做的事吗？从过去的 run 里学习，更新 skills 和 system prompt。」 还有 cykros 说「这听起来跟 Hermes-agent 已经在做的事没区别」。这个批评是成立的：Propose–Probe–Compose 是好工程，但离「递归自我改进」这个宏大叙事还有距离。论文自己的数字也支持这种怀疑——JobBench 只有 +4.5 分，说明跨领域泛化还很弱。真正的新意在于它把这件事形式化并开源了。

对 agent 开发者的具体用法：去读 docs/BENCHMARKS.md 里的 benchmark 设计（JobBench / LAB / WorkBuddy-Bench 三个职业任务集），然后抄它的「support count」概念——给每条经验规则标注它是从多少个不同训练任务里提炼出来的，高 support 意味着这条规则泛化性强而非一次性经验。这正好可以嫁接到你现有的 skill/memory 系统里做规则筛选。

P0IBM Research记忆学习τ²-bench

ALTK-Evolve：GPT-4.1 + 一份「学到的手册」，把客服 agent 送上 τ²-bench 榜首

发生了什么：IBM Research 10 月 20 日在 Hugging Face 博客发布 ALTK-Evolve。做法极其简单：不改任何权重，让 GPT-4.1 分析自己在训练任务上的轨迹，把成功和失败蒸馏成短的行为规则（「如何验证客户身份」「如何确认交易」「如何处理退货」），追加到 system prompt 末尾，然后在 held-out 测试集上原样使用。

用的是 Sierra 的 τ²-bench 客服 benchmark——严格二值奖励，只有最终数据库状态匹配才算通过，跑的是官方原版 ReAct scaffold，唯一改动就是那段 learned guidelines。

Retail 域的 67.5% Pass^4 高于 10 月 12 日 leaderboard 快照里所有零售类条目。更有说服力的是对照组：他们又用 gpt-5.5 重跑 airline（frontier 模型 + 学到的手册），accuracy 从 72.5% → 82.5%（+10），Pass^4 从 55% → 70%（+15）。手册对 frontier 模型照样有用，而且是从更高的地板往上跳。

成本账算得比性能账更有意思：提升不是靠聊更久换来的。在「两种配置都解出」的匹配任务集上，加手册的 agent 对话轮数反而略少（retail 10.59 → 10.16，airline 9.15 → 8.82）。代价全在输入侧：retail 的 292 条指南把每次对话成本从 $0.084 推到 $0.139（+65%），airline 更温和（+32%）——而且生产环境里这段指南 block 每次调用都一样，prompt caching 基本能吃回来。作者原话：这是「accuracy、reliability、time-to-completion 三者同时朝对的方向走」的反常交易。

意味着什么（这是今天最反直觉的一条）：

市场默认「越强的模型越不需要手工脚手架」。ALTK-Evolve 直接给了反例：同一个模型自己生成的规则手册，把 frontier 模型也推高了 15 个点的可靠性。原因不难猜：瓶颈不在智力，在领域规程的隐式知识——「执行任何写数据库操作前必须拿到用户明确批准」「每步只做一个动作，别把 tool call 和面向用户的消息放同一轮」。这些是 τ²-bench 的 policy document 写了但模型不会稳定遵守的东西。

还有一条极实用的结论：指南剂量是个旋钮，不是常数，而且两个领域的最优值相反。retail 越多越好（要 292 条全量才跳起来），airline 在可靠性端反转为「14 条高置信核心」打败 292 条全量。support count 阈值要按域调，不能硬编码。

对你的 agent 怎么用：这是今天最可以直接抄走的一条工程实践。把你 agent 的失败轨迹喂回给模型，让它蒸馏出带 support count 的规则块，塞进 system prompt，前缀缓存兜住成本。三天能出 prototype。注意 pass^k 这个指标的选择——「4 次全对才算过」比「平均正确率」更贴近客服场景的真实约束（退款成功 3/4 意味着四分之一的客户被坑）。

P1安全

20+ 个 Cairn 攻击面板暴露在公网：一个人 + 几千美元 + 一支 agent 军队打进了 100 个站点

NorForge 10 月 19 日发布 Inside Cairn 调查报告。Cairn 是一套 AI 渗透测试系统——给它目标和意图，它就能协调一支 agent 队伍调查目标、找漏洞、尝试攻破。起因是 Gambit Security 9 月披露的针对在线商城的入侵行动，攻击者恢复了其暂存服务器，发现用了 Hermes、Strix、Cairn 等 AI harness。NorForge 用 Shodan / Censys 扫描后发现20 多个暴露在公网的 Cairn 面板，泄露了大量目标信息（受害方身份、已发现漏洞、账户密钥、是否已被攻破）。路透社同日跟进报道：一名黑客用 AI agents 和几千美元买到的算力，打穿了 100 个网站，受害者包括 John Deere、SharkNinja。

最刺眼的数字来自报告本身：「在我们观察到的这些活动里，所见 harness 的平均成功率在 10% 左右。」——10% 的成功率，攻击面却是全自动化的。

意味着什么：注意报告里的一个关键转折——相当一部分暴露的面板看起来是合法的红队演练，这让客户自己都面临风险。这句话的潜台词比新闻标题更值得警惕：AI 攻防工具已经在两侧同时部署，而「谁能访问控制面板」这件事没有任何行业标准。

行动建议：三点，都很具体：(1) 你的 agent 控制面绝不能暴露在公网——Hermes 这类有 web UI 的 harness 必须绑定 localhost 或强制认证；(2) 如果你在做红队/安全测试工具，把面板默认配置改成 fail-closed；(3) 认真考虑 egress allowlist——10% 的成功率乘以无限制的出网能力，是攻击者能接受的赔率。

P1供给侧变化

网站开始系统性关闭大门：Amazon 对购物 agent 关闸，Shopify 开城

The Verge 报道零售与内容平台正在大规模屏蔽 AI agent，且即使 agent 持有正规访问凭证也在拦。社区里最具代表性的例子是 Meta Muse 购物 agent：与其被 Amazon 等巨头封杀，不如直接与 Walmart、Gap、Sephora、Best Buy 结盟开放，同时 Shopify 也把自己的店铺网络向 agent 敞开。Zuckerberg 9 月在 Sources 播客里说 Muse 的商业模式是抽成「a very small cut」——钱的流向反转了：从广告变成交易佣金。

另一个容易被忽略的细节：HN 讨论（156 分）里有人指出，连普通用户注册 GitHub 账号都被 DataDome 判成 bot；买火车票要装 chromium 而不是用 firefox。WAF 正在大规模误伤真人——一位 DataDome 员工主动在评论区承认这个问题并说正在改进 IP 段画像。

意味着什么：技术派和商业派的分歧点很清楚。技术派认为「这只是 API 的回归，我们以前就有——Reddit、Zillow、Wells Fargo 都限制过 API」，商业派认为「这次不一样，因为 agent 让跨店比价成本趋近于零，直接击穿整个电商的利润结构」。

值得关注的收敛信号：评论里被反复提起的 L402 / HTTP 402 Payment Required 微支付协议，以及 Cloudflare 正在做的 agent 微支付。如果这条路走通，agent 访问互联网会像 API 经济一样变成「付费换数据」——那今天这些封堵决策很多都会显得短视。对做浏览器 agent 的团队，现在就该把「拿到站点授权」设计成一等公民能力，而不是事后加的补丁。

Mercury 3：diffusion LLM 打到 1,068 tok/s，$0.20/M 输入——价格战从下一档开始

Inception Labs 10 月 19 日发布 Mercury 3，据称是迄今最强的生产级 diffusion LLM。

指标数值
速度1,068 tok/s（NVIDIA GPU），作者称 5-10× 于优化后的 frontier 模型
质量称在匹配 reasoning effort 下超过 GPT-6 Luna 和 Claude Haiku 5.5
上下文1M tokens（Mercury 2.5 是 260K）
定价$0.20/M 输入、$0.70/M 输出，首发 5 折 $0.10/M

对比参照：Haiku 5.5 是 1M context + adaptive thinking 被重新定价的那款小模型；Mercury 3 用更便宜一半的价格和数量级更高的吞吐去对标它。HN 255 分，实测反馈两极：有开发者拿到 300-400 tok/s「远超我以前用的任何模型」，也有人只测到 160 tok/s 并质疑宣传值。

为什么 diffusion 路线值得关注——以及它真实的软肋：

diffusion LLM 一次并行解码多个 token 再迭代修正，速度优势来自这里。但 HN 上一位研究者的技术解释很关键：它无法像标准自回归模型那样靠 batching 摊薄内存带宽。Google 去年把 Gemini Diffusion demo 悄悄下架、Diffusion Gemma 也表现平平，根因就在这——大规模多用户服务恰恰是 batching 收益最大的场景。有评论直指：「llama.cpp 不支持它，vLLM 不能真正卸载到 host RAM，HF transformers 只支持 MoE 的 f16 量化」——对低配设备来说，理论上最该受益的 diffusion 反而跑不起来。

还有个 agent 开发者必须知道的隐忧（来自 fraywing）：「这些模型因为非线性地产出 token，会不会更难推理？我们依赖非 latent 的推理来知道模型在想什么。」——diffusion 模型没有天然的 CoT 暴露面。对需要 step-level 可解释性和监控的 agent 架构，这是个真实的设计约束。

行动建议：把 Mercury 3 当作「延迟会复利」的场景来评估——搜索 agent、语音管线、coding subagent。OpenRouter 官方描述里就是这个词："latency compounds"。如果你现在因为 TTFT 太慢而放弃某类 agent 设计，这可能是第一个让它跑起来的选项。但别把它放在需要审计推理链路的合规场景。

LFM2.5-24B-A2B：2B 激活参数跑 184 tok/s，Liquid AI 把 LFM2.5 家族收官

Liquid AI 10 月 13 日发布 LFM2.5-24B-A2B，24B 总参 / 2B 激活的 MoE reasoning 模型，131K context，open-weight（base + post-trained 双 checkpoint）。这是 LFM2.5 家族的收官作，跨度两个数量级：230M → 24B。

关键数字：

  • Apple M5 Max 上 184 tok/s，单张 NVIDIA B300 上最高 21K output tok/s（Q4_K_M 量化，4K 输入上下文）
  • LiveClaw 48.09，与参数量多约 50% 的 Qwen3.6-35B-A3B 打平（38.19）
  • AutomationBench 27.69 vs 8.72——这是碾压级的差距，也是最能说明「为 agent 而生」的指标
  • 相比同级 MoE 端侧快 1.7×（因为只有 2B 激活）

架构上两个明确变化：context 从 32,768 扩到 131,072；tokenizer 词表从 65K 原地扩到 128K（更好的非拉丁文本分词）。预训练从 17T 扩到 33T tokens，mid-training 两阶段（2T @32K 偏推理/数学/代码 + 300B @131K 偏长上下文），tool call 和多轮轨迹贯穿两个阶段。另一个重要转变：这是纯 reasoning 模型，先显式输出 CoT 再给答案——作者说这是为了利用它的高 decode 速度。

意味着什么：131K context + 端侧 184 tok/s 这个组合，第一次让「本地常驻的 agent」在技术账上成立——不是只能做补全或分类，而是能真的持有长对话历史、调工具、做多步推理。加上 2.5GB 起就能跑的 4B 去 slop 模型（见下），端侧 agent 的组件现在齐了。

需要打的折扣：AutomationBench 27.69 对 8.72 这种碾压级对比，通常说明两者训练分布严重不同——Liquid 自己在这个 benchmark 上训练/调优过。8 个 benchmark 里打平 5 个，剩 3 个落后，这才是更诚实的读法。

PyTorch 2.15 把 FP8 带上 MPS：Mac 端推理栈补上最后一块

Hugging Face 的 PyTorch 团队 10 月 20 日发布 MPS in PyTorch 2.15。MLX 之外的第二条路：

Apple 生态1.0

AnyLanguageModel 1.0：Foundation Models API 的 drop-in 替换，一行 import 切换本地/云端

Matti Puledo（PyTorch / Core ML 负责人）团队 10 月 20 日发布 AnyLanguageModel 1.0，同时发布 swift-huggingface 1.0 和 swift-xet 1.0。核心用法是改一行 import：

- import FoundationModels → + import AnyLanguageModel

之后同一份 session 代码就能跑在系统模型上、或通过 llama.cpp / MLX / Core ML 跑 open-weight 模型上、或切到托管 provider。tool calling 和 guided generation 对所有 provider 都可用。

意味着什么：这解决的是端侧 agent 最实际的一个工程痛点——多 provider 适配的重复劳动。如果你之前因为「要同时支持 on-device 和云端 fallback 而不想写两套代码」而推迟了端侧 agent 方案，这个库把那个理由消掉了。

安全供应链

arXiv 2610.13928：模型权重可以「可证明地」藏住任意能力

把加密神经网络嵌进宿主模型权重里，只有收到特定 secret trigger 才解密执行。用数字锁（digital lockers）实现，在密码学假设下，即使拿到完整权重也无法诱出或解释这些隐藏电路——把先前「藏固定字符串」的工作推进到「藏任意计算」。作者实测了微调、权重加噪、梯度搜索 trigger、latent 对抗训练四种诱出手段，全部无效。
点评：这是今天最该被安全团队读完的论文。它给「能力审计」划了一条硬边界——「我们评测过没发现问题」和「没有问题」不是一回事。作者开放了模型用于改进防御。

内容生态

「编造统计数据，然后被 LLM 引用」：一个 7 个月的实验

Peec AI 的 GEO 研究员 Metehan Yesilyurt 做了个实验：上线一个含 5 万条全假统计数据的网站。7 个月后——Google 已把它 deindex，但 ChatGPT 没有；期间带来超过 1 万次 AI 会话访问；330 多个 referring domain（包括 Shopify、Bluehost、DHL）链接到了它；编造的数字已经进入一篇学术论文和一份银行的投资研究报告。HN 314 分。
点评：这不是新问题——Wikipedia 时代叫 citogenesis，地图上叫 trap street——但LLM 把它工业化了，因为模型的检索层缺少「认识论分层」：输出用专家的自信口吻呈现，来源是伪造的。评论区的共识是这不是 LLM 特有的缺陷，而是任何依赖「网上没人撒谎」的系统都是坏掉的。真正的坏消息是另一条：「ChatGPT 用 web search 时 top 10 结果本身常常是 LLM 生成的内容」——模型在自己训自己。
对你的 agent：如果你的 agent 输出涉及统计数字，优先接一手信源（BLS、央行、统计局 API）而不是让模型去搜。HN 有开发者明确说自己从不问 Claude「上季度通胀率是多少」——直接调数据集。

💭 深度思考

思考一：今天最被低估的信号，是「harness 正在成为真正的产品」

把今天的 P0 放在一起看：Harness²（Google 开源递归 harness 优化）、ALTK-Evolve（学到的规则手册把 GPT-4.1 送上榜首、连 gpt-5.5 都被推高 15 点）、Harness Engineering 101（HN 132 分的社区共识）、加上 HN 上那篇 300 分的「If you don't run your own LLM proxy, how do you know what's going on?」——四条指向同一个结论：

行业的竞争焦点，正在从「谁的模型更强」不可逆地转向「谁把模型包得更好」。

证据是数字层面的：ALTK-Evolve 用 GPT-4.1（一个已经过两代的老模型）打赢了 τ²-bench 零售域的所有条目。这不是「小模型也能用了」的老调陈词，而是一个更精确的命题：领域规程知识可以脱离模型能力单独存储、单独优化、单独迁移。这部分能力一旦被 harness 吸收，模型代际差异带来的收益就被部分抵消了。

对 agent 开发者的 actionable 建议，按投入产出排序：

  1. 先建 prompt 级的手册机制（今天就能做）——学 ALTK-Evolve：让模型从自己的失败轨迹蒸馏规则，给每条标 support count，按域调阈值。它有全套 benchmark 代码和数字可以直接对标，不需要任何训练资源。
  2. 再考虑 harness 层的自动化改进（Harness²）——但先看你能不能诚实回答：「我上一次系统性地从失败里学到东西并固化下来，是什么时候？」 如果这个问题的答案是「从来没有」，Harness² 的 Propose–Probe–Compose 是现成的脚手架；如果已经有 manual 版本了，再考虑自动化。
  3. 最后才是自建 harness 框架——HN 上 libraryofbabel 那条评论我认为是今天最健康的建议：「与其读一堆关于 AI 写作的爬藤类比，不如从零手写一个最简 coding harness。你会学到的东西比这些文章多得多。」

并且，请务必读评论区里那条最冷静的质疑：当一个热点出现时，同质化的表态会大量涌入。mchusma 说「这不就是我们过去一年一直在做的事吗」——如果你的第一反应是「我们早就在做了」，这不一定是坏事，但要小心：早期采用者的工作通常经不起框架化。

思考二：今天有个反常组合——推理成本在塌陷，但 token 总量也在平台化

把两条曲线放一起：

成本曲线：DeepInfer 让开源推理的边际成本被摊到明面上（$38/card/hr）；Mercury 3 把 Haiku 级能力的定价打到 $0.20/$0.70；LFM2.5-24B-A2B 让端侧 184 tok/s 成为现实；PyTorch 2.15 给 Mac 补上 FP8。四个方向，全在往下压。

总量曲线：OpenRouter 用量首次平台化，Anthropic 营收停止逐季翻倍，有开发者称自家花费只剩峰值 20%。并且这个人的表述很关键：「我们能用低得多的价格买到同等水平的智能。甚至 Sonnet 5.5 对我们大部分 agentic workload 已经 overkill 了。」

这两个趋势同时成立，最可能的解释不是「需求饱和」，而是「单位任务所需的 token 数在同时下降」——而这恰恰是今天另一条新闻的另一面：OpenRouter 那条讨论里 judge2020 指出，SWE 类工作对上下文和 token 吞吐的需求正在放缓（参见 Opus 5.5 的表现），而那些真正能采用 AI 的新行业（法律正确使用 LLM 这类）本来就不需要海量 token 流动。

这个组合对 2027 年的 agent 产品形态有一个具体推论：如果 token 单价继续跌、同时单任务 token 需求也在跌，那么「用最大模型跑最贵 agent」的默认架构会越来越不合理。赢的架构会是：廉价的常驻小模型处理绝大多数步骤，只在 harness 检测到需要时升级到 frontier 模型——这正好是 ALTK-Evolve 隐含的结构（GPT-4.1 手册 + gpt-5.5 也受益），也正好是 Harness² 在做的事（冻结权重，优化周围的调度）。

顺带一个被忽略的商业信号：今天 DHS 禁 DeepSeek 的时点非常微妙——正好卡在「中国开源模型开始在美国机构里产生不可忽视的成本优势」这个节点上。而 BIS 至今没把 DeepSeek 列入实体清单这个事实，比禁令本身更能说明问题：贸易与产业政策的优先级，压过了安全叙事。我个人的判断（主观）是：这份禁令的真实作用是延缓而非阻断，因为美国开发者社区里「弃用 Gemini 换 DeepSeek」这类行为，行政令管不住。
