GNAP — Git-Native Agent Protocol：4 个 JSON 文件搞定多 agent 协调

P0 多 agent开源GitHub

farol-team/gnap 项目最近在 HN 和 awesome-ai-agents-2026 上冒头（HN 讨论）。核心理念：用 Git 当 backend 协调多 agent——不需要服务器、不需要数据库，只要 4 个 JSON 文件丢进 repo，任何能 git push 的 agent 就能加入。

为什么有意思：当前多 agent 框架（AutoGen、CrewAI、LangGraph）都需要中心化运行时——broker、消息队列、状态服务。GNAP 反过来：把 agent 之间的契约（任务清单、状态、产物）当 commit 推到 Git，agent 自己 pull 自己的"工单"。

  • 优势：零基础设施、审计天然（Git log）、跨语言/跨平台兼容、异步/离线友好。
  • 局限：低频、长延迟任务才合适（秒级交互就别想了）；并发写需要 Git 自身的冲突解决。
落地建议：如果你的 agent 团队是"夜间跑、批处理、产物归档"模式（日报生成、周报分析、代码 review），GNAP 比搭一套 Kubernetes + Redis Streams 轻得多。MIT 协议，可商用。

Jev（TypeSafe AI）：System One 决策模型，70-500ms 响应，$0.042/M tokens

P0 新范式小模型typed decision

这是本期最被低估的发布。TypeSafe AI（前 OpenAI 工程师创办）9月15日发布的 Jev，定位完全不是 ChatGPT 那种对话模型。官方说法："the next moment is AI that talks to software, not people"。

关键特性：

  • Transformer 架构，但不是 LLM——不写自然语言回复，只输出 typed decision（结构化决策）。
  • 输入：文本 + 强类型 schema；输出：每个选项的概率 + 置信度。
  • 延迟 70-500ms（比 GPT-6 Astra 的 5-30 秒快两个数量级）。
  • 价格 $0.042 / 1M input tokens，输出免费。
  • 已经被 HN 热议为"OpenAI fast-follow"对象（Arcturus Labs 分析）。

为什么是范式转变：LLM 是"万能瑞士军刀但慢且贵"；Jev 是"专用螺丝刀但极快极便宜"。在 routing（路由）、guardrail（安全拦截）、分类、提取这类高频低复杂度决策场景，Jev 比 GPT-6 Astra 便宜 5000 倍、快 50-100 倍。配合 JevBench 这种 typed decision benchmark，整个"小决策模型 + 大推理模型"的分层架构正在成型。

对 agent 开发者的启示：你的 agent 里有多少"判断 X 是否属于 Y"这种二分类/多分类调用？把它们从 GPT-5/6 切到 Jev，单次成本能压到 $0.0000001 量级，整套 agent 的 TCO 重写。如果你正在做实时 routing / safety filter / intent classification，立即试。

💭 深度思考

洞察一：模型市场出现"决策/生成"双轨分离

Jev（System One，决策）+ GPT-6 Sol/Luna（System Two，生成）+ Opus 5.5（深度 reasoning 强制 thinking）三件事放在一起看，市场正在自发形成三层架构：

  • Layer 0 — 决策路由层：Jev 类 typed model，$0.0001/次，决定"该用哪个下游模型"。
  • Layer 1 — 主力推理层：GPT-6 Sol / Claude Opus 5.5，处理 95% 的工具调用 + 多步推理。
  • Layer 2 — 极端深度推理：GPT-6 Astra / Claude Fable 5.1，0.1% 概率触发的"超能力模式"，解 Enigma、解 Navier-Stokes 就是这个层级。

对 agent 架构师来说，这意味着未来一年最重要的工作不是选模型，而是设计 routing。一个好的三层 router，能把单任务成本压到单模型的 1/5-1/10。

洞察二：agentic coding 进入"工程级可交付"区间

Opus 5.5 的 Terminal-Bench 4.0 拿到 66.4%，Astra 自己造工具解密码——两件事合起来指向一个临界点：agent 已经能交付"工程级"产出物（不是 demo）。

以前的 agent coding 局限在"单文件函数补全"，现在可以做到：跨 10 个文件重构 + 自己写 migration script + 跑测试 + 改 bug + 重跑回归。这不是渐进式进步，是能力曲线的一次阶跃。

对独立开发者的具体建议：

  • 把"agent 完成 5 小时工程任务"加入你的工作量估算基准——而不是"agent 完成 5 分钟小任务"。
  • 反思你的产品：哪些环节是"5 分钟小任务"（替代即可），哪些是"5 小时工程任务"（赋能 10x 生产力）。
  • 建立你自己的 eval set——基准分差不能预测实际差异（Anthropic 自己说的），你需要自己测。
