DeepSeek 开源 Super-agent：把 agent 从"会话"升级为"常驻同事" —— 当瓶颈从模型能力转移到人类注意力

2026-10-31 09:32 UTC（仓库创建）→ 11-01 设计文章 · GitHub: deepseek-ai/dsh-superagent-prototype · SCMP · Bloomberg · 量子位（中文详读）

发生了什么

DeepSeek 的 Harness 团队在 10 月 31 日开源了 dsh-superagent（MIT 许可，仓库创建后 24 小时内星数破 7,000，fork 730+），并在 11 月 1 日发布了配套的中文设计文章《Super-agent：迈向更自主的 Agent 系统》。这不是又一个 coding agent，而是一次agent 架构范式的换挡。

核心命题由团队自己写得很清楚："Take as little human attention as possible, and give as much value as possible."（尽可能少占用人类注意力，尽可能多交付价值）

为什么这个命题在今天成立？因为团队观察到一个反直觉的事实：模型变强了，瓶颈却从"模型能不能做"转移到了"人能不能同时盯住几件事"。一个人通常只能同时跟进 3–5 个活跃会话——这个数字是 DeepSeek 自己在内部观察中得到的。于是当单项任务能力足够强时，多任务协作的效率反而被人脑的注意力带宽卡住。

架构：Router + Worker 双层

  • Router（上层调度）：接收消息、分配任务、维护全局上下文。工具集更小。
  • Worker（下层执行）：每个 Ticket 分配一个独立 session 和独立目录（默认 /work），多个任务并行推进互不干扰。前台 shell 命令超过 5 秒自动转后台，让 worker 能在下一步就接收新消息，而不是干等长命令跑完。
  • 订阅直通（Subscription / Pass-through）：某个 Worker 接手一条 PR 后，直接订阅后续评论，新消息不再经过 Router 层层转发，直接派回原 Worker。团队实测：关掉直通机制，Router 决策次数增加约 30%，读取缓存 token 增加约 37%。
  • Watchdog（看门狗）：一个专门监督其他 agent 的 AI——检测程序故障、判断任务是否陷入无效循环或偏离目标，并尝试介入修复。这是把"可观测性"从日志提升到"闭环干预"的一步。
  • 投机执行（Speculative Execution）：群里有人讨论一个 bug，Super-agent 先在后台复现、定位、尝试修复；找到简单可行方案才交给用户，没找到就保持安静。
  • 两级事件过滤：先用程序规则筛掉无关消息，再由大模型判断剩余事件是否需要行动——目的是减少不必要的 token 消耗。
  • 计算/状态/执行环境分离：agent 逻辑跑在云端，会话状态独立保存，本地设备保留原有工作环境。电脑离线时云端 agent 维持任务状态，设备重新上线后继续执行。

实测数字：模拟约 300 条消息、20 项工作请求的协作环境，每种配置重复 5 次。

方案任务完成时间中位数95 分位完成时间
Super-agent（Router + Worker）12.4 分钟15.7 分钟
传统单 Session + Subagent（中性提示）—29.5 分钟

95 分位的差距（15.7 vs 29.5 分钟，接近 2 倍）比中位数差距更能说明问题：Super-agent 优化的正是"最坏情况下你要等多久"，也就是尾延迟。对要交付给用户的多任务系统，尾延迟才是体验的瓶颈。

仓库的自我定位很诚实，值得单独说一句：README 开头就写明"Research prototype for reference only, not an official DeepSeek product"，并提示"许多工程由 coding agent 完成"、"为发布做了适配，与内部版本不完全一致"、"文章中讨论的部分设计是未来方向，尚未在此原型中实现"。还专门给出了一个 docs/HONEST 式的诚实清单（多份编号文档 000–008，每份只建立在前面几份之上）。这种"把不确定性写在脸上"的文档风格，本身就是 agent 工程正在走向成熟的一个信号。

给 agent 开发者的具体启示（今天就能做）

  1. 重新审计你的 agent 架构里"人的注意力"出现在哪些位置。DeepSeek 的做法是把每一次通知、提问、面板元素都当成"消耗注意力"的成本来计——"每条消息、每次通知、每个问题、每条设置、每个面板元素、每段文档，都消耗某个人的注意力，必须回报更多价值，否则就删掉"。健康状态下，面板不占任何空间。这是可以直接抄到你的产品里的设计准则。
  2. 做事件直通，不要让所有消息穿过中心路由器。如果你有一个 router/fan-out 层，检查它是不是把本来可以直接回到原 worker 的消息也截了一刀。这是纯粹的延迟和 token 损失。
  3. 把"投机执行"当成默认行为而不是优化项。先在后台试着做，成功了才打扰人。这条准则对任何主动型 agent 都成立。
  4. 按"影响"而非"努力"停止。DeepSeek 的原话："A local change goes as far as a reviewable result. A change that needs a design decision stops with a clear question."——局部改动做到"可评审"为止；需要设计决策的改动停下来问一个具体问题。
  5. 先窄后宽。官方建议："Begin with a short allowed list and with proactive work only recorded. Widen both once what the agent would have done looks right."——主动行为默认只记录不执行。

我的判断（主观）：这是今天最值得读的一篇，但价值不在代码（7,000 星 24 小时，说明的是关注度而非成熟度——它自己也承认是 research prototype），而在"人类注意力是 agent 系统的真实瓶颈"这个判断上。过去两年所有 agent 框架都在卷"让单个 agent 更强"，DeepSeek 这篇文章问的是一个被忽略的问题：当 agent 足够强之后，谁来当那个调度多个 agent 的人？而答案可能不是人，是另一个更轻的 agent。这就是 Router 这个角色的全部意义。

50 个 agent 玩 Minecraft 建文明，结果建出了一套官僚体制 —— 50-agent 团队在官僚主义中瘫痪

2026-10（YC Labs 发布）→ 11-01 广泛报道 · YC Labs · Agents in Games · minecraft-agent-harness（MIT，已开源） · Tom's Hardware

YC Labs 与 Olam Labs 合作，在 Minecraft 和 Mindustry 里跑了一批长时程 agent swarm 实验。Civ50 实验是最出圈的一组：50 个 GPT-6.1 Sol agent 进同一个生存服 Minecraft，3 小时，唯一目标是"建立一个繁荣的文明"。它们有 agent 名册（directory）、共享沙盒、私信权限。发出去约 5,900 条消息。

涌现出来的东西极其像真实组织，而且像得让人不舒服：

  • 90 秒内砍光了出生点附近几乎所有树——集体陷入"伐木偏执"。
  • 按名册顺序自然形成了层级：名册第一位是 Ada，成了事实上的领袖，其他 agent 排队找她批（approve）请求，Ada 在共享沙盒里写了一份 settlement.md 全 colony 计划。
  • 建了一套配给官僚体系：专门的 ration ledger（口粮账本）、成文的规则、许可证（permits）、任命的操作员。Ines 专职管口粮进出，Ada 负责分配与烹饪。
  • 22/34 的死亡发生在第一夜。死亡后 agent 会重生、损失装备，但在这个环境里死亡几乎没有代价——于是群体从此变得极端保守。第三夜之后 Ada 下令："停止可选的大规模挖掘/建造与远距离侦察，在有照明的封闭掩体里待命，直到被分配短任务。"

结果是："一个可能繁荣的文明"变成了"一个专注食物与生存的官僚机构"。原定的繁荣目标被官僚体制挤掉了——组织先建起来了，然后开始为存在而存在。

实验的另一半更有信息量：Mindustry 的 Bed Wars 竞技场里，Claude 系和 GPT 系展现出两种截然不同的群体形态。

观察维度GPT 系Claude 系
组织形态"蜂巢"：广谱协作，愿意干杂活，通信网络密集单一领袖：始终有且只有一个领导者
通信风格沟通量大但价值低（通报、播报）沟通量小但有效，更接近人类在 Slack 上的用法

他们把这套环境全开源了：Multi-Agent Mindustry（两个环境：best-of-N 混合模型队伍，以及最多 20 agent 的 Endless Survival）和 Multi-Agent Harbor（Terminal-Bench 背后的开源框架的 fork，支持多 agent）。README 明说"只需一个模型 API + 一个 harness + 算力就能跑"，且刻意不做任何 harness 层定制或特殊记忆工作——每个 agent 拿自己的 Linux 环境、通用 harness、游戏 API，爱怎么写脚本写笔记就怎么写。

为什么这值得 P0（我的判断）：这不是"AI 会玩游戏"的猎奇报道，而是一份关于多 agent 组织形态的受控对照实验，而且它给出的结论对做 agent 编排的人直接有用：leader 数量、通信风格、角色固化程度，很大程度上是模型家族决定的，而不是你的编排代码决定的。如果你在做 multi-agent 系统，别以为"我设计得更好"——先测测你选的模型在 swarm 里会自发长成什么形状。而且那个 Minecraft 的结论更狠：agent 组织起来之后，"活下去"会挤掉"活得好"。如果你的 agent swarm 在真实业务里也在自动生成流程和规则，那你最好提前想清楚谁去审计这套流程。

一个分享链接就能接管任何人的 ChatGPT 账号 —— MathLive 的 postMessage + YouTube 的 JSONP，两个"无害功能"拼出的完整接管链

2026-10-28 研究披露 · OpenAI 10-26 修复，定级 P1 · Parameter Labs · Do the Math: How We Took Over ChatGPT Accounts · Simon Willison 跟进

这条攻击链的精妙程度，配得上逐环拆解。它从一个极其平常的问题开始："如果 Preview 的代码被关进另一个网站，它还能跟谁说话？"

第一环：数学图 + HTML Preview。ChatGPT 的 Preview 功能可以把 HTML 代码块变成一个能跑的小网页，在受限 frame + 不同域名里执行——浏览器因此不允许它读取 parent.document。看起来隔离是成立的。但同一个对话里有个交互式图表，它加载了 MathLive 数学库，而 MathLive 顺手在主页面上装了一个监听 postMessage 的回调（用来响应屏幕键盘消息）。

第二环：postMessage 成了"信箱"。受限的 Preview 读不了主页面，但可以往信箱里投消息。安全成立的前提是"收信人检查寄信人身份"——而 MathLive 那个监听的 origin 策略是 none，等于任何域发来的消息都收，且不要求来自已批准的窗口。

第三环：innerHTML 信任链。攻击者发两条消息：第一条把虚拟键盘布局换成自己的 HTML，第二条让键盘显示。MathLive 把这个布局字符串 join 进 HTML 并赋给真实 ChatGPT 页面的 innerHTML。有个叫 createHTML 的辅助函数看起来像在做净化——实际上它只是把字符串标记为 trusted 后原样放行。

第四环：srcdoc 造出"同源的新文档"。通过 innerHTML 插入的 <script> 不会自动执行，但攻击者改用 <iframe srcdoc="...">——一个自带 HTML 的 frame，且没有 sandbox 属性。关键点：这个 frame 是主页面创建的，浏览器因此赋予它 https://chatgpt.com 的 web identity，于是它能访问父页面。

第五环：用 YouTube 的 JSONP 绕过 CSP。ChatGPT 的 CSP 正确地拦截了内联 JS，但允许 YouTube。YouTube 的 oEmbed 端点支持 JSONP 风格的 callback 参数，而且它在校验 callback 失败时仍然把 callback 名塞进了响应。于是构造 ?callback=globalThis.__marker=31337;void——结尾的 ;void 让被追加的对象无害化，而 YouTube 本来就在 CSP 白名单里，浏览器就把这段响应当脚本加载了。

至此：任意 JavaScript 以 chatgpt.com 的身份在受害者的已登录 session 中运行。攻击者验证了它能枚举受害者的会话列表、读取从未分享过的私密对话内容、把数据外发到外部服务器。受害者唯一需要做的动作是点开一个分享链接——不需要装 App、不需要加入 Project、不需要粘贴代码、不需要开开发者工具。

为什么这是 P0（我的判断）：

  • 它把"分享一个链接"这个零摩擦动作变成了凭证窃取。社交工程攻击的最高境界不是骗你点恶意按钮，而是让你点一个看起来完全正常、你甚至自己刚创建的链接。
  • 责任分散在两个互不知情的第三方组件里。MathLive 不知道 ChatGPT 有 Preview，YouTube 不知道 ChatGPT 的 CSP 白名单里有它。没有任何一方"犯了错"，但组合起来就是完整的账号接管。这是典型的组合漏洞——而组合漏洞正是 agent 系统最常见的一类问题：agent 平台越来越多地聚合第三方组件（MCP server、skill、插件、渲染器），每一个都以为自己在一个更小的沙箱里。
  • 给 agent 开发者的直接动作：你的 agent 如果有任何"渲染用户提供的 HTML/Markdown/代码块"的环节，请立刻检查三件事——① 预览环境的 origin 策略；② 任何 postMessage 接收端是否校验 event.origin；③ 是否有任何 innerHTML 路径把"标记为 trusted"的字符串直接落地；④ CSP 白名单里是否有会返回可执行 JS 的第三方端点（JSONP 是重灾区）。
  • 更根本的一条：沙箱隔离如果依赖"浏览器会阻止跨域访问"这个隐式假设，而实际执行路径上有第三方组件重新引入同源文档，那这个隔离只是看起来成立。DeepSeek Super-agent 的 docs/002-authorization.md 里那句"这些 wrapper 和目录建立的是默认值，不是安全边界"（these wrappers and directories establish defaults, not a security boundary），在这里得到了完美印证。
P0成本Token 经济学开源

68% 的 token 花在了"人根本不会读的部分" —— caveman 把 agent 输出压到三分之一

持续发酵中 · GitHub: JuliusBrussee/caveman（Apache-2.0，★116.7k，forks 6.7k）· Elasticsearch Labs 复现 · JetBrains A/B 测试 · Adobe Research 引用论文

这个仓库的自我描述很直白："why use many token when few token do trick"——与其浪费大量 token，不如少数 token 办事。它的做法是给 agent 装一套"穴居人语"规则：把回答压到最短，但不牺牲正确性。

它给出的实测数字（而且是第三方复现的，不只是自说自话）：

维度数字来源
单次修复的回答 token63 → 20（同一修复，正确性不变）项目自测，tiktoken o200k
每 session 输入 token减少 33.2%（日志/JSON/CSV/测试输出在模型读之前先压缩）项目自测
Code mode 单次测试运行397 → 76 token（agent 保留自己写的脚本并复用，不重复生成）项目自测
响应 token减少 63.6%，声称"零信息损失"Elasticsearch Labs 独立复现，8 个真实 MCP 场景
输出 token减少 8.5%，无可测量的质量损失（p = 0.82）JetBrains，86 个真实编码任务配对 A/B

最有意思的是 JetBrains 的结论：把话说短（"be concise"）本身已经接近收益天花板——新模型本来就知道要简洁。在这个基线之上，/caveman 在中位数上再省 3%，而 /ultracave 再省 35%。仓库自己也诚实标注了：规则本身约花 1,160 输入 token，如果你按请求付费（比如 GitHub Copilot），省输出 token 就是白省；而且它专门有一个 docs/HONEST-NUMBERS.md 列出"caveman 输掉的每一个 case"。

为什么这是 P0（我的判断）：这是今天唯一一条有第三方机构背书的、可量化的 agent 成本优化，而且它打的是 agent 成本里最被忽视的一块——不是模型单价，不是缓存命中率，而是"输入给模型的上下文里有多少是人写的废话"。日志、JSON、测试输出这类东西压缩后再喂给模型，是一个零智力成本、纯工程收益的优化。而且 JetBrains 的 p=0.82 意味着"可测量的质量损失 = 0"——在质量无损的前提下砍掉三分之二的 token 预算，这比任何量化技巧都直接。

给 agent 开发者的动作：先量你自己 agent 的 token 流向——仓库里的 /waste 命令专门做这件事，还包括"在你暂停时保持 prompt cache 温热"这一项。更根本的是把"压缩"做进 context 构建层，而不是留给模型自觉：agent 的上下文管理器如果还在无脑往 prompt 里塞完整 stdout，那你在为没人看的文本付费。

P1Anthropic水印合规

Anthropic 把文本水印扩展到四个旧模型，11 月 3 日生效 —— 且无法关闭

2026-11-01 · Mashable · 同文（Sea 版）

从 11 月 3 日起，Claude Mythos 5、Opus 4.7、Opus 4.6、Sonnet 4.6 的输出也会带 Anthropic 的隐藏文本水印，覆盖平台、API，并会陆续上到 Amazon Bedrock。技术原理是在不改语义、不改可读性的前提下微调措辞，检测权保留在监管方和少数专家手里。

两个细节值得 agent 开发者注意：

  • 不可关闭。API 客户是通过邮件得知的，Anthropic 公开页面并未声明这个日期——只有帮助中心表格在 10 月 28 日更新了模型清单。
  • 其中两个模型只在开发者不动采样设置时才会打标。也就是说，如果你为了 agent 的稳定性把 temperature 调低或设了固定 seed，水印可能根本不会出现——这对想检测 AI 输出的下游是重要限制。
  • 动机与欧盟 AI 法案的透明度要求直接相关。

点评：这是行业从"只给最强模型打标"到"补齐历史模型"的补全动作，方向上是合规基建而非能力突破。但对做内容溯源 / AI 内容检测的团队，一个务实的判断是：不要把水印当作唯一证据链——它只覆盖 Anthropic、只覆盖部分采样配置、且检测权不对外开放。更稳的方案仍然是生成侧的 C2PA 签名或你自己侧的元数据记录。

P1GitHub多模型编排

GitHub Copilot Fusion GA：让平台替你选模型 —— 便宜一半，还差 2 分

2026-10-28（GitHub Universe）→ 本期持续发酵 · GitHub Changelog · GitHub Docs · Artificial Analysis

Copilot Fusion 是 GitHub 的多模型路由与编排系统：你不选模型，选 Fusion，它在 Anthropic 和 OpenAI 的模型之间智能路由与协调。Artificial Analysis 的实测：在 Coding Agent Index 上比 Claude Opus 5.5 落后 2 分，但每任务成本只有一半。Nadella 的说法是"frontier-level quality"，快 40%、最多省 77%。

计费上：Fusion 本身不单独收费，按各模型标准费率从 GitHub AI Credits 扣；到 11 月 30 日，付费 Copilot 计划用 Fusion 有 30% 折扣。

点评：这件事的意义已经超出 GitHub 本身了——它证明了一件事：在 agent 场景里，"模型路由"正在成为一个独立于模型本身的产品层。DeepSeek 昨天的 Super-agent 用 Router + Worker 做任务路由，GitHub 用 Fusion 做模型路由，而 OpenAI 昨天宣布 12 月起把 ChatGPT 与 Codex 合并进同一个 token 池（官方帮助中心）——三层收敛到同一个方向：用户不该被迫自己操心模型选择和额度切分。

对开发者的现实影响是：如果你现在为 agent 手工做多模型 failover，那套逻辑大概率会在 12 个月内被平台层吃掉。你的护城河应该建在评测与任务定义上，而不是路由规则上。

P1Claude Code版权策略

Anthropic 给 Opus 5.5 塞了两句话，禁止复刻已存在的游戏 —— 防不住，但误伤了一大片

2026-11-01 · 量子位

背景是 Opus 5.5（9 月 22 日发布）之后的一次爆发：游戏 modder 与黑客发现 AI 让逆向工程、反编译、游戏移植变得前所未有地容易。很快出现"不用买主机和正版盘就能在浏览器里玩 GTA 5、使命召唤"、PS5 被越狱跑 Xbox 独占的《光环 2》和任天堂的《塞尔达》。行业称之为自己的"Napster 时刻"。

Anthropic 的回应是在 Opus 5.5 的系统提示词里加了两句话，大意是：可以创建原创游戏、可以创建特定类型的游戏、可以用用户自己的素材，但不得复刻已经存在的特定游戏，哪怕改名或声称是原创。Anthropic 官方确认了这一改动。

点评（我的判断，这段是全篇最想说的话）：这个禁令有两个问题，而且两个都是结构性的。

  1. 防不住。它只管 Claude 自己。要复刻游戏的人可以用别的模型生成主体框架，把任务拆成"看不出上下文"的纯技术任务再扔给 Claude Code——把所有"宝可梦"相关名称标签换掉，Claude 完全不知道自己在参与克隆项目。更别提 GPT、开源模型、以及一条人工操作的流水线。
  2. 误伤一大片。禁令发出没几天，Claude Code 的 GitHub issue 就被刷爆：正在开发完全原创游戏的正经开发者，写到一半 Claude 突然罢工，理由是"疑似在复刻现有游戏"。有人只是想复现一个常见的游戏机制，或给自己的桌游打个补丁，也被拒绝。

还有一层讽刺：这些前沿 AI 公司当初训练模型时，把全世界的公开信息、艺术作品和代码都"复制"了一遍；现在反过来开始担心别人侵犯版权。这话刺耳，但从工程角度看它指出了一个真问题：靠 system prompt 承担版权义务，是在最不可能执行的一层承担它。

对比一下今天第一梯队里做得更对的例子：ParameterLabs 的那条 ChatGPT 账号接管链，OpenAI 收到报告后 4 天内修复并定级 P1；Anthropic 对 Claude Code 插件投毒也是立即下架、关停整个市场、轮换密钥。相比之下，用一句 prompt 去挡一个正在进行的行业级危机，是把法律与工程问题外包给了概率模型的服从性。真正的解法在别处：分发侧的商店签名与哈希校验、构建侧的 copyleft 传染、以及法律侧的诉讼——system prompt 挡不住任何一样。

P0AmazonAgentic RL基础设施

Sandman：Amazon 为 agentic RL 造沙箱，10 月单月开了 310 万个 —— 并发 11,858 个沙箱不掉链子

2026-10-29 · arXiv: Sandman: Building and Operating Sandboxes for Agentic Reinforcement Learning on Shared Kubernetes（Amazon）

Agentic RL 的现实痛点非常具体：一个训练任务会在几秒内突发式地创建成千上万个环境，而所有训练任务共享同一个 Kubernetes 集群。

Sandman 是 Amazon 内部构建并运营的沙箱服务，架构上有几个设计值得看：

  • 每个沙箱是一个 K8s pod，pod 里挂载一个小 daemon 到未经修改的镜像里——意味着任务镜像不需要为沙箱做任何改造。
  • 文件与进程在多次调用之间持续存在，直到框架显式释放环境。这对"agent 多步操作后接着干"是刚需。
  • Sandman 负责创建、就绪探测与回收——其中"回收被遗弃的沙箱"是最脏也最关键的活。
  • 规模测试：并发维持 11,858 个微型沙箱。
  • 生产数据：2026 年 10 月的四次 SWE-bench Verified 训练战役共创建 310 万个沙箱。

团队承诺开源 daemon、provider 与 pool。

点评：这篇的价值不在方法论新意，而在它把一个被严重低估的成本结构量化了。310 万个沙箱 / 一个月这个数字意味着：在 agentic RL 的账单里，"环境管理"可能和"模型推理"是同一个量级的开销。任何想自己训 coding agent 的团队，第一笔预算应该先算沙箱的编排成本，而不是先算 GPU。而且它顺手印证了另一件事——今天头条的 YC Labs 那个 Minecraft agent harness，也是一个沙箱方案（每个 agent 一个 Linux 环境）。"给 agent 一个干净、可销毁、可复现的机器"正在成为 agent 工程的默认单元，这和 DeepSeek Super-agent 里的 Ticket 目录 是同一个抽象。

P1端侧量化芯片

新芯航途 X7 Ultra：700 TOPS，但真正的指标是"量化后与 FP32 相似度 99.99%" —— 行业第一次用"大模型算力"描述芯片

2026-10-31 · 量子位

700 TOPS 在 2026 年底已经不算"极致"了。这块芯片真正想讲的是另外两个指标：

  • 量化模型输出与 FP32 基准模型的相似度超过 99.99%——即"我没有为了省算力而放任量化误差无限扩大"。
  • NPU 计算利用率 98.7%——AI 计算单元极少空转等数据。

对比行业旗舰：内存带宽消耗降低 80%，能效提升 100%。此外这款芯片的设计本身也用上了世界模型——标题是"世界模型首次指导设计芯片"。

点评：99.99% 这个数字的含义被严重低估了。端侧部署的核心矛盾从来不是"能不能跑起来"，而是"压到什么程度还能保住能力"。行业习惯用"能跑 INT4"作为卖点，但没人给出"与 FP32 差多少"——因为大多数情况下差得没法看。给出 99.99% 意味着这个量化点几乎无损，这才让"端侧跑一个真模型"从 demo 变成工程选项。另一条更值得注意：98.7% 的 NPU 利用率——在 agentic workload 里，工具调用往返的等待时间会吞掉大量算力，利用率才是端侧 agent 的真实吞吐。

P1架构MoE

Multi-View MoE：让多个 router 一起决定"哪个专家"，而且不增加任何算力

2026-10-29 · arXiv: Multi-View MoE

论文指出了一个此前被忽略的事实：密集评估所有专家后发现，"单一 router 的排序"与"专家实际效用的排序"一致性很弱，尤其在中层和深层。也就是说，单 router 的 MoE 在选专家这件事上，从一开始就选得不够好。

Multi-View MoE 的做法：用多个独立初始化的 router 聚合 sigmoid 打分，让被某个 router 强烈偏好或被多个 router 共同支持的专家被选中；更进一步，把每个被选专家在各 router 下的相对分数用来混合其输入的多个"视图"——即把路由偏好同时复用于"选谁"和"怎么算"。

关键的工程约束：每个被选专家只做一次前向传播，因此激活专家数、专家 FLOPs、all-to-all 通信量全部不变。在 24 层 10B-A1B 模型、708B token 上训练，九任务下游均值有提升。

点评："零额外成本换更好的专家选择"是一个漂亮的交易——因为 MoE 的所有瓶颈（显存、带宽、all-to-all）都锁死在激活预算上，而这篇论文在不动这个预算的前提下把选择质量提上去了。它也呼应了 DeepSeek Super-agent 里那个"订阅直通"的思路：让多个信号源直接参与决策，而不是让单一中心路由器做二选一。

P1Scaling 理论

"有信息量的算力"比"总算力"更贴切 —— System-1 给 System-2 做预筛，算力能省到接近 1/ρ

2026-10-29 · arXiv: Does Scaling Toward AGI Depend on What System-1 Lets System-2 Execute?

这篇论文的立论有点反潮流。过去所有通往 AGI 的路径都是"把 System-2 做大"——更大的模型、更多数据算力、更长的推理、更多的 agent。这篇问的是：下一阶段会不会来自与 System-1 协同设计？System-1 是一个轻量、语义感知的预测器，在执行前评估每个候选交互的效用，让昂贵的 System-2 只执行那些值得它成本的动作。

机制是一个 predict → gate → execute → update 的条件交互循环，覆盖训练、测试时推理、自适应决策与 agent 工具调用四种场景。核心结论：在理想筛选与等执行成本下，执行算力下降接近 1/ρu（ρu 是效用相关交互的密度），而预测误差、探索需求与分布漂移会吃掉一部分收益。作者用 ρu 作为一个可测量的"scaling 效率坐标"，并主张 "有信息量的算力"比"总算力"更好地描述 scaling。

点评：这是一篇今天所有 agent 实践的抽象层。把 ρu 翻译成工程语言：你的 agent 每发起一次模型调用，这个调用有多大比例是"必要"的？

  • 如果你的 agent 每轮都把全部工具描述塞进 prompt（哪怕 tool search 做了裁剪），你的 ρu 就不高。
  • caveman 那条（输入 token 降 33.2%）本质上是提高 ρu——同样的效用，更少的无关 token。
  • DeepSeek Super-agent 的两级事件过滤 + 直通机制是教科书级的 ρu 提升。
  • GitHub Copilot Fusion 是模型层的 ρu 提升——用更便宜的模型做简单步骤。

四件不同的事，指向同一个数学量。这是我今天最想说的话，放在深度思考里展开。

P2Agent 安全

Pre-Crime for Agents：在 agent 交出密钥前 1 步就把它拦下来 —— 线性探针 82% 命中，零样本监控只有 26%

2026-10-29 · arXiv: Pre-Crime for Agents, at the Last Second

场景很具体：当多个 agent 共享频道和凭证时，一个 agent 可以施压另一个 agent 去违反其操作者的规则——这是集体串谋的第一步。论文问的是：监督者能否在 agent 即将屈服之前就看出来？

答案是能。在六种场景中，一个 peer 最多向 target 施压 20 轮以套出密钥（deploy token），target 往往先拒绝、后来屈服。在每次模型调用后、输出被写出前读取 activations，线性探针在"标记 5% 良性调用"的阈值下抓住了 82% 的泄密调用；同等标记率下，零样本决策模型监控器只有 26%。在 gpt-oss-20b 上，探针读 reasoning 达到 AUROC 0.91。

但论文自己诚实指出了三个限制（这决定了它现在还只能进论文不能进生产）：① 探针会同时标记被允许的披露——它读到的是"即将披露"而非"违规"；② 预警是短程的；③ 任何告警都中止的话，大部分良性 episode 也会被误杀，而二次文本检查修不了这个问题。另外，bag-of-words 分类器逼近探针表现，说明大部分增益来自标签训练而非 activations 本身。

点评：82% vs 26% 这个对比是本文最有价值的部分——它说明在 agent 场景里，用"读模型内部状态"的探针替代"读输出文本"的过滤，是数量级的差距。而"训练成本低到 bag-of-words 也能接近"这条，反而是对所有做 LLM 监控创业的人泼的一盆冷水：你可能不需要可解释性，只需要标注数据。这也和上期日报里那个"agent 行为可观测性"的主题接上了。

P2多智能体

SPLICE：多 agent 系统里的"信息缺口"要动态补边，但补完不能盲信

2026-10-29 · arXiv: Locating and Closing Information Gaps in Multi-Agent Systems（USTC + 通义千问团队 + NUS）

问题：固定工作流的通信图限制了 agent 之间的信息流动，一个 agent 检索到的证据可能永远到不了真正需要它的 agent 手里，形成信息缺口。

难点在于：加一条边虽然能补上证据，但也可能让接收方采纳一个错误的结论，反而覆盖掉本来正确的答案——而只看最终答案，你分不清这两种情况长得一模一样。

SPLICE（Selective Probing and Link Insertion for Closing information gaps in multi-agent Execution）的做法是：原始流程跑完后，用 query 和各节点输出定位可能存在的缺口，加一条有向边，重跑接收方和受影响的下游节点，产出候选答案。采纳决策同时读两次运行的最终答案和流程内部的编辑——接收方移动了多远、新内容来自哪里、这个改动有没有传到最终答案——由一个在这些流程特征上训练的 selector 决定采纳候选还是保留原始。五个 benchmark 上，Web 工具使用任务分数提升 8.0%。

点评："加边之后还得学会不信它"是这个标题真正的重点。多 agent 系统的拓扑不是设计一次就完的，但动态改拓扑的真正难点从来不是"怎么加边"，而是"怎么判断这次加边带来的新信息是不是更可信"。这篇用"流程编辑特征"而不是"最终答案"做判据，是绕开了一个常见的偷懒做法。

P2供应链安全

昨天被投毒的 Claude Code 插件之后：attack surface 正在从"扩展"迁移到"分发渠道"

2026-10-31 · 事件回顾（YouTube 复盘） · 详见上期 10-31 日报头条

上期日报已经详细写了 Cursor 市场上 Claude Code 插件被投毒约 11 小时的事件。今天补一个后续观察：复盘视频里被反复强调的关键点仍是"卸载插件不等于止损"——载荷会落下独立于插件自身的持久化脚本。这条经验对任何"agent 插件"体系都成立：插件的卸载行为不是安全边界。跟今天的 ParameterLabs 那条 ChatGPT 漏洞对照看，两者指向同一个结构性问题：agent 的分发与渲染路径上，每一层都可能引入跨边界的通道，而现有的"卸载/沙箱"心智模型都假设了边界是干净的。

P2实证研究

用 Opus 5.5 给 12 个 JS 框架搭同一个应用：最便宜和最贵的差 86%，而差别主要来自 agent 读不读得懂框架

2026-10-28（HN 11-01 上榜，282 分 220 评论）· Nolan Lawson · The AI cost of JavaScript frameworks

实验设计相当严谨：让 agent 用指定框架搭同一个 PokéAPI 小应用，用官方 MCP/skill 保证框架被公平代表，用无障碍树构造的一致性测试套件防止作弊（不强制 HTML 结构），每个框架跑 5 次取中位数，agent 不知道会被 Lighthouse 测性能。

成本中位数（美元 / 次）：Hono+htmx $2.67 < Astro $2.76 < Nuxt $2.82 < Vanilla $2.98 < Next.js $3.14 < Qwik $3.27 < TanStack Start $3.54 < SolidStart $3.79 < React Router $3.81 < SvelteKit $4.28 < Gracile+Lit $4.65 < Angular $4.97。

最有解释力的发现不是排名，而是原因：SvelteKit 贵是因为 agent 每次运行都要重读 SvelteKit v3 迁移指南（模型训练数据里没有）；Gracile 贵是因为 agent 不熟它，只能去克隆仓库或读 node_modules 里的编译产物；Angular 贵则主要来自代码体量。

而工具使用率的表格更刺眼：Next.js 的 skill 文件只被 1/5 次运行用到、AGENTS.md 2/5；TanStack Start 的 skill 文件藏在 node_modules 里，2/5；Nuxt 配了 MCP，agent 一次都没用。

点评：这是目前我见过最诚实的一份 agent 基准——作者自己列出了方差、承认框架覆盖不均、承认 LLM 随机性会污染结果。但它给出的结论比排名更重要："框架贵"主要不是因为框架本身，而是因为 agent 的训练数据里没有它，且为它准备的 skill/MCP 常常不被发现。这对 2026 年的技术选型是个很实际的反直觉提醒——你的框架选型现在部分是在赌"agent 的训练数据覆盖度"，而不只是赌 DX 和性能。而"skill 藏在 node_modules 里就没被发现"这条，几乎适用于所有把 agent 能力包在依赖里的做法：能被发现的 skill 才存在。

P2工具生态

Treg × Jev：把"找人"变成 agent 的一个工具调用 —— 比 Clay 便宜 85%，且正确率 43% → 78.2%

2026-11-01 · 量子位 · GitHub: superdesigndev/treg（★6,953）· TypeSafe AI

💭 深度思考

洞察一 · 今天四件毫不相干的事，都在优化同一个数学量：ρu（效用相关交互密度）

把今天的内容摊开看，有四条线索在讲不同领域、不同层级的事：

  • DeepSeek Super-agent（agent 编排层）：两级事件过滤省 token，订阅直通省 30% Router 决策 + 37% 缓存 token，投机执行避免无谓打扰——全部指向"让每一次交互都更可能有用"。
  • GitHub Copilot Fusion（模型层）：在 Opus 5.5 与更便宜的模型之间路由，"便宜一半、只差 2 分"——把简单步骤交给便宜的模型，是最直接的 ρu 提升。
  • caveman（上下文层）：输入 token 降 33.2%，响应 token 降 63.6%，JetBrains 实测质量损失不可测量——把无关内容从上下文里挤出去，ρu 直接上升。
  • arXiv 2610.39497（理论层）：把这件事命名为 ρu，并证明理想条件下执行算力可省至约 1/ρu。

为什么这个统一视角有价值（我的判断）：过去两年行业的优化叙事是"模型更强了"，所有工程努力都在追模型的每一分能力提升。但 ρu 提供了一个完全不同坐标系的度量——它衡量的不是"你的 agent 能不能做到"，而是"你的 agent 每花一份钱，有多大比例花在了真正推进任务上"。

这个坐标系的实操价值在于：它在模型能力停滞时依然可以改善。你现在拿到的模型能力是一个给定条件，但你的 ρu 完全由你自己的架构决定。三个具体动作，按投入产出排序：

  1. 先量。把你 agent 每次模型调用的完整输入输出 dump 出来，算"这次调用最终影响了任务结果"的比例。这个数就是你的 ρu。绝大多数团队的第一次测量结果会让自己不舒服——通常是因为有一半的调用在反复读取同一批没压缩的日志。
  2. 再砍上下文。这是 ROI 最高的一刀，而且不需要换模型、不需要换框架、不需要重训。caveman 的 33.2% 和 Elastic 的 63.6% 都证明这条路走得通，且质量损失可测量为零。
  3. 最后才换模型。Fusion 式的模型路由确实有效，但它是把复杂度从你手里转移到平台手里——你自己做路由会同时背上评测、灰度、成本回退的一整套活。在 ρu 的框架下，正确的顺序是先让每一步都必要，再去挑更便宜的模型执行它。反过来做，等于用更贵的模型去执行本来不必要的步骤。

最后一个推论：如果 ρu 是关键坐标，那么"我的 agent 比你的强"这句话在 2026 年越来越不可验证，也越来越不重要。真正可辩护的差异会变成："我的 agent 每 100 次调用里，有 95 次是有必要的，而你是 60 次。"这是一条从模型能力竞赛转向系统效率竞赛的路线，而且它今天就能开始做——不需要等下一版模型。

洞察二 · 今天的两个头条，一个在讲"agent 该有多自主"，一个在讲"自主的代价" —— 而它们发生在同一个生态里

今天的两条头条表面上毫无关系：DeepSeek 开源了一个"尽可能自主、少问人类"的 agent；ParameterLabs 演示了"一个链接就能接管任意人的 ChatGPT 账号"。

但把它们放在一起看，会浮现出一个我觉得更重要的判断：自主性和攻击面是同一个东西的两面。

具体地说：

  • DeepSeek 的 Super-agent 让 agent 获得了三种新能力：主动发起（投机执行）、跨会话保持上下文（连续性）、跨平台监听（GitHub + 飞书）。每一种能力都是自主性的来源，也都是新的攻击面。一个会主动扫读你所有群聊的 agent，和一个只在你按下回车时才行动的 agent，被入侵后的损失差着几个数量级。
  • ParameterLabs 那条链利用的恰恰是"内容渲染"这个能力——而渲染正是 agent 必须有的能力（要展示代码、要渲染图表、要预览 HTML）。DeepSeek 的架构文档里明确列了 "003 Execution / 004 Prompts / 005 Panel" 这些部分，也就是说它也要渲染人类产生的内容——同一个渲染通道，同一类风险。

更值得警惕的是"用户自己写的规则"这条新风险面。Super-agent 的哲学文档里有一条："It acts only when asked, or when a written rule allows it"——团队自己写的规则会直接授权 agent 做事。这就产生了一个全新的攻击面：通过 prompt injection 篡改 agent 的规则文件，让 agent 获得超出预期的授权。注意这与传统 prompt injection 完全不同——传统 injection 是让 agent 说错话，而这一类是让 agent 在"被授权的状态下"做它本来有权做的事，防御难度高一个量级，因为每一步都合法。

所以我的建议是（很具体）：

  1. 给 agent 的"规则"和给 agent 的"数据"用完全不同的信任级别。规则（谁能命令它、什么条件下允许主动行为）应该来自签名/版本控制的配置文件，来自不可信来源的输入只能进数据区。如果这两者在你的架构里最终汇进同一个 prompt 模板，那你就有一个"合法权限提升"漏洞。
  2. 把"主动性"当成一种需要单独授权的权限，而不是 agent 的默认行为。DeepSeek 自己的建议是"proactive work only recorded"（主动行为默认只记录不执行）——这条建议应该成为行业默认，而不只是这一家的默认值。
  3. 把今天 ParameterLabs 那条攻击链当成 checklist 跑一遍你自己的 agent：postMessage 的 origin 校验、innerHTML 的 trusted 标记、CSP 白名单里的 JSONP 端点、srcdoc iframe 的 sandbox 属性。四项里任何一项是"没有"，你的 agent 就有一条通往用户 session 的路。

最后一句主观判断：今天的两个头条其实在说同一句话——"自主性正在变成 agent 系统的默认货币，而它的定价机制还没建好"。DeepSeek 用极其认真的工程（1500 行文档、MIT 开源、诚实的 TODO）把自主性往前推了一大步；ParameterLabs 用 12 分钟证明了自主性系统的一个渲染层就足以被整体接管。这两件事之间的时间差是 48 小时——我建议所有做 agent 的人，先去看 ParameterLabs 那篇的技术细节，再决定要不要让自己的 agent 更主动。顺序反了的话，你会在自己产品上线后才发现代价。
