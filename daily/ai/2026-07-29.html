MCP 协议发布史上最大更新：彻底走向无状态

P0 Agent Infrastructure · 2026-07-28

Model Context Protocol (MCP) 正式发布了 2026-07-28 版规范——这是一次根本性的架构变革。MCP 从一个有状态的、需要握手的双向协议，转变为无状态的请求/响应协议。这意味着什么？

  • 取消握手与 Session：不再有 initialize/initialized 交换，不再有 Mcp-Session-Id header。每个请求自包含协议版本、客户端身份和能力声明。
  • Multi-Round Trip Requests (MRTR)：服务器可以在单次请求中返回「需要更多输入」，客户端重试携带补充数据。这在无状态约束下实现了原来有状态才能做的多轮交互。
  • Header-based 路由：Mcp-Method 和 Mcp-Name 直接走 HTTP header，网关层即可路由和鉴权，无需解析 JSON body。
  • HTTP+SSE 正式弃用：给了一年过渡期，全面转向 Streamable HTTP。
  • Tasks 扩展正式化：从实验性核心提升为正式扩展 io.modelcontextprotocol/tasks，支持 poll-based 任务管理和更新。
💡 为什么这是今日最重要的事：MCP 从「玩具协议」进化到了「生产级基础设施」。无状态化意味着你可以把 MCP server 部署在标准负载均衡器后面、在 Lambda/Cloud Run 上水平扩展、用 CDN 缓存 tool 定义——之前这些都是奢望。AWS Bedrock AgentCore 已宣布同步支持。这对 agent 开发者意味着：你的 MCP 工具服务器现在可以在真正的生产环境里跑了，不再需要维护脆弱的 WebSocket 长连接。

📄 StateAct：用程序状态替代像素——长时程 Computer-Use Agent 的新范式

P0 Agent Computer Use · Hugging Face Papers · 2026-07-28

当前的 computer-use agent（如 Claude Computer Use、OpenAI Operator）依赖屏幕像素理解界面状态，这在长时程任务中面临严重挑战：分辨率损失、视觉歧义、上下文窗口爆炸。StateAct 提出一个颠覆性思路：让 agent 直接读取程序状态（DOM tree、accessibility tree、窗口层级）而非截图。论文证明这种方法在长时程任务中显著优于 pixel-based 方法。

💡 对 agent 开发者：如果你在做 GUI automation agent，这个方向值得密切关注。程序状态作为 agent 的观测空间，信息密度远高于像素，token 消耗也更少。这可能会成为下一代 computer-use agent 的标准做法。

🚀 Kimi K3 发布：2.8T 参数，史上最大开源模型

P0 Open Source Architecture · 2026-07-28

Moonshot AI (Kimi) 发布了 Kimi K3——这是一个 2.8 万亿参数的开源模型，一举成为目前最大的 open-weight 模型。Sebastian Raschka 第一时间发布了详细的架构分析。核心亮点：

  • LatentMoE：类似 Nemotron 3 Ultra，将大规模线性层压缩为低维潜在空间后进行 MoE 路由，大幅降低推理时的内存占用。
  • Multi-Head Latent Attention (MHLA) + Kimi Delta Attention：对传统 attention 机制的效率改进，减少 KV cache 开销。
  • 推理效率优先：整体架构设计哲学是「在不牺牲太多性能的前提下，让推理更快更省」——与 DeepSeek V4、Nemotron 3 的大方向一致。
  • 可本地运行：社区已验证在 M1 Max 上可运行。
💡 这不是又一个「参数更大就更好」的故事。Kimi K3 的真正意义在于它证明了一件事：开源社区现在有能力训练并公开 2T+ 级别的模型了。这不是 Meta 或 Google 放出来的，而是一个相对小得多的团队（Moonshot）做到的。加上 LatentMoE 等效率技术，它为 agent 开发者提供了一个真正可以在本地或私有云上部署的 frontier 级模型。这对「不想把数据送给 API 厂商」的 enterprise agent 场景意义重大。

💭 深度思考

🧠 MCP 无状态化 + Kimi K3 开源 = Agent 基础设施的关键转折

今天的两条 P0 新闻看似不相关，但合在一起指向同一个趋势：agent 开发的「民主化」和「工业化」正在同时加速。

MCP 的无状态化解决的是「怎么让 agent 在生产环境稳定运行」的问题——这是工业化。Kimi K3 的 2.8T 开源模型解决的是「不依赖 API 厂商也能用上 frontier 模型」的问题——这是民主化。

两者叠加，意味着一个团队现在可以：用 Kimi K3 等开源大模型在私有基础设施上部署推理，通过无状态 MCP server 连接企业内部工具和数据源，构建完全自主可控的 agent 系统。几个月前这还需要大量的工程妥协——现在正在变成工程现实。

📌 Actionable：如果你的团队还在用 stateful MCP + API-only 模型，现在就是重新评估架构的好时机。无状态 MCP 的迁移成本不高（一年过渡期），但带来的可扩展性提升是质变的。

🔍 Computer-Use Agent 的新方向：告别像素

StateAct 的「程序状态 > 像素」思路值得所有做 GUI agent 的开发者重视。过去一年我们看到了大量基于截图的 computer-use agent，但它们在长时程任务中几乎都会遇到上下文窗口和视觉歧义的问题。直接读取 DOM/accessibility tree 不仅能解决这些问题，还能让 agent 的操作更精确、token 消耗更低。

同时，这也意味着 agent 的安全边界需要重新思考——一个能看到 DOM tree 的 agent 比一个只看截图的 agent 拥有更多信息。权限控制不再只是「能不能截图」，而是「能访问哪些程序状态」。
