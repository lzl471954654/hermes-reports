MIT CSAIL：GPT-6 Astra 能原生"读"和"写"神经网络权重 —— 优化器之外的第二条路

2026-11-02（发布当日登上 Hacker News 首页，30+ 评论）· Sparks of Weight-Space Programming · 作者：Rikiya Takehi, Jayden Teoh, Alex Zhang, Omar Khattab（MIT CSAIL）· 公开日志：github.com/RikiyaT/lm_understand-logs

发生了什么

MIT CSAIL 的一篇长文给出了一个我觉得被严重低估的结果：当前的前沿 LLM（用 GPT-6 Astra）能直接读懂、并且直接改写一个神经网络的原始权重——不通过梯度、不通过 Adam/Muon 之类的符号优化器、也不允许写训练循环。模型被允许的只有"自然语言 + 一段 Python"。他们把这套做法叫 Weight-Space Programming（WSP）。

核心论点是：过去十几年，我们把"优化"这件事全部外包给了符号优化器，因为没人能手写神经网络权重。但 LLM 优化的对象已经从 prompt 扩展到 harness、训练脚本、超参——现在，可微的那一半也该轮到 LLM 了。

实验 1：只给权重，它能说出这个网络是干什么的？

四个用 PPO 训练的网格游戏策略网络（Breakout / Pong / Pac-Man / Freeway），输入通道、动作空间、网络维度完全相同，所以不看权重根本分不出来。把 17,253 个权重以文本形式喂给 Astra，不告诉它候选游戏是哪些，它四个全猜对。

它的推理路径很具体：看第一层权重集中在输入图的哪个位置——Breakout 的 paddle 权重沿着底边那一行；再看输出层怎么区分动作。

实验 2：扩散模型也一样。三个 DDPM（12×12 灰度图，分别训练生成圆/方/三角），Astra 全部答对，并且自己把形状画了出来。有个细节特别说明问题：它把所有形状都画成了轮廓线，而真实模型生成的是实心图形——这个"错误"恰好证明它没有跑前向传播，而是真的在读权重的几何结构。

实验 3：把输入层和输出层都删掉，只给中间 4 个 transformer block。

三个 7.16M 参数的字符级语言模型，分别训练在 Python 源码、日文罗马字（青空文库）、英文维基。剥掉输入输出层后，网络已经无法在任何文本上运行，也没有任何维度标签能指明哪个字符是哪个。

Astra 三次全部答对语言，并且找出了每一个 induction head（复制头）——即让模型重复它见过的文本的那些头——而且它标注的位置与实际运行测量的结果逐一吻合。它的推理方式是：先找到往前看一个字符的复制头，再通过矩阵相乘推出后面那些"拿着它找到的东西往下搜"的头。

作者特别注明：这种分析方法其实早就由 Elhage et al. 提出过——他们只是没告诉 Astra。Astra 是自己重新推出来的。一个模型重新发现了 circuit-level interpretability 的经典方法，这本身就是一个可解释性的强信号。

实验 4：它能"修"一个坏掉的网络吗？

Kinetix 环境里的"车上坡"关卡，官方 PPO 训练出的是一个收敛到局部最优的策略：车直接冲向斜坡卡住，256 次 episode 成功率为 0%。把权重、场景描述和一段录像交给 Astra，让它解释失败原因并只改写权重——一次尝试、无工具。Astra 的编辑改了 3.5% 的权重，之后 1,024 次 episode 成功率 100%。

它的解法很干净：它没有重训，而是在网络中额外接了一条小的旁路，读车的位置和速度，检测到绿色轮子越过红色条带后就把旁路关掉，剩下的路交给原来训练好的网络走。

实验 8（最有工程价值的一个）：直接修一个真实语言模型。

对象是 Qwen3.5-0.8B。任务：让它数学好一点。关键在于——Qwen 自己的 model card 就警告过这个模型有"reasoning loop"的问题。Astra 在不跑梯度、不写训练循环的前提下，从权重里定位到了造成这个循环的结构问题，原生编辑了 0.016% 的权重。同一个采样设置下：

以及实验 5/6：让它从零写出能玩三个 MinAtar 游戏、以及能下围棋的网络。

为什么这件事重要（我的判断）

我的看法可能偏激进，但这篇论文把一个大家默认的边界划掉了：我们一直认为"模型改权重"和"人改代码"是两种活动，前者靠梯度，后者靠语言。但 LLM 已经在用自然语言读懂一个模型的内部结构，并且能定位到具体是哪些参数导致了具体的行为缺陷。

立刻能想到的三个后果：

  • Interpretability 从"工具"变成"可编程接口"。过去读一个模型的 circuit 要么靠训练好的探针，要么靠人肉看激活。现在多了一条路：把权重给模型，问它"这个网络在干什么"。当然这还很脆（只在小模型上验证过），但它把 interpretability 的成本结构完全改写了。
  • 对齐干预从"重新训练"降到"改几个数"。0.016% 的权重修改同时提升了数学和指令遵循——注意，不是牺牲一个换另一个。现在的对齐手段（RLHF/DPO/SFT）都是全局重训，成本是几千 GPU 小时；WSP 展示的是另一种成本结构：定点手术。
  • Agent 的能力边界往上移了一层。今天的 agent 优化的是 prompt、harness、工具链。WSP 说 agent 还能优化模型本身——一个能自己改自己权重的 agent，在安全上的含义是极其重的（这也是为什么这类东西必须极端谨慎地评估）。

给 agent 开发者的具体启示

  1. 先看论文的"不许做什么"，再看它做了什么。这一篇的实验设计非常克制：禁止跑网络、禁止 search、只给中间层、每一步都检查有没有作弊。作者甚至在实验 3 里说"我们检查了每一次 run"。这是你评估任何"模型能理解什么"类宣称时应该照抄的标准——先找它的约束条件，再看结论。
  2. 你要的"能改权重"的能力，现在就能用另一条路拿到。如果你不想等 LLM 直接改权重，今天在 agent 里做"诊断 + 定点干预"是可行的：让 agent 读日志、定位到具体模块、提出最小化修改，然后在测试保护下应用。这是很多 agent 团队已经在做的事——只是没人把它叫 Weight-Space Programming。
  3. 值得盯的场景：小型专用模型的"手工调优"。一个 7M 参数的分类器、一个特定格式的抽取器、一个在你自己数据上训的小模型——这类场景用 LLM 去读权重然后手改，比再训一轮便宜得多也快得多。

保留意见：所有实验都在小规模模型（7M–0.8B）上完成，唯一的大规模案例是 Qwen3.5-0.8B，而且只有一次成功。"LLM 能理解权重"这个结论目前离"LLM 能可靠地理解任意权重"还很远——从 7M 到 744B 的外推是完全未知的。这是一篇"点亮方向"的论文，不是一篇"可以依赖"的论文。

OpenAI 公开 Pando：Git 兼容后端，push 延迟降 5 倍，每天服务近 1 PB —— agent 数量涨 24 倍后，Git 先撑不住了

2026-11-02 · OpenAI: Scaling Git at OpenAI · The New Stack 详读

OpenAI 公开了内部自研的 Git 兼容后端 Pando。背景数字：相比 2024 年 Q1，OpenAI monorepo 的季度提交量到今年底预计增长超过 2,400%——这基本上就是 agent 写代码的曲线。

他们的问题很具体：Git 后端的可靠性已经掉到 90% 以下，fetch 变慢、merge 失败。而团队决定不抛弃 Git 生态，因为二十年来所有工具都围绕 Git 建起来了。

Pando 做了两件"传统 Git 服务器视为必须"的事的反面：

  • 不再要求所有分支同时保持一致状态。传统 Git 服务器对整个仓库的写入排序，于是并行开发时，push 到 A 分支的请求会排队等 B 分支。Pando 每个分支独立处理，互不相关的分支的 push 不再互相等待。
  • 不再为每个 fetch 客户端专门构建 packfile。push 时，Pando 在 packfile流入 blob 存储的流式过程中就完成校验，不落地解包；只记录新分支 tip、packfile 位置和依赖关系到元数据存储。默认只 advertise trunk 分支作为基线，这样一个 pack 可以被已有 trunk 历史的客户端复用。fetch 时按客户端已有历史挑选需要的 pack，通过 packfile-uri 协议分发。

缓存层叫 Express，走区域缓存，命中率 >99%；标准云 VM 上 clone/fetch 可以跑满 10 Gbps 网卡。

代价他们也写清楚了：当客户端同时查看多个分支时，可能看到略微不同的时间点。OpenAI 的论点是：用户和 agent 真正在乎的只是单个分支上更新的顺序。

为什么对 agent 开发者重要

这是我今天读到的、对 agent 工程最直接的一条基础设施事实。三个观察：

  1. "agent 化的 Git"是一个正在成型的独立问题域。注意开头提到的两条新闻线索：前 GitHub CEO Thomas Dohmke 创办了 Entire，Cursor 做了 Origin——它们都还建立在 Git 之上。而 Anthropic 走的是另一条路（基本从零重写客户端和架构）。两条路线的成本结构差异巨大，而这个差异未来会决定哪些 agent 产品能建成。
  2. Per-branch 独立是 agent 并行的天然需求。传统 Git 服务器的全局写入排序，对人类开发者是"顺序混乱"的麻烦，对 agent 来说是直接的吞吐上限——因为 agent 的天然工作方式就是"几十个 worker 各自 push 到自己的分支"。Pando 的做法本质上就是为 agent 的分支拓扑重新设计了 Git 服务器。
  3. 如果你在自建 agent 平台，现在就该检查你的 Git 层。判据很直接：当你的 agent 数量增长 10 倍时，你的 push 延迟是常数级还是线性增长？如果线性，那它就是你的下一个瓶颈。OpenAI 的答案是"顺序排序整个仓库"，而 OpenAI 有 2,400% 的提交量增长才撞上这堵墙。

为什么这条重要

插件生态的分水岭从来不是"有多少插件"，而是造插件的成本。当创建插件的门槛从"写代码 + 打包 + 发布"降到"说一句话"，会发生三件事：

  • 插件的长尾会爆炸。历史规律是：制作门槛下降 10 倍，长尾内容数量增长远不止 10 倍。DeepSeek 演示的 3D 渲染器、视频剪辑工作台这类东西，恰好是传统插件市场里最不会被人类开发者去做、但用户真的想要的那部分。
  • 但这也把审核问题推到了台前。ShiftDelete 的报道里明确提了 security caveats。一个能自己写、自己安装、自己运行代码的 agent，如果用户不知道它生成的插件干了什么——这就是一个新的供应链攻击面，而且这个供应链的入口是自然语言。
  • 时机很关键。这是 DeepSeek 在 10 月 31 日开源 Super-agent 原型（详见上期日报）之后仅两天的动作。先给"常驻 agent"架构，再给"造工具"能力——这两件事合起来的含义是：DeepSeek 想让 Harness 成为一个 agent 操作系统，而不只是 Claude Code 的中国版。

给 agent 开发者的启示：如果你在做 agent 平台，"让用户用自然语言造自己的工具"这件事几乎一定会被期待——但你要先想清楚审核与权限模型。思考方向：生成的插件默认在什么沙箱里跑？能不能声明它需要的能力？能不能回滚？这三个问题的答案决定了你的插件生态是资产还是负债。

vercel-labs/agent-desktop：今天 GitHub Trending 第一 —— computer use 走 accessibility tree，不做像素匹配

2026-11-03 · github.com/vercel-labs/agent-desktop（Rust，Apache-2.0，9,576 stars，今日 +2,275，v1.0.2 发布于 10-30）· npm: agent-desktop

Vercel Labs 的 agent-desktop 登上 GitHub Trending 日榜第一（+2,275 stars）。它给 agent 提供 computer use 能力，但走了一条和主流不同的路：通过操作系统的 accessibility tree 读取和操作桌面应用，而不是截图 + 视觉模型 + 像素匹配。

接口设计很干净：snapshot 返回 JSON，每个可操作元素带一个 ref；agent 对 ref 动作，然后重新 snapshot 验证。文档里那句话是重点："the loop stays in your agent"——观察-行动-观察的循环在 agent 侧，不在工具侧。CLI 与 C 库，macOS / Windows / Linux 通用，npm 安装即用。

值得单独提的安全设计：即使是 headless 调用，也禁止前台激活和合成输入。另外 README 里也直说了隐私风险——snapshot、剪贴板读取、截图、命令输出都可能包含桌面私密内容。

为什么这条值得单独看

现在的 computer use 几乎全是"看屏幕 → 猜坐标 → 点"，这条链路的三个问题都很硬：慢（每步一次视觉推理）、脆（分辨率/主题/遮挡一变就崩）、贵（每步都吃一遍图像 token）。accessibility tree 把这三件事同时解决了——因为 DOM/a11y tree 本身就是结构化的、可序列化的、无需推理的。

代价也很清楚：accessibility tree 只有实现了 a11y 接口的应用才可用，很多自绘 UI、Canvas、游戏界面读不到。而且它读不到"视觉上呈现但语义上不存在"的信息。所以这条路的正确定位是主路径 + 视觉回退，不是替代。

可操作建议：如果你在给 agent 做桌面操作能力，先按 ref-based 的方式设计你的工具接口，把像素匹配留作兜底。这不只是更快更稳——它让 agent 的每一步操作变成可验证的结构化动作，可以直接进日志、可以做断言、可以做回放审计。这对"agent 出错时你要能解释它到底点了什么"是决定性的。

为什么这条必须进 P0

因为它是今天唯一一条能直接否掉一个流行工作流的证据：把老文件丢给 LLM 说"现代化一下"。而这个工作流现在被大量 agent 工具默认启用，甚至包括一些自动化的"代码清理 agent"。

论文给出的机制解释也很有价值：大部分破坏是不必要的——模型倾向于"做点什么"，而正确动作往往是"什么都不做"。这和 DeepSeek Super-agent 那篇里的"投机执行"原则正好互为镜像：一个好的 agent 必须同时学会"提前动手"和"果断不动"。

给 agent 开发者的具体启示

  1. 在你的 agent 里区分"值得改"和"必须改"。这不是靠模型自觉的——需要外部证据。Rector 这类规则工具在"该不该改"上比 LLM 可靠得多，因为它有 PHP 8.3 的实际语义。正确的架构是：规则工具决定改什么，LLM 决定怎么改——而不是反过来。
  2. 必须有"保持行为一致"的自动化验证——这正是 630 个隐藏行为检查干的事。没有这个，你的 agent 就是在批量生成无法验证的 diff。
  3. 给你的 agent 一个明确的"不动"出口。如果 prompt 里全是"现代化 / 优化 / 清理"，模型几乎不会返回原样。建议把"保持不变"做成一个显式的、同样有价值的动作，并给它单独的评估口径。
  4. 默认无执行反馈的单文件模式是最差的工作方式。论文里"没有项目上下文、没有执行反馈"是刻意设置的最差条件，但它恰好描述了大量真实 agent 的默认行为——多文件、有依赖、有测试反馈的情况下结论会不同，但"能不能自己跑一遍验证"这个变量，值得你认真配置。

P0arXivAttentionPrefill 成本

两篇 arXiv 把"长上下文很贵"这件事量化了：prefill 的能耗是线性 + 二次的叠加

2026-10-29 / 10-30 · arXiv: 2610.39621 — The Real Cost of Context · arXiv: 2610.42147 — Latent Sparse Attention (LSA)

《The Real Cost of Context》（2610.39621）：系统性地 profile 了 prefill（输入）与 decode（输出）两个阶段的计算时间与能耗，并用广义线性模型拟合。结果：decode 的计算时间和能耗随输出长度线性增长，而 prefill 同时呈现线性和二次两种标度。

作者的批评很到位：以往的工作只盯着生成的 output token，而 agentic 工作流真正的特征恰恰是巨大的输入上下文。

《Latent Sparse Attention》（2610.42147）：针对 100 万 token 以上的超长上下文，全注意力贵到不可行；现有稀疏注意力方法要么索引本身仍是二次的，要么在超长尺度上掉精度。LSA 的做法是在习得的隐空间里对 key 做层次聚类，query 只对聚类层级打分而不是对每个 key 打分，从而在 prefill、decode 和训练三个环节都变快；并提出 Distilled-LSA 变体用于推理时加速。

为什么对 agent 开发者重要

这两篇拼起来是一组可以直接用来做架构决策的数字：

  1. 你的 agent 的真实成本大头在 prefill，不在生成。这和直觉相反——大家盯 token 价签时盯的是输出。带长上下文的 agent（每轮把整个历史 + 检索结果塞回去）其成本曲线里 prefill 占主导，而且随上下文长度超线性增长。这条结论直接支持"压缩上下文 / 分层记忆 / 缓存复用"这类工程投入。
  2. 它也解释了为什么"只算 output token"的成本模型会系统性低估 agent。如果你的账单模型只统计生成量，那你看到的成本曲线是错的——真实成本会更早、更快地压垮你。
  3. 可操作建议：给你的 agent 做一次 prefill/decode 成本画像。用 GLM 拟合你自己的数据，测出"上下文长度 → 成本"的实际曲线，找到那个"再长一点就不划算"的拐点。这个数字应该是你 agent 上下文策略的硬约束，而不是拍脑袋定的 token 预算。
  4. LSA 这类"层级索引"思路值得跟踪：如果 agent 场景真的普遍跑在 100 万 token 上，"稀疏注意力 + 隐空间层级"很可能成为默认架构。值得关注后续是否有开源实现。

为什么值得看：Anthropic 原本 2025 年 10 月在 Claude Code 里做 skills 时发现"通用知识工作做得好，但缺程序性知识"，于是 11 月就有开发者在 GitHub 上发了成千上万个 skill，还自己写了给 Codex、Cursor、OpenCode 的加载器。这个从"某家产品的功能"到"跨厂商开放标准"的速度，是过去两年 agent 生态里最快的标准化速度之一。

对 agent 开发者的启示：如果你在做 agent，"用 SKILL.md 而不是硬编码 prompt"已经是明确的方向——可读、可版本化、可被别的 agent 加载。而且现在有 AAIF 这样的中立托管方了，意味着你可以开始正式投资 skill 生态，而不用担心标准易主。注意路线图里那条"安全指南"——skill 是从网络加载的可执行内容，它的供应链安全问题会和 npm 一样真实。

P1arXiv安全预训练投毒

0.1% 的预训练数据投毒，就能让 agent 后门执行任意命令 —— 4B 模型攻击成功率 92%，且模型越大越容易中招

2026-10-27（10-31 HN 首页）· arXiv: 2610.37741 — Agentic Backdoors via Pretraining Poisoning · 代码：github.com/safety-research/agentic-backdoor

论文第一次证明：在预训练语料里埋毒，可以给 agent 植入一个远程代码执行后门。作者从零预训练了 0.6B / 1.7B / 4B 三个 Qwen3，再用干净流程后训练成 CLI agent。

只要 0.1% 的预训练语料被污染，后门就被植入：触发条件出现时 agent 执行攻击者指定的命令，干净输入下表现完全正常。攻击成功率随模型规模上升——4B 模型在 0.1% 投毒率下 ASR 约 92%，即使把投毒率降到 0.0005% 仍然有效。

为什么这条对 agent 开发者是直接可操作的：你现在训练的每一个 agent 模型，都建立在一个"预训练语料是干净的"假设上。这个假设现在有实验证据支撑不住它了。可操作的方向：

  • 不要信任上游 checkpoint 的"干净"声明。如果你基于 Qwen / Llama / GLM 等开源权重做后训练，你的后门风险继承自它的预训练数据——而你无法审计那部分数据。
  • 在 agent 的工具执行层做触发器检测。论文说"干净输入下表现正常"——那检测不该只看输入，还要看行为偏离。具体的低成本做法：对 agent 的命令执行做 allowlist + 对"罕见参数组合"告警。
  • 这个发现对"更强的模型更危险"是一个反向证据。论文明确观察到 ASR 随规模上升——也就是说你换更大的底座模型来提升 agent 能力的同时，攻击面也在变大。这是个需要写进风险评估的非显然结论。
P1arXivAgent 协议Typestate

Concordat：把 agent 当成一个"有限状态协议"来实现 —— 不合法的工具调用在产生副作用之前就被拒绝

2026-10-27 · arXiv: 2610.37461 — Concordat: Typed Sessions for LLM Agents

问题定义得很准：agent 越来越被允许做有后果的动作（取消预订、发起退款、改账户），而支配这些动作的规则——"改任何东西之前必须获得客户明确确认"——通常只写在 prompt 里，然后被模型以"它选择遵守"的方式遵守。

Concordat 的做法：把 agent 当成一个接口是有限状态协议的对象（typestate / session types 的精神），并在运行时强制执行。具体机制：

  • 每一轮只向模型提供当前协议状态下合法的工具；
  • 不在集合内的调用在产生副作用之前就被拒绝；
  • 保留给人类的决策点只能被"请求"，不能被 agent 自行执行；
  • token 与 tool-call 预算在交接之间线性计费与拆分。

点评：这是今天最"工程可落地"的一篇。它的核心洞察是：不要指望模型遵守 prompt 里的规则，要把规则编码进工具可见性本身——模型看不到违规工具，违规就不可能发生。这比事后审计强得多。给 agent 开发者的具体启示：把"当前状态下允许什么"变成由代码生成，而不是由你在 prompt 里描述。用 MCP 的工具接口（每个工具单独注册）天然适合做这件事——你可以在网关层按状态过滤暴露哪些工具。

💭 深度思考

洞察一 · 今天八条 P0 里，有五条在讲同一件事：模型已经不是瓶颈了，模型下面那一层才是

把今天的内容按"它在解决哪一层的问题"重排一遍，会看到一个非常整齐的图案：

  • 权重层：WSP 让 LLM 直接读写神经网络权重；arXiv 的预训练投毒论文证明权重里能藏 RCE 后门。
  • 上下文层：prefill 成本是线性 + 二次的叠加；LSA 用隐空间层级聚类给超长上下文降本。
  • 部署层：colibri 用 1,300 行 C 把 744B 塞进 25 GB 内存；LongCat-2.5 用 W4A4 把吞吐拉 +43%。
  • 版本控制层：OpenAI 的 Pando 为"每个分支独立"重写了 Git 服务器的并发模型。
  • 协议层：Concordat 把 agent 的行为规则从 prompt 移到工具可见性；AAIF 收编 Agent Skills 这个跨厂商标准。

这五层的共同点是：它们都不是"让模型更强"，而是"让模型可以被更有效地承载、约束和监控"。

为什么是现在？我的判断是三个条件在最近同时成立：（一）模型的边际能力仍在快速提升，但提升的形态从"更会回答"变成了"更会执行"；（二）单次任务成本已经低到可以让 agent 承担起系统级的工作量（Nous 那条：19 小时、1,393 个 agent、$19k）；（三）agent 的产出开始进入有后果的领域——退款、订金、改账户、跑命令、改代码。

（二）和（三）放在一起才是真正的转折点：当 agent 的产出量足够大、后果足够真实，瓶颈就从"模型能不能做"转移到"系统能不能承载和约束它"。这不是新架构的胜利，是新约束的出现。

给 agent 开发者的 actionable 建议：如果你现在只优化 prompt 和模型选择，那你优化的是这次浪潮里最不稀缺的那一层。值得投入的是：你的 agent 系统的"承载层"在哪里漏？具体三个自查项——(1) 上下文成本有没有被 profile 过？(2) agent 执行工具的权限是不是只写在 prompt 里？(3) 你的"版本控制层"（agent 的产物、prompt、工具定义、技能包）在 agent 数量涨 10 倍时会先坏在哪？

洞察二 · 今天有四篇独立材料在讲同一句话：你测的那个数字，不是你该优化的那个数字

今天有四条互不相干的线索指向同一个问题：

  • OpenAI LifeVal：它测的是"生活琐事"，不是 SWE-bench——因为任务来自时间使用研究和 3,995 人的真实调查，而不是研究者想象的困难。
  • MIT Tech Review（赞助稿）：测 "cost per merged PR"，不是 token 数；并明确警告"要同时跟踪返工和缺陷，否则更便宜可能只是更烂"。
  • arXiv 的 Legacy PHP 研究：测"行为是否保持一致"（630 个隐藏检查），不是"现代化分数"——结果发现现代化分数最高的模型兼容性并不更好。
  • arXiv 的 Prefix Executability（2610.40444，10-29）：测"轨迹的前缀是否始终可执行"，不是"最终是否成功"——论文明确指出"只看结果的排序和看前缀的排序会分叉"，尤其是那些基于未验证计划做条件判断的 agent。

这四篇的方法论是同一个：把"容易测的代理指标"换成"接近真实后果的指标"。而且注意这个转向的共同驱动力——agent 正在从"做一次任务"变成"在真实系统里持续运行"。一次性的演示可以用成功率和 benchmark 分数衡量；持续运行的系统必须用"可验证的、无副作用的、端到端的"指标衡量。

具体到你的 agent，该换掉哪个指标？我给一个判断标准：如果你的 agent 指标和你的用户价值之间隔着"一次人工确认"，那这个指标就选错了。而"人工确认"的具体形态，决定了该换什么：

  • 如果形态是 "这个 diff 对吗" → 换成 合并 PR 数 / 每个 PR 的返工次数。
  • 如果形态是 "这步 tool call 能执行吗" → 换成 前缀可执行率（Prefix Executability），因为最终成功率会掩盖中间步骤已经烂掉的事实。
  • 如果形态是 "改完之后行为还一样吗" → 换成 行为保持检查，并把规则工具用在"该不该改"的判断上。
  • 如果形态是 "这到底是我的活还是它的活" → 换成 从真实用户需求推导出来的任务集（LifeVal 方法论）。

最后一句主观判断：2026 年下半年的 agent 工程，正在从"提示词工程"迁移到"度量工程"。谁先把度量搞对，谁的 agent 迭代速度就是别人的几倍——因为在一个错误的指标上做优化，迭代得越快，离目标越远。
