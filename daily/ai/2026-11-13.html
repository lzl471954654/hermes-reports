P0 · 行业格局Nvidia出口管制

黄仁勋辞职，Nvidia 进入"CFO 守门"时代——但真正的系统性风险，在同一天被另一篇论文坐实了

11 月 12 日，Nvidia 董事会正式公告：黄仁勋辞去总裁、CEO 职务及董事身份，立即生效。CFO Colette Kress 兼任临时 CEO 并继续掌管财务，Harvey C. Jones 出任公司史上首位独立董事长，董事会正启动永久 CEO 的内外部搜寻。这条消息在 Hacker News 上以 2774 分 / 2639 评论成为当日讨论量第一，远超第二名（1026 分）。

触发点是路透社报道黄仁勋与一名被美方情报界指认为中国间谍的女性存在婚外情，另有第二条婚外情曝光。Democrat 参议员已就此致函展开调查，Reuters 同步报道另有第三方指控。更有意思的连锁反应是：量子位援引报道称马斯克已准备好聘请黄仁勋——从 GPU 供应方到潜在 AI 实验室，这条人事线的走向本身就是一种定价。

但真正值得 agent 开发者停下来的是这件事：就在同一天（11 月 12 日），Unemployment Labs 发布了一篇取证报告，用模型权重本身证明 DeepSeek-V4-Flash / V4-Pro、Kimi K3、MiniMax 与蚂蚁集团的六个模型（均 2026 年 4 月后发布）在训练时使用了受出口管制的 NVIDIA Blackwell 硬件——DeepSeek-V4-Flash 对应 B200/B300，V4-Pro 对应 GB200/GB300，且对 V4-Flash 与 Kimi K3 在物理 Blackwell 芯片上完成了确认；而这些公司更早的模型（DeepSeek-V3、Kimi K2）指纹一致地指向旧一代 Hopper。这不是泄露或内部人爆料，是可复现的数值取证。

把两件事放在一起看：Nvidia 换了 CEO，而"先进算力出口管制已经失效"第一次有了技术层面的公开证据。黄仁勋任内的护城河叙事是"AI 算力受制于我"，而这条证据直接侵蚀的是这个叙事的地基。财报上 Nvidia 仍会卖得很好，但"卡脖子"这件事的可信度已经变了——Kress 守门期间要面对的，是监管者拿着权重指纹来问"你们的出口管制到底有没有用"。

对 agent 开发者的直接影响：算力供给的不确定性会沿着价格和合规两条路径传导。如果后续有更多实证坐实中国前沿模型的 Blackwell 来源，管制措施只会更严——这意味着（a）开源权重模型的部署门槛会继续上升（这恰好解释了今天另一条主线：端侧、小模型、量化为什么同时升温）；（b）选模型时，"哪家在训练管制清单上"会成为一个新的架构约束变量，就像今天有人不得不考虑数据中心电力来源一样。

我的判断（主观）：这一天的关键词不是"八卦"或"权力更迭"，而是供应链叙事的可信度第一次被模型权重本身挑战。任何做 agent 基础设施的人，都该把"算力地缘政治"从宏观背景降级为具体的采购与合规变量来处理。

P0 · 架构范式GoogleHuggingFace决策模型

决策模型（Decision Model）从"小众 API 怪癖"升格为独立模型品类：Google 亲自下场，$0.10/M、150ms、最多 1000 问

11 月 11 日 Google 发布 Gemini Decisions API 与新模型 gemini-decision-1。它不是生成模型，而是打分模型：一次前向传播同时对最多 1000 个 yes/no、choice（2–255 选项）、score（有序评分）问题给出概率与置信度，不做逐 token 解码。支持 text / image / audio / video / PDF 原生多模态，单次输入上限 256K token。

关键数字：端到端 150–250ms（纯模型计算中位数 50–100ms），$0.10 / 1M 输入 token，输出 token 计费为零。在共享 benchmark 上比 Gemini 3.5 Flash-Lite（走 Interactions API）便宜近 5 倍。Google 内部 Gemini Notebook 已把它当实时路由层用，宣称延迟最多降低 40%。

这不是孤立事件。Hugging Face 在 11 月 10 日发了官方长文 《Decision Models in Hugging Face》，把 State + Questions + Allowed Answers → Decisions + Probabilities 定义成独立接口范式，并指出社区已从 TypeSafe 的 "Jev"（System One 模型）自然收敛到 "decision model" 这个中性术语；文中还给出 Transformers / llama.cpp 两条部署路径和训练方法。Simon Willison 当天记录："Google 加入 Jev 和 OpenAI 的决策模型行列"，三种问题类型完全一致，连 yes/no 的术语 "Noul" 都是同一个。

开源侧同步在补位：OpenJev（开放权重，84.0% 对 Jev 的 85.4%）、上海 AI Lab 的 Intern-Decision 0.8B/2B/4B（不生成自由文本）、Perplexity pplx-decider v1.2（Apache-2.0，Decision Index 174 分，厂商模型里最高）、Decido（Gemma 4 26B-A4B 的 8-bit GGUF LoRA，笔记本 CPU 可跑），Ollama 0.35 也已加入 Jev 风格的本地 decision API。

这意味着什么（我认为这是今天对 agent 架构影响最大的一条）：过去两年 agent 系统里，"判断"环节是被严重浪费的。我们让一个能生成几千 token 的模型去回答"这个工单该转哪个部门""这段代码有没有注入风险""这轮对话要不要升级给人工"——每次都是完整的自回归解码、完整的输出计费、完整的 JSON 解析失败风险。决策模型把这一层单独剥离出来：不写字，只给概率，150ms、$0.10/M、置信度可以拿来路由到 fallback 或人工复核。

对 agent 开发者的具体动作：（1）把 agent 里的分类/路由/评分环节全部盘一遍，凡是用大模型 + JSON prompt 实现的，换成 decision model 或本地小模型——这是最直接的降本点；（2）决策模型的概率输出比"模型说 A"更有用，你可以用它做阈值策略（>0.8 自动执行，0.3–0.8 转人工，<0.3 兜底），这正好补上 agent 最缺的一环——可判定的升级逻辑；（3）它把 "System One / System Two" 的架构分层落到了工程上：决策层便宜快、执行层贵而深，中间用概率阈值耦合。Google 自己的 Orchestrator（见下条）就是这套分层的一个具体实现。

一个值得警惕的点（主观）：决策模型在多跳推理上会明显退化——有基准测试显示用 ProofWriter 三千六百道多跳题测下来，决策模型和 LLM 分类器在需要链式推断时会一起崩。所以它不是"更小的 LLM"，是换了个问题子集。别拿它做推理。

P0 · 范式突破AWSAgent 写生产代码

AWS Emulator：200+ 个 AWS 服务的本地模拟器，100% 由自主 agent 编写，人类没写也没 review 過一行代码

11 月 11 日 AWS 发布 AWS Emulator——一个用 Rust 写的本地 AWS API 模拟器，覆盖 438 个 AWS API 模型 / 200+ 服务，以 CC0 许可开源在 github.com/aws/aws-emulator。你把 AWS CLI / SDK 的 endpoint 指到本机 127.0.0.1:9297 就能在无 AWS 账号的情况下开发和测试。支持 server mode、Docker、以及 Rust 测试的 embedded mode（每个测试一个隔离实例，无需 endpoint 证书）。

真正的新闻是它怎么来的。AWS 团队博客的原话是："我们的团队没有写过、也没有 review 过这里的任何代码。"起源是 Anthropic 早前展示 agent 能自主构建 C 编译器的结果。AWS 给了 agent 两样东西——spec（AWS API Models）和reference implementation（真实 AWS 云）——然后在周末让 Kiro 跑出了第一个 SQS 实现。

最终形态是三支 agent 团队的流水线：

  • 测试队：从公开 API Model 设计保真度测试，每个测试先在真实 AWS 上跑通再提交，目前数万条，持续增长；
  • 找茬队：重放保真度测试找分歧，先用"给 SQS 写个第一版"这类 issue 引导冷启动，再对失败测试按根因聚类提 issue；
  • 修复队：一个 issue 一个 agent，定位根因、改代码、然后过合并门禁——门禁里有独立的 agent 审编码规范、审安全、验保真度不回归，不过就退回返工。

官方说每天修复数千个 issue，数百个 agent 并发写同一个仓库。GitHub 上连"已修复"和"待修复"的 issue 目录都公开了。还有个细节很说明问题：早期版本 agent 自己写了个 Python 解释器来支持 AWS Lambda，后来被要求复用现有库——原话是"这在不需要涂色书的人看来或许显而易见"。

这意味着什么：这是"agent 写的代码进生产"第一次以规模化、可下载、CC0 的形态出现在世界上。它证明的不是"AI 能写代码"（那已经不算新闻），而是当 spec 足够形式化、reference implementation 足够完备时，agent 可以独立完成一个有真实用户、有真实 API 兼容要求的工程项目。AWS 有史以来第一次把整个 AWS API 面当作可执行 spec 来使用。

对 agent 开发者的具体动作：（1）AWS Emulator 是你做 agent 测试基础设施的最佳样板——你的 agent 需要一个"确定性、可离线、可反复重放"的环境，而不是每次调真云。（2）三支 agent 团队的分工（测 / 找 / 修）是可以直接抄的架构：写代码的 agent 和验收代码的 agent 必须分开，否则就是自己给自己打分。（3）今天你就可以用 agent 把你自己项目里那些"没有测试、每次跑都烧真钱"的外部依赖变成本地可回放的 fixture——这正是 agent 时代测试基础设施的形态。

一个诚实的保留（主观）：保真度分（fidelity score）由 AWS 自己定义和公布，且"用于构建和测试、不用于生产、不用于安全测试"——CC0 免责也很彻底。它证明了"agent 能造基础设施"，但没证明"agent 能造可信的生产系统"。

P0 · 模型发布Google动态编排

Gemini 4 Hydrogen 发布 + Orchestrator 上线：用"动态双向模型编排"替代静态模型路由

11 月 12 日 Google DeepMind 发布 Gemini 4 Hydrogen，定位"为可靠 agentic workflow 和日常任务而生"的快模型。定价在整个 100 万 token 上下文窗口内完全平价：$1.50 / 1M 输入，$7.50 / 1M 输出（对比 Artificial Analysis 的中位价 $2.00 / $10.00）。

但发布本身不是重点，重点是同日的 Google Antigravity 推出 Orchestrator 模型下拉选项。Google 官方博客里那段话值得完整引用，因为它是今天对 agent 工程最有指导意义的一段：

"业界常见做法是用一个静态『模型路由器』，从你的第一个 prompt 猜任务难度，然后把整个任务路由到够用的最便宜模型。可惜，随着 agent 变得长时间运行、在不同阶段需要不同复杂度时，这种做法开始失效——复杂度往往是在任务演进过程中才被发现的。"

Orchestrator 的做法是动态、双向的：Carbon（前沿推理）先以只读方式探索依赖、消除歧义、产出带明确重规划触发器的具体计划；然后 Hydrogen 接手写代码、改依赖、跑测试；一旦遇到阻力就把控制权交回 Carbon去检查状态、修复计划、恢复执行。实测数据：在 Terminal-Bench 4.1 上，Orchestrator 达到接近 Carbon 的任务成功率，同时平均少消耗 24% 配额、快 19%。

背景是 Google 上周刚发布 Gemini 4 Carbon 与 /swarm（多 worktree 并行 agent 团队），据其博客称"短短几天内已有数万次 swarm 被启动"。

这意味着什么："模型路由"正在从"入口处的一次性分类"变成"贯穿执行轨迹的持续调度"。这是 agent 架构的实质性变化——它意味着你的 agent 运行时需要一个真正的编排层，而不是一个开头调用 route() 的 if-else。而且注意它和上一条是同一个故事的两面：Gemini Decision 1 是决策层（要不要换模型、该由谁做），Orchestrator 是调度层（换给谁、什么时候换回来）。

对 agent 开发者的具体动作：（1）如果你今天用静态 router，别急着删——但要开始记录"每个阶段实际用的是什么模型"，因为没有这份数据你永远不知道静态路由在哪里失效。（2）"重规划触发器"是个可以直接抄的设计：让廉价模型在明确条件下（测试失败、依赖解析出错、需要改设计）把控制权交回强模型，而不是让强模型全程盯着。（3）24% 配额节省是量化的——对你的 agent 做同样的 A/B，这是能写进成本报告里的数字。

P0 · 生态标准Agent Skills标准之争

Agent Skills 已经吃下 GitHub 周榜：Anthropic、Google、Cloudflare、Chrome 官方全部下场

本周 GitHub Trending 周榜里，skills 类仓库成建制占位：anthropics/skills（193,693★）、mattpocock/skills（323,000★）、addyosmani/agent-skills（116,657★）、cloudflare/security-audit-skill（71,200★）、google/skills（24,062★）、vercel-labs/agent-browser（50,323★）、vercel-labs/agent-desktop（22,701★）、NVIDIA/auto-ontology（12,232★）。日榜里还有 GoogleChrome/modern-web-guidance-src（739 stars today）、openai/codex-security（643 stars today）、meta/astryx（1,830 stars today）。

这不是巧合。Anthropic 10 月 22 日把 Agent Skills 捐给 Agentic AI Foundation，官方说法是"自 2025 年 12 月发布标准以来，ChatGPT、Cursor、GitHub Copilot、VS Code 等 70 多个 agent 平台已经集成"。Google 随即开了 google/skills（Cloud IAM、GKE、AlloyDB、Agent Gateway 多 agent 安全等），Cloudflare 开了 security-audit-skill，Chrome / Edge / Firefox / MDN 联合维护 modern-web-guidance——后者解决的是一个很具体的问题：模型训练数据里全是 legacy 前端写法，导致 coding agent 倾向生成臃肿 JavaScript 而不用原生 web 平台能力。

Cloudflare 那个 skill 的结构值得看：六阶段结构化审计——侦察（架构、信任边界、输入面、覆盖账本）→ 覆盖驱动狩猎（分配隔离 hunter、记录检查、用覆盖 critic 找盲区）→ 候选验证（每个候选交给全新的 verifier 去尝试证伪）→ 结构化输出 → 独立记录验证 → 目标中立报告。这是 Cloudflare 漏洞发现 harness 的单仓库起点。

这意味着什么：Agent Skills 已经从"Claude Code 的一个功能"变成了跨厂商的能力打包与分发格式。Anthropic 捐给基金会这一步是关键——它把一个可能被做成"Claude 专属插件"的东西，变成了像 MCP 一样的中立层。而各家的跟进方式也很有意思：Cloudflare 给的是方法论 skill，Chrome 给的是知识 skill（浏览器兼容性数据），Google 给的是产品操作 skill。三类内容共用一个格式，这是标准真正成熟的标志。

对 agent 开发者的具体动作：（1）如果你在造 agent 工具链，skills 兼容性现在应该进你的 roadmap——npx skills add google/skills 就能装，格式是开放的，晚了就接不上了；（2）"每个候选交给一个全新的 verifier 去证伪"这个模式，可以直接用在你自己的 agent 输出审核上（生成者与验证者必须是不同实例，最好不同模型）；（3）skills 是分发专业知识的载体，而 MCP 是分发工具能力的载体——这两个协议是互补的，你的架构里两个都要有。

P1 · Agent 运行时自托管

Agent 运行时三件套：OpenBot 1.0（治理外壳）/ Pomerado（网站→MCP）/ AgentRun（自我进化 + 成本优化）

今天 GitHub 上同时冒出来三个不同方向但互补的 agent 运行时，值得并排看：

  • CopilotKit OpenBot 1.0（11.6k★，MIT）：每个 AI 同事拥有自己的一台电脑——浏览器、文件、工具；每个动作执行前先被决定、执行后被记录；支持接入任何 AG-UI agent，自托管、桌面端 App（Apple silicon / Windows）、K8s 部署、Web/iOS/Android/Slack/Teams。核心是"动作先审批再执行"这个模型——agent 要发邮件时先停下等你点头，你能随时接管。
  • Pomerado（YC F26，MIT）：把任意网站变成 MCP 集成，只需自然语言描述任务，不需要 HAR 文件或录制；生成的是确定性集成而非 computer use，所以比 computer use 更快更可靠；能穿透登录态与双因素认证；产物是标准 MCP stdio server，Claude Code / Codex / Cursor / VS Code / Gemini CLI 都能挂。代价是构建阶段需要 OpenAI API key（但你的 agent 可以跑任意模型）。
  • AgentRun：加在 Claude Code / Codex / OpenCode / pi 之上的开源层，提供自我改进、持久化执行、控制平面。它给的数字很具体：Greptile 3 月起按每次 review 收 $1，他们的 agent 上量后账单从 $180/月涨到 $6,451，于是自己训了个便宜模型做 reviewer，每次 review 18 美分，在 30 个没见过的 PR 上抓到真实 bug 的数量是 Greptile 的 1.6 倍。另一个案例：merchant 分类从 Opus 学会后交给便宜模型执行，$0.89 → $0.12。

对 agent 开发者的具体动作：这三个分别补 agent 栈的三个洞——OpenBot 补"治理与审批"，Pomerado 补"把没有 API 的世界接进来"，AgentRun 补"别再重复付学费"。其中 Pomerado 的思路最值得研究：它的定位是"确定性集成"而非"更聪明的 computer use"，这与今天的主线（决策模型、Orchestrator）完全一致——不要让模型在每一步都重新决定，而是把决策固化下来。如果你现在用 computer use 点网页，试试这条路的成本对比。

P1 · arXiv 前沿记忆治理工作流编译

arXiv 今日两簇信号：agent 记忆的"该不该记"，以及把 SOP 编译成无 planner 的工作流

今天 arXiv 上 cs.AI / cs.CL / cs.LG 共产出 93 篇相关论文，两个簇格外密集：

  • 记忆治理三连：《When Should Agents Remember? Falsification-Gated Self-Evolution》指出当前自我改进把 episode 里的教训直接写进记忆，导致"局部成功"被当成"可复用的安全知识"——论文提出用证伪门控来决定一次行为更新是否被允许进入持久状态；《Don't Just Trust Your Memory: Evidence-Linked Memory Reduces Memory-Induced Degradation》点破了一个反直觉现象：agent 有了记忆反而会变差（memory-induced degradation），因为教训只从轨迹推断、没有被独立验证，agent 会盲目执行一条错误教训；《Coding Agent Memory Post-Training II》则把"写什么、读什么、何时写何时读"当作 policy 来做 on-policy 蒸馏。
  • 《ReTrace: Distilling Tool-Using Agents into Planner-Free Workflows》——最实用的一篇。问题定义得很准：业务流程每次都跑同一个 SOP，LLM agent 每次都调 LLM 来选下一步，规模和延迟都吃不消。解法是把 SOP 和几次 agent 运行日志蒸馏成一个可复用的工作流，由代码而不是 LLM 来决定下一步走哪。这正好是 AgentRun 那个"18 美分一次 review"的学术版。
  • 另有 Continual-ARC（用终身流式任务测技能习得，而非一次性单任务）、ARE-bench（在真实研究者会话与工作区里测 agent 的研究能力，批评现有 benchmark 太"干净"）、EngineAgent（把端侧推理引擎的接入变成 agent 任务，因为转换/算子/硬件后端的跨层依赖太难人工处理）、Program-Aided Patchable Skill Evolution（skill 用程序而非自然语言表示以便可修补演化）。

对 agent 开发者的具体动作：这三条串起来就是一条完整的工程路线——ReTrace（把流程编译成确定性代码）→ 证伪门控（决定哪些经验有资格进记忆）→ Evidence-Linked（给每条记忆挂上证据链）。如果你正在做"agent 越用越聪明"的产品，这三篇几乎把你的 roadmap 写好了。更重要的元信号是：学术界和工业界在同一周独立收敛到同一个结论——agent 的下一阶段竞争力在"记忆与流程的状态管理"，不在"再调一次 prompt"。

P0 · 量化华为诺亚W4A4

华为开源 MACaQ：模型无关的 SOTA 量化，122B 参数模型 64 分钟量化完，只需 32.5GB 显存

MACaQ（Model-Agnostic Quantization）由华为诺亚方舟实验室开源，定位是超越纯文本的模型无关量化：

  • 速度：量化一个 122B 参数模型只需 64 分钟，设备内存占用 32.5GB；达到 MR-GPTQ 和 DuQuant++ 更好的 perplexity，或用 11× 更少的量化时间匹配它们在 Llama-3-8B 上的最好成绩。
  • 覆盖面：llama.cpp（2/3/4-bit GGUF）、vLLM（W4A4 或 weight-only）、Diffusers（图像/视频/音频生成模型 W4A4）、PyTorch（语音生成 W4A4）、以及 Ascend 后端。已给出 Qwen3-4B / Qwen3.8-27B / Qwen3-30B-A3B / Qwen3-Coder-30B-A3B / Qwen3.6-35B-A3B / Qwen3-Next-80B-A3B / OLMoE-1B-7B / FLUX.2-klein-4B / Wan2.2-TI2V-5B 等 recipe。
  • MACaQ-R：反向路线——直接 refine 已有的 GGUF 权重码，同时保持 llama.cpp 原生格式和 block scales 兼容，产出物用标准 llama.cpp 就能跑。

这意味着什么：量化这件事在过去两年已经从"个人玩家的 hack"变成了有正式论文 + 完整多后端工程栈的基础设施。真正的新意在"model-agnostic"和"W4A4 落到扩散/音频/语音生成"——过去量化基本只服务 LLM 文本，现在连视频扩散模型都能 W4A4。对做多模态 agent 的团队，这是实打实的部署成本下降。

对 agent 开发者的具体动作：端侧 agent 或私有化部署，优先试 MACaQ-R——它不需要重跑量化流程（几分钟而不是一小时），直接 refine 你已有的 GGUF，且保持 llama.cpp 兼容，迁移成本几乎为零。昇腾用户可以直接走 Ascend 后端这条路。

P0 · 端侧 AgentTether AI Research0.8B

BotPsy 0.8B：sub-billion 参数的端侧 agentic 模型，在工具调用榜单上打赢所有 ≤1.2B 的对手

Tether AI Research 发布 BotPsy，一个 0.8B 参数、基于 Qwen3.5-0.8B 的 function calling / agentic 模型，专为端侧个人助理设计，覆盖 web 搜索与研究、旅行与生活、电商与金融、商务与客服、设备与车辆控制、文件与文档、日历、邮件与消息等域。官方称其在 tool-use 与 agentic 基准上超过所有测试过的 ≤1.2B 模型，包括 2.5 倍大的 Qwen3.5-2B-Think（仅在 Claw-Eval 上被后者反超）。已提供 safetensors 与 bf16 / Q8 / Q4 的 GGUF。

这意味着什么：agent 的每一步工具选择正在下沉到可以在手机上跑。这是"本地 agent"从概念变成可交付产品的信号——因为端侧 agent 的成本结构里，决策层（调哪个工具、填哪个参数）才是调用频次最高的部分，而这正是 0.8B 能干的事。

对 agent 开发者的具体动作：如果你在做端侧/隐私优先的 agent，试试这个分层——0.8B 负责工具选择与参数填充，2B–4B 负责需要推理的子任务，7B+ 负责最终输出。BotPsy 本身就是这个架构的第一层。注意它暴露的 GGUF（Q8/Q4）意味着配合 MACaQ 这类工具可以进一步压。

P0 · 结构化上下文IBM GranitePrompt Injection

LLMON：给 3B / 8B 小模型装上"LLM 原生标记语言"，间接 prompt injection 攻击成功率降到近乎为零

IBM Granite 团队发布 LLMON（LLM Object Notation，读作 "lemon"）——一种显式把结构与语义传给模型的标记语言，并同时放出两个实验预览模型：granite-4.1-3b-LLMON-preview 与 granite-4.1-8b-LLMON-preview。

出发点是一个很具体的观察：LLM 上下文里塞满了各种异质组件——system prompt、历史对话、作用于检索文档的指令、工具返回、约束输出的要求、推理链——但它们要么是隐式的，要么被塞进 JSON 这种"不是为 LLM 消化而设计"的格式。这正是小模型脆弱、易意外失败的原因，也是 prompt injection 的可利用面。

LLMON 的做法：用有意义的标签包裹语义连贯的组件，标签本身用保留的特殊 token 分隔；嵌套结构对因果 LLM 无歧义；每个指令有唯一 ID，可以从上下文任意位置指向，并与它该作用的数据载荷绑定——类似编程语言里函数调用传参的方式。官方声称：因为指令/数据显式分离，藏在用户数据里的间接 prompt injection 基本会被忽略，部分 benchmark 上攻击成功率降到接近零，而通用能力相对 Granite 4.1 Instruct 基本保持。配套还有把现有 JSON 无损转成 LLMON 的转换器，以及原生支持 LLMON 的 Mellea（自动把 LLM 调用 LLMON 化）。

这意味着什么（这条被我低估了，看完想把它排到更前面）：安全圈正在从"靠模型自觉识别注入"转向"从上下文格式上让注入在结构上不成立"。ID → 数据绑定这个机制，本质是把 prompt injection 从"语义攻击"降维成"格式不匹配"——模型没有理由把一段被显式标注为 data 的内容当成 instruction。

对 agent 开发者的具体动作：如果你在做 agent 且处理外部内容（RAG 文档、网页、用户上传、工具返回），你今天最大的安全杠杆可能不是换模型，而是换上下文格式。哪怕你不训模型，也可以先把"指令 / 数据 / 工具输出 / 输出约束"用显式标签 + ID 绑定的方式组织好——先在 prompt 层面手搓一个简化版 LLMON 试试，攻击成功率可能立刻下降一个量级。

P1 · 极限端侧1-bit

smolmaxxing：1GB 内存的 iPad Air 2013 和小米电视盒子上跑 16B MoE，1-bit 内核 24–26 tok/s

一个把"极限端侧"做成可复现工程的仓库，全部数字都是在自己设备上实测的：

  • 小米电视盒子 S（3 代）：Amlogic S7D，4× Cortex-A55，1.9GB RAM（约 1GB 可用），Android 14 无 root → 日常模型 Qwen3.5-2B @ 7.7 tok/s；1-bit 的 Bonsai-1.7B @ 24–26 tok/s；最大模型 Ling-mini-2.0（16B）@ 5.1 tok/s。
  • iPad Air (2013)：Apple A7 双核，1GB RAM（约 700MB 可用），iOS 12.5.7 越狱 → Ling-mini-2.0 (16B) @ 2.6–4.5 tok/s。
  • 关键技巧：只把部分模型留在内存，其余从 flash 按需流式读取，因此 8B 和 16B 的 MoE 模型能在约 1GB RAM 上跑起来；1-bit 内核只需基础 NEON 指令。

对 agent 开发者的具体动作：这条的意义不在"电视盒子能跑 16B"这个炫技数字，而在于flash 流式加载 + 极低位宽这两件事可以叠加在任何"内存远小于模型"的设备上——路由器、树莓派、老旧工控机。如果你在做边缘 agent，这套技术路线值得完整读一遍 README 的方案文档（作者说明还会加手机、SBC、路由器）。

P1 · 效率快讯语音 / 音频 / 图像

三个小体量快讯：29M 流式语音识别、74M 流式音频 codec、10 秒 4K 生图

  • Earlybird（arXiv 2611.14421）：29M 参数的预测式流式语音识别器，4-bit 下仅 16.8MB。它从"音频在随机点被切断（包括单词中间）"中学习，因此在说话人还没说完时就能开始输出词——官方说法是传统流式识别要晚 90–400ms 才出词，而语音 agent 里每一毫秒都决定了 agent 能不能提前开始搜索或规划回复。
  • Liquid AI LiquidCodec：74M 参数的流式音频 codec，把 24kHz 语音编码成离散 token 再解码回音频，被 LFM3-Audio-2B 与 LFM3-Omni-2B 使用（自研音频编码器 + codec 整体替换了 LFM2.5 的方案）。
  • MiniMax H3-Image 开源（11 月 10 日放权重）：10 秒生成 4096×4096（16MP）图像，速度约为市面主流的 5 倍；支持文生图、图像参考与图像编辑。量子位标题里的"一张两毛"是更直观的成本表达。

对 agent 开发者的具体动作：Earlybird 是这三条里最值得立刻关注的——如果你的 agent 有语音入口，"延迟"就是产品体验本身，而 90–400ms 的提前量足以改变对话节奏设计（可以在用户说到一半时就开始检索）。29M / 16.8MB 意味着它可以常驻在设备上，不需要联网。

💭 深度思考

洞察一 · 本日主线

今天所有 P0 条目都在讲同一件事：agent 的架构正在从"调模型"变成"分层调度"

把今天看似无关的几件事摆在一起：

  • Gemini Decision 1 —— 一个不写字、只给概率的决策层；
  • Orchestrator —— 一个在执行轨迹中持续做双向模型调度的编排层；
  • ReTrace / AgentRun —— 把决策从运行时固化到代码或记忆里；
  • Pomerado —— 把 agent 的动作从"每次重新推理"变成"确定性集成"；
  • LLMON —— 把上下文里的指令与数据在格式层就分开；
  • AWS Emulator —— 把 agent 的运行环境变成可离线重放的确定性系统；
  • 证伪门控 / Evidence-Linked Memory —— 把 agent 的经验写入变成有证据准入的流程。

共同点是：把决策从"生成式的一次性调用"里拿出来，搬到有明确接口、可验证、可缓存、可审计的位置。这跟 2024–2025 年"agent = LLM + 工具调用 + prompt 编排"的范式是路线级的区别。上一代 agent 的每一次运行都在重新推理；这一代 agent 的目标是尽可能少推理——判断交给便宜的决策模型甚至代码，执行才交给强模型，路径交给编译过的工作流，经验交给有准入门禁的记忆。

给 agent 开发者的可执行建议（按投入产出比排序）：

  1. 先把所有"判断型"调用从主模型里剥出来。你现在的 agent 里有多少次 LLM 调用其实只是在回答"是/否"、"选哪个"、"打几分"？把它们换成 decision model 或本地小模型，通常能拿到 5 倍以上的成本下降和 10 倍以上的延迟下降。这是本周投入产出比最高的一步，今天就能做。
  2. 给 agent 加一个"流程编译"层。读 ReTrace：同一个 SOP 跑第二次时，让代码决定下一步，让 LLM 只处理异常分支。哪怕你只做一条主流程，收益就已经很大。
  3. 把静态路由改成带"交还触发器"的动态路由。抄 Orchestrator 的模式：廉价模型负责执行，明确的失败条件（测试挂了、依赖解析不了、设计要改）触发把控制权交回强模型。这比一开始就上最贵的模型更省，也比纯静态路由更准。
  4. 给 agent 的记忆加一道准入门禁 + 证据链。参考今天两篇记忆论文：一条从轨迹里学到的教训，在被写进持久记忆之前，应该有一个独立实例尝试证伪它；每条记忆应当能指回它的来源 episode。
  5. 把上下文格式当成安全工程来做。不管你训不训模型，先用显式标签 + ID 绑定把"指令 / 数据 / 工具输出 / 输出约束"分开。这是投入最小、对抗性收益最大的一步。

我的判断（主观）：2027 年的 agent 框架竞争，胜负手不在"接了多少模型"或"支持多少 provider"，而在"你的架构里有多少决策被固化下来了"。模型能力是租来的，决策固化能力是自己的。

洞察二 · 被低估的方向

被市场低估的不是模型，是"护栏"本身：spec、测试与合并门禁正在成为 agent 时代的核心竞争力

AWS Emulator 的故事里，最关键的三个角色不是写代码的 agent，而是：AWS API Models（spec）、真实 AWS 云（reference implementation）、合并门禁（agent 组成的评审 + 校验流水线）。作者的原话是"我们之所以能做到，是因为我们设的护栏给了 agent 独立工作的空间，也给了我们相信它们不会越界的信任"。

同一天，Cloudflare 的 security-audit-skill 把"给每个候选漏洞配一个全新的 verifier 去尝试证伪"写进流程；AWS Emulator 的门禁里有 agent 审规范、审安全、验保真度不回归；Apple 的 Foundation Models framework 上 HN；agent 记忆的两篇论文在讲"什么有资格被写进记忆"。方向完全一致：可信度不来自产出者，而来自一个独立的、可重复执行的验证机制。

被低估的结论："护栏"过去被当成产品功能（安全审核 UI、权限弹窗、评测分数），实际上它是工程基础设施，而且很可能是 agent 时代最稀缺、也最难被后来者复制的东西。因为模型能力可以买、可以换模型、可以换 provider，但"如何把一个 agent 产出的东西验证到可以下生产"是组织性的、流程性的、试错成本极高的。

具体建议：如果你的团队正在做 agent 产品，现在就值得单独建一个"验证层"小组/子系统，职责是：(1) 用形式化 spec（不只是自然语言需求）描述 agent 的产出契约；(2) 建可离线、可重放的环境（AWS Emulator 是最好的模板）；(3) 保证生成者与验证者用不同实例、最好不同模型；(4) 所有"agent 的产出进入生产"都必须过一道机器可执行的 gate。这套东西建起来很难，但一旦建好，它就是你相对其他 agent 团队最真实的护城河——因为它是复利资产，每次运行都在变强。

一个反向的提醒（主观）：同一天 Anthropic 玻璃翼计划"挖了 37966 条只修了 217 条"的数字，说明"挖"的能力已经远超"补"的能力。整个行业当前最稀缺的不是发现问题的能力，而是验证与修复的能力。这个缺口会持续至少到 2027 年。
