今日头条：Claude Haiku 5.5（10/7 发布）——$0.10/$0.50 / 1M 上下文 / 自适应推理 / 90% 降价，第一次让「Haiku 跑主循环」变成默认选项

P0 昨日发布 范式 Anthropic 小模型 Anthropic · Claude Haiku 5.5 · adaptive reasoning · 1M ctx · 官方公告 · Simon Willison 实测 · Artificial Analysis · OpenRouter · GitHub Copilot 上线 · 价格报道

昨天发生了什么：Anthropic 10/7 放出 Claude Haiku 5.5——这是自 4.5 之后第一次重大升级，也是 2026 年最重要的「小模型」发布。四个硬数字：

  • $0.10 / 1M input、$0.50 / 1M output——比 Haiku 4.5 降价 ~90%，和 OpenAI GPT-6 Luna 完全对齐（同样 $0.10/$0.50）；
  • 1M token 上下文 / 128K max output——长上下文从 Sonnet 下放到 Haiku；
  • adaptive reasoning + effort setting（Xhigh / Max / Default）——Anthropic 第一次把 effort 暴露成可调参数，同一个模型可以跑「快答」也可以跑「深推理」；
  • 5 个模型变体（不同 effort / 默认 fallback 策略）——价格从 $0.12/任务 到 $0.50/任务 连续可调（Artificial Analysis 数据）。

「Haiku 不再是 'cheap worker'，而是 'tier-collapsed' 主循环」

把 Haiku 5.5 和过去 12 个月的小模型横着看，叙事已经完全不同：

  • Haiku 4.5（2025）：定位「subagent」——做摘要、分类、prefilter，SWE-bench Verified 73.3% 是其主要卖点；
  • GPT-6 Luna（9/22）：定位「每天重复任务」——$0.10/$0.50，Artificial Analysis index 37；
  • Mistral Small 3 / Gemma 4 26B-A4B：开源阵营的 4B-26B 主力；
  • Haiku 5.5（今天）：在 同等 $0.10/$0.50 价位 上拿到 Artificial Analysis index 43（Max effort）、Terminal-Bench 2.1 拿到 39.2%（vs 上一代 0%）——「Haiku 跑主循环」从「省钱选项」变成「默认选项」。

关键的范式转移：Artificial Analysis 把 Haiku 5.5（Max）列入「leading models」第一档——和 Sonnet 5.5 / GPT-6 Sol / Mistral Large 4 同档，只是更便宜。过去「Haiku tier = 弱 50%」的等式被打破，tier 之间的能力差距被 effort setting 收窄。

⚠️ Simon Willison 的隐藏成本警告

Simon 在 10/7 实测 里发现：Haiku 5.5 处理同样的长 prompt 用 token 量是 Haiku 4.5 的 ~1.25x。换句话说：

  • API 价格（$0.10/$0.50）确实降了，但单 prompt 消耗的 token 增加了——同一任务的真实账单成本需要重新评估；
  • 「降价 90%」是按 list price 算的，如果你的 prompt 平均超过 100K tokens，实际降价幅度是 ~70-80%；
  • effort 设置为 Xhigh 的变体在长 prompt 上不一定便宜——Artificial Analysis 给出的最低价 $0.12/任务 是在 Default effort 下。
为什么重要（主编观点）：① agent 主循环的经济学再次坍塌——Haiku 5.5 Max 在 SWE-bench / Terminal-Bench / browser use 三个 agent benchmark 上都进入了「leading tier」，agent 的默认模型从「Sonnet / Sol」变成「Haiku 5.5 Max effort」，单任务成本再降 3-5x；② 「effort setting」成为新的可调旋钮——Anthropic 把推理深度暴露成 API 参数，意味着 agent 框架可以在不同决策点动态调整 effort（prefilter 用 Xhigh、verify 用 Default、creative 用 Max），这比「多模型路由」灵活 10x；③ GitHub Copilot 同步上线——Haiku 5.5 GA 进 Copilot（10/7），agent 工具链的默认 tier 被官方推着向 Haiku 倾斜；④ 10/27 配合 Mistral Le Chonk 开源，「小模型做主循环」的工程现实被三件事同时验证——闭源 Haiku 5.5 + 闭源 GPT-6 Luna + 开源 Le Chonk。
对你意味着什么：① 如果你的 agent 还在用 Sonnet / Sol 跑全量主循环——今天就改 prompt，把「summarize / classify / route / extract」这类「窄任务」换到 Haiku 5.5 Default effort，成本立刻降 70-80%；② 如果你在做 multi-tier agent——effort setting 比「多模型路由」更优雅：同一个 Haiku 5.5 模型 ID，根据任务复杂度切换 Xhigh / Default / Max，省掉了 90% 的 model selection 代码；③ 如果你的 agent 在做 long-context 工作流——1M context + 128K output 让 「整本代码仓库 + 长文档一次塞进 prompt」第一次在小模型 tier 成为可能，但记得用 Default effort，Xhigh 在 1M context 上账单会爆。

GPT-6 + Intelligent UI 全员上线（10/7）—— ChatGPT 第一次变成「能输出真 UI」的模型，agent 应用层被重写

P0 昨日 范式 UI 生成 OpenAI · GPT-6 · Intelligent UI · 官方公告 · GPT-6 十月 system card · MacRumors · Safety 部署 · ExplainX 解读

发生了什么：OpenAI 10/7 把 GPT-6 全量推送到 ChatGPT 全员（Plus / Pro / Business / Enterprise 今天，Free / Go 明天），同时上线 Intelligent UI——GPT-6 可以在答案里直接生成可交互 UI（图表、按钮、表单、小型计算器、可点击地图），而不是返回 markdown 文字或图片。

几个关键细节：

  • GPT-6 Sol = 中等档（$2/$10）；GPT-6 Luna = 经济档（$0.10/$0.50）；10/7 的 ChatGPT 后端是 「GPT-6 October」系统卡版本；
  • Codex 和 ChatGPT Work 用户暂时还在用旧版本——OpenAI 在 system card 里特意区分了「October」vs「之前的版本」；
  • Intelligent UI 的实现路径：模型在 thinking 过程中可以提前返回 UI 组件（「native component library + compiler」），用户看到的是 progressive UI 渲染，不再是「等模型输出完整 markdown 再渲染」。
为什么重要：① ChatGPT Free 也能用 GPT-6——这是 OpenAI 第一次把 frontier 模型完全 free tier 化，用户增长曲线会被再拉一波，Claude Sonnet 5.5 在 consumer 端的「自然流量优势」会被追平；② Intelligent UI 是 application layer 的范式转移——过去 12 个月所有人都在做「模型 + markdown」，现在变成「模型 + UI 组件」，MCP 2026-07-28 spec 里说的「agent 内 UI 渲染」第一次被 OpenAI 实现；③ 对开发者：「在 ChatGPT 里跑的内部 SaaS」第一次有了标准路径——你可以让 GPT-6 调你的 API、生成你的 UI、跑你的工作流，这是新的 application layer。
对你意味着什么：① 如果你的产品是 SaaS——重新评估「ChatGPT 内应用」机会，MCP server + Intelligent UI 配合能让你的产品以「组件」形式出现在 ChatGPT 里；② 如果你在做 agent framework——今天开始支持 Intelligent UI 输出格式，3-6 个月内会成为 baseline；③ 如果你的 agent 还在「return markdown 给用户」——改用 component-based 输出，否则体验会明显落后。

OpenAI Decisions API 公测（10/6）——给 agent 一个「10x 速度的分类器」专门做 routing 和下一步选择

P0 10/6 infra 路由 OpenAI · Decisions API · GPT-6 Luna · 官方公告 · OpenRouter 列表 · HF 教程 · Vercel 对比 Jev

发生了什么：OpenAI 10/6 放出 Decisions API public beta——一个专门做分类 / 路由 / 下一步选择的 API，背后是 GPT-6 Luna。关键卖点：

  • 比 GPT-6 Luna through Responses API 快 ~10x（官方数字）；
  • 输入：text + image；输出：有限决策（classification / route / 有限选项里选一个）；
  • 不是聊天 API——OpenRouter 明确说「chat completions SDK 不能用」，这是一个独立的决策层；
  • 竞品：TypeSafe AI 的 Jev（text-only，rubric scoring + yes/no probabilities）。
为什么重要：① agent 的 routing layer 第一次有「专用 API」——过去 agent 框架（LangGraph / CrewAI / AutoGen）都用 LLM call 做 routing，每个 routing 决策都是一个完整 chat completion，浪费 token + 慢 10x；② Decisions API 把 routing 层从「LLM 模拟」变成「专用服务」——意味着 agent 的 routing 决策路径有了 SLA，可以做缓存、可以做熔断、可以独立计费；③ 这是 OpenAI 在 agent infra 层的第二次布局（第一次是 Agent SDK + Computer Use）——和 Anthropic 的 MCP server、LangChain 的 tool calling 一起，agent runtime 三大组件正在分层：reasoning model + decision router + tool protocol。
对你意味着什么：① 如果你的 agent 有 routing / classification / 状态机分支——今天就试 Decisions API，把 routing 从 main LLM call 里拆出来，预计主循环延迟降 30-50%；② 如果你的 multi-agent 编排用了 LangGraph / AutoGen——用 Decisions API 替换 supervisor node，省 80% token（routing 不需要完整 chat completion）；③ 如果你的产品形态是「用户问题 → 路由到正确 agent」——Decisions API 是工业级解决方案，比自建 classifier 更稳定。

arXiv 2610.07753「From Evidence to Action: How Tool-Using Agents Fail」（10/6）——首次系统化失败模式分类

P1 10/6 论文 失败模式 arXiv 2610.07753 · arXiv

Lin Hongzhan 等人 10/6 提交到 arXiv 的论文，第一次把 tool-using agent 的失败模式做了系统化分类：

  • 不是「agent 没找到证据」——是「找到了但用错了」（evidence-action misalignment）；
  • 不是「工具调用错了」——是「工具调用对了但参数错」（partial correctness）；
  • 不是「agent loop 没收敛」——是「收敛了但判断错了」（premature stopping）。
为什么重要：过去 12 个月 agent 失败分析都是个案研究，这是第一个把「失败模式」分类学化的论文。对 agent 调试工具（LangSmith / Helicone / Arize）意味着 未来 6 个月会有「failure taxonomy」标注工具——你跑 agent 时会自动标出「这次失败是 evidence-action misalignment」。

Claude Haiku 5.5：5 个 effort 变体连续可调——agent 主循环第一次有「成本 × 智能」完整滑块

P0 10/7 小模型 范式 Anthropic · Claude Haiku 5.5 · effort setting · 官方 · Artificial Analysis 5 变体对比 · Experiential Labs

Haiku 5.5 不是一个模型，是 5 个变体的连续谱。Artificial Analysis 把它们排成一张「成本-智能」表：

变体Intelligence Index每任务成本典型用途
Haiku 5.5 Xhigh~37$0.12高频 subagent / 分类 / prefilter
Haiku 5.5 Default~39$0.20通用主循环 / summarization
Haiku 5.5 High~41$0.35多步 reasoning
Haiku 5.5 Max~43$0.50coding agent / tool use
Haiku 5.5 (Default Fallback)39$0.20production 默认

关键设计：同一个 API endpoint，通过 effort 参数控制推理深度。这是 Anthropic 在「模型分层」这件事上给出的最优雅答案——「分层」不是「不同模型」，是「同一个模型的不同 effort」。

为什么重要：① 过去 18 个月 agent 框架用「多模型路由」来平衡成本和能力（Haiku → Sonnet → Opus 阶梯），但每次切换都是「不同的 prompt 模板 + 不同的 context window 行为 + 不同的 tool use 格式」——工程复杂度很高；② Haiku 5.5 的 effort setting 把这些复杂度收进了同一个 API——你只需要写一份 prompt，agent 自己根据任务复杂度选 effort，省掉了 90% 的 routing 代码；③ Artificial Analysis 数据：Max effort 的 intelligence index 43 已经接近 Sonnet 5.5 的 46——Haiku Max 跑主循环在 SWE-bench / Terminal-Bench / browser use 上能拿 Sonnet 90% 的能力，成本只有 1/10。
对你意味着什么：① 如果你的 agent framework 还在硬编码 model tier——今天改用 Haiku 5.5 + dynamic effort，agent 代码量立刻减半；② 如果你的 agent 跑长 prompt——Simon Willison 的实测：长 prompt 用 token 量 1.25x，Xhigh effort 在 1M context 上账单可能爆，Default effort + 拆分 prompt 是更稳的姿势；③ 如果你做 agent 评估——在 eval harness 里加上 effort dimension，未来 6 个月这是关键可调变量。

💭 深度思考：2026 Q4 的「两层 agent 架构」已经成形——effort setting + Decisions API + tool protocol 三件套

把过去 24 小时的事件横着看，一个清晰的范式正在成形：

  1. 10/7 Claude Haiku 5.5——同一个模型 ID + effort 参数，成本 × 智能连续可调；
  2. 10/6 OpenAI Decisions API——agent routing 专用 API，把 routing 从 main LLM call 拆出来；
  3. 10/7 GPT-6 + Intelligent UI——agent 输出从 markdown 升级到 UI 组件，application layer 重写；
  4. 10/6 arXiv 失败模式分类——agent 调试有了标准化 failure taxonomy。

横着看的结论：2026 Q4 的 agent runtime 正在从「一个模型 + 一个 loop」变成「分层专用服务的拼装」：

  • Reasoning 层：Haiku 5.5 / GPT-6 Sol / Mistral Large 4（用 effort setting 调深度）
  • Routing 层：OpenAI Decisions API / 自建 classifier（专用路由 API，比 LLM 模拟快 10x）
  • Tool 层：MCP 2026-07-28 spec / A2A（标准化协议，进入 Linux Foundation 治理）
  • Output 层：Intelligent UI / MCP server UI rendering（agent 输出真 UI 组件）
  • Debug 层：failure taxonomy（标准化失败模式标注）

主编建议（主观）：

  1. 如果你的 agent 还是「单 LLM call + prompt 拼接」——今天开始做分层重构：routing 拆出去用 Decisions API、main loop 用 Haiku 5.5 effort setting、tool 用 MCP、output 用 Intelligent UI，这四件事每做一件，agent 性能 +30%；
  2. 如果你的 agent framework 还在支持多模型路由——把 routing 代码删掉，改用单模型 + effort setting——代码量减半，性能持平或更好；
  3. 如果你的 agent 在做 long-context summarization / prefilter——立刻切到 Haiku 5.5 Default effort——价格降 70-80%，质量持平；
  4. 如果你的产品在 ChatGPT 里出现——今天就设计 Intelligent UI 集成路径，3-6 个月内会成为 baseline；
  5. 如果你的 agent 在做 routing decision——今天就试 Decisions API——主循环延迟降 30-50%，省 80% token。

被低估的方向：「effort setting 是 agent 时代的 POSIX」——过去 18 个月 agent 框架的「模型分层」是一个工程问题（你要写 routing 逻辑、要处理 prompt 模板差异、要管理 token budget），effort setting 把这个工程问题变成了「模型 API 的内置能力」。未来 12 个月 所有 frontier 模型都会暴露 effort / reasoning depth 参数——OpenAI 已经有 o-series 的 reasoning_effort，Anthropic 的 effort setting 是这个方向的「工业标准化」。在它之上构建的 agent framework 会比硬编码多模型路由的 framework 优雅 10x。
