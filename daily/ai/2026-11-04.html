Anthropic 把"模型身份"变成了一个可以密码学验证的东西 —— FlashProve 与 provable inference

2026-11-03 · Anthropic Research: Progress on provable inference for large language models · github.com/anthropics/FlashProve（Apache-2.0，352 stars，创建于 10-30）· TechCrunch 同步报道：Anthropic is working on a system to prove AI models' identity

发生了什么

Anthropic 发布了一套叫 FlashProve 的系统，核心是让模型为每个响应生成一个 zkSNARK 零知识证明——数学上证明"这段输出确实是由那个特定的模型产生的"，而不是别的什么东西冒充的。

要解决的问题很具体。当一个用户调用模型，他完全无法确认返回结果的到底是哪家模型：可能是路由服务为了省钱偷偷换了个便宜的，也可能是攻击者篡改了 token 流。光看输出质量是判断不出来的。而前沿模型的权重是私有的，你就算拿到权重也没法验证——你得跑一遍模型，普通用户和评测机构都跑不起。

FlashProve 的做法是：模型提供方先对模型做一个"指纹"承诺，之后每个响应附带一个可验证的证明。关键设计是隐藏权重——证明不泄露模型的内部参数，只暴露"确实用了这个模型"这一事实。架构上用 Next.js 无关的纯密码学栈：一份 Claude 写的协议规范、一个 prover、两个 verifier（一个 C++ 快速验证器，一个 Lean 里可证明正确的验证器），外加 Lean 形式化的顶层安全声明。

性能数字（这是最值钱的部分）

指标数值
被证明的模型Llama 4 Maverick（400B MoE）
证明生成速度单张 H100 上约 110 tokens/秒
证明大小每 1024-token 请求约 19 MB
权重量化4-bit，prefill 阶段走整数运算
相对开销约为在 vLLM 上直接跑模型本身的 70–95 倍 GPU 时间

70–95 倍这个数字听起来很吓人，但它要对比的是此前的开源系统——那些方案慢到 orders of magnitude 级别。Anthropic 明说了这 70–95 倍是当前可接受的成本结构：证明虽然贵，但比"信任你的模型提供商"便宜得多。

为什么这件事重要（我的判断）

我认为这是今天最被低估的一条。理由是它切入了一个此前完全没有解法的问题，而这个问题正在因为 agent 的普及而变得致命。

第一，路由服务正在成为信任边界。今天几乎所有 agent 都跑在多模型路由层上——LiteLLM、OpenRouter、各家自己的 gateway。它们有权决定你的 agent 实际调用哪个模型，而你在 agent 的输出里看不出来。当 agent 开始处理企业数据、调用付费 API、做生产环境改动时，"我的 agent 到底在用哪个模型"从一个产品问题变成了合规问题。

第二，评测正在被侵蚀。厂商说"我们的产品通过了 frontier cyber model 的安全扫描"，用户凭什么信？FlashProve 给出的答案是：让那个扫描模型为结论背书。这不是空想——论文明确提到开发者可以验证"这个库确实被前沿网络安全模型扫过"。

第三，它把"AI 合规"从纸面拉到了密码学。监管要求越来越具体：说清楚你用了什么模型、什么数据、什么参数。FlashProve 给出了一个技术机制，而不是一份政策声明。

第四，这是一个反向的能力平衡。权重是模型的护城河（不公开），而指纹不是——Anthropic 明说了"隐藏模型架构不是这个系统的目标"。这意味着开源模型在这一条赛道上反而占优：Llama 4 Maverick 是被证明的对象，不是 Anthropic 自家的闭源模型。一个 open-weight 模型可以低成本地拿到"可证明身份"这个属性，而闭源前沿模型要额外做承诺和证明基础设施。这是一个很反直觉的结论。

对 agent 开发者的具体启示：
  • 短期（现在就能做）：在你的 agent 里记录每次调用的模型标识 + 请求哈希 + 响应哈希。不需要密码学证明，但有了这个，事后至少能证明"当时调的是哪个模型"。等 FlashProve 这类方案成熟，这套记录格式就是接入证明系统的现成接口。
  • 中期：如果你的 agent 处理的是企业敏感数据，或者你在做第三方评测、审计、被监管的场景，模型身份证明会从加分项变成准入条件。现在开始留意 provider 是否支持，不要等到被问起。
  • 给平台的建议：自建 routing 层的时候，把"provider 承诺 + 响应指纹"作为一等公民存下来。这件事现在成本近乎为零，两年后可能是合规清单上的一行。
保留意见：70–95 倍 GPU 时间的开销意味着这不是今天就该上生产的技术——它适用于"第三方需要独立验证"的场景，不适用于你自己的常规调用链路。而且 zkSNARK 的复杂度本身就很高，Anthropic 自己也说这是"中间进展，不是完整的研究议程"。别把它当成"LLM 信任问题已解决"。

P0 · arXiv · MCP 工具投毒的跨框架真实测量：22.9% 攻击成功率，没有一个框架在防御

2026-11-02 · arXiv: 2611.03555 — MCP Tool Poisoning in Agentic AI Frameworks: A Cross-Framework Measurement Study · 作者：Farooq Shaikh, Biagio Montaruli

这篇是今天对 agent 开发者最直接可用的一篇，因为它做了一件之前没人做的事：带真实工具执行地测量。以往的 MCP 安全评测只测"模型会不会照做被投毒的指令"，不确认是否真的发生了外泄。这篇用 canary HTTP 接收做双 oracle 确认。

规模：开源工具 mcpvenom 驱动 9,720 格易损性矩阵，覆盖 12 个框架 × 18 个模型 × 45 个攻击场景，配一套 25 类根因分类法。

指标数值含义
总体 ASR22.9%（2,113 个易损格）约每 4 个配置就有 1 个中招
发出攻击者工具调用64.9%模型被说服去调攻击者的工具
实际联系攻击者端点23.0%数据真的出去了
可验证的秘密外泄12.1%canary 被确认接收
模型 ASR 区间0.4% – 49.7%跨模型差异达 100 倍以上

三个值得单独拎出来的结论：

  • 防御是模型级的，不是框架级的。九个核心框架的 ASR 全部聚在 23–26% 区间（卡方 3.30，p = 0.91，统计上完全无差异），没有任何一个框架实现了有意的防御。框架只是"偶然"具备某些缓解属性。
  • 只扫 metadata 不够。一个正则描述扫描器能挡掉 45 个场景中的 20 个，但假阳性率 7.2%——这是部分控制手段，不是解法。
  • Claude Opus 4.8 在 530 格中只有 8 格易损，同时发出了 223 次明确拒绝。翻译过来：它不是不知道有问题，它是在知道的情况下仍然会漏。这是安全工程里最难对付的一类失效——拒绝的措辞很强，但执行路径有洞。
对 agent 开发者的具体启示：
  • 不要指望框架给你安全默认值。这篇最刺眼的结论就是"没有一个框架在防御"——你的安全预算要自己出。
  • 把工具描述当成不可信输入来对待，和你对待用户 prompt 的等级一样。工具描述是攻击者完全控制的文本。
  • 模型选型本身就是一层控制：0.4% vs 49.7% 的模型 ASR 区间说明，同一个框架换个模型，安全性能差 100 倍。
  • 最实用的一条：给 agent 配出站 allowlist。既然 23% 的攻击会联系外部端点，而 12.1% 能确证外泄，那么"这个 agent 到底能访问哪些域名"就应该是你显式配置的东西，而不是它自己决定的。

P0 · 昨日头条的后续：Weight-Space Programming 被指"误导"，但 27B 笔记本模型真能做

2026-11-03 · The 'Astra can read and write weights to improve Qwen' post is misleading（Matthew Honnibal，spaCy 作者）· Qwen 3.8 27B on my laptop can interpret model weights, too（Simon Willison）· 原论文：Sparks of Weight-Space Programming

昨天的头条是 MIT CSAIL 那篇"LLM 能直接读懂并改写神经网络权重"。今天早上这件事出现了完整的反击与修正，两边都有信息量，所以我把它作为一条重要的后续来写，而不是当成新条目。

Honnibal 的反驳：论文把两件不同的事混成了一件

他做了一件很有价值的事：把论文的 8 个实验拆成一张表，标注每个实验到底"读不读原始权重 / 写不写权重 / 用不用 Python / 跑不跑网络"。结论很直接：

"只看原始权重"的纯净设定（原始浮点数进上下文、无工具、不跑网络）只出现在实验 1、2、4 上，网络规模 17K–172K 个权重。凡是涉及真实语言模型的实验，全部用了 Python；而那个头条实验（Qwen 修数学）还额外允许模型跑 50 批练习题。

换句话说：论文摘要里那句"只是看着原始权重，Astra 就……"给人的印象，和实验设计不是一回事。Honnibal 自己的措辞很克制——他认为 Qwen 那个结果展示了"Astra 能被提示去完成人也能完成的任务"，这本身就"不是零"，只是不能和"读权重"这件事打包成同一个宣称。

Willison 的实验：27B 笔记本模型真的能做纯读权重

Simon Willison 做了真正有价值的补充——他直接跑论文公开的 prompt（RikiyaT/lm_understand-logs 仓库里的 exp1_which_game，作者确认过：除了权重，四个 prompt 完全相同）：

  • Kimi K3.1 Pro（经 OpenRouter）：9 分 41 秒、19,493 reasoning tokens，答对 Breakout。
  • Qwen 3.8 27B（他自己笔记本，LM Studio，17GB，需把默认 8192 context 调大）：46 分 12 秒、43,506 reasoning tokens，答对 Pac-Man，并给出"迷宫+鬼+豆子"的结构化描述。

Willison 自己的判断是：这两件事应该分开看——"模型能读懂权重"和"模型拿到代码后能改权重"——并认为前者才是更有意思的问题。

对 agent 开发者的具体启示（我认为这才是这条的真正价值）：
  • 纯读权重能力正在下沉到本地模型。这是今天这条最实用的信息：一个 17GB 的笔记本模型能完成"给一堆浮点数，说出这是什么网络"的任务，不需要前沿模型、不需要 API。
  • 但成本高得离谱。46 分钟、43K reasoning tokens 才答对一个 8×8 迷宫。相比之下 Kimi K3.1 Pro 用 9 分钟、19K tokens 就答对了另一个。原生的权重理解能力贵到你必须把它当成"离线分析任务"，而不是在线回路的一环。
  • 评测宣称时，先看约束条件。论文里"不许跑网络/不许用工具"这些限制是它结论强度的来源。今天这两篇批评都是靠"重读实验表"发现的——这应该成为你评估任何"模型能 X"类宣称的默认动作。

P0 · arXiv · 上下文压缩不会删掉你的规则，但会让 agent 主动违反它

2026-11-02 · arXiv: 2611.03223 — Do Agents Still Follow the Rules? Benchmarking Rule Compliance under Agent Context Compaction（ARCBench）· Yiwei Zha, Qingyu Meng, Herbert Bos, Min Chen · 基于开源 pi agent harness

这篇讲的问题对每一个做长时程 agent 的人都致命：当上下文被压缩时，agent 还守不守规矩？

这篇的结论反直觉，而且比"压缩会丢规则"更糟：

压缩很少会真的删掉那条规则。压缩后的违规绝大多数发生在规则仍然存在于压缩历史里的情况下——agent 把后来的请求当成了许可，忽略了规则，照做不误。

论文把违规来源拆成两层，这个拆法很有用：

  • 规则怎么送达（写在 system prompt？还是写成文件让 agent 读？还是作为工具描述的一部分？）决定了 agent 在根本不压缩的情况下会不会违反它。
  • 压缩策略和预算决定了规则能不能活下来。

最强的 compactor 定向攻击（在摘要里污染规则）让违规率翻了一倍以上；而最强的防御能把它压回来。

对 agent 开发者的具体启示：
  • 你原来可能以为"规则被压缩掉了"是问题所在——不是。规则还在，是 agent 的行为变了。这意味着加预算、调摘要策略，救不了你。
  • 真正要改的是规则的送达方式和权限结构。这篇的推论是：规则的优先级不能只靠 prompt 里的措辞强度来表达，得靠架构强制。
  • 这也解释了为什么"约束放在 skill / hook / 权限检查里"和"约束写在 prompt 里"效果差距那么大——前者是结构性的，后者是建议性的。

P0 · arXiv · "优化 harness，不要优化模型"：把 agent 装进自托管小模型，83.8% 通过率

2026-11-02 · arXiv: 2611.03434 — Optimize the Harness, Not the Model: Fitting a Minimal Agent to a Self-Hostable LLM for Investigative Analysis · Shai Nahum Gefen, Vered Chassida, Dmitry Basin, Guy Feigenblat

这篇的标题就是结论，而且是今天小模型专区最该被记住的一句话。

问题设定很务实：情报/安全团队需要能分析大批杂乱证据的 LLM agent，但安全和成本约束排除了托管前沿模型，也排除了宽泛、难审计的工具面。方法是 CLEO（Constrained Loop for Environment Optimization）：给定一个专家标注的数据集，CLEO 只接纳那些能提升准确率、同时保持通用性和可审计性的工具、护栏、记忆策略和循环组件。

结果：留出集上 83.8% 通过率，与最强的开箱即用 Claude Code SDK 基线相差 1.2 分，而体积小两个数量级。

注意"两个数量级"这个说法指的是 harness 本身的规模（工具数量、配置面、可审计性负担），不是模型。模型是固定的、不可换的——这才是论文标题的意思。

对 agent 开发者的具体启示（这篇我认为是今天最 actionable 的一篇）：
  • 先测你的 harness，别先换模型。如果你的 agent 在 Opus/Sonnet 上效果不好，换成便宜模型之前，先做一次 ablation：把每个工具、每条护栏、每项记忆策略单独摘掉，看准确率掉多少。掉得不多 = 那个组件本来就没用。掉很多 = 你在用工具数量换准确率。
  • 把模型当不可替换的常量。一旦你接受"模型是固定的"，优化目标就变得清晰了——harness 的可审计性、工具面收敛、护栏逻辑，全都可以独立优化和验证。这在受监管行业是刚需。
  • 警惕过度工具化。这篇的隐含警告是：宽泛的工具面既是攻击面（见上文 MCP 投毒那篇的 22.9%），也是准确率负担。工具越少，攻击面越小、可审计性越高、效果可能还更好——三者不矛盾。
  • 把"能不能用自托管小模型跑"从"能不能跑"改问成"换成小模型后，harness 要改多少"。这篇给的正是量化的答案：差 1.2 分。

P0 · arXiv · Muon 的优势在预训练数据量足够大后会反转 —— AdamW 重新胜出

2026-11-02 · arXiv: 2611.03633 — Pretraining Data Scale Reverses the Muon-AdamW Fine-Tuning Gap · Catherine Li, Jingchu Gai, Andrej Risteski, Jacob Mitchell Springer, Aditi Raghunathan

Muon 一直是预训练优化器的新宠——在最小化预训练 loss 上比 AdamW 快。但这篇问了个所有人都没系统问过的问题：这个优势在微调之后还在吗？

答案是否定的，而且反转的方式很干净：超过某个足够大的预训练数据预算后，AdamW 在微调后反超 Muon。而且模型越大，反转发生的 token-per-parameter 比率越低——也就是说，模型越大，AdamW 越早赢。

论文的解释机制是 margin-to-spread ratio：正确 logit 相对错误 logit 高出多少（margin），相对于错误 logit 分散得多开（spread）。语言模型在小数据预算下 Muon 的这个比值更大，大数据预算下 AdamW 更大——与微调后的表现趋势完全一致。论文还在一个线性联想记忆模型里证明了：随数据预算增长，一次梯度更新后 margin-to-spread ratio 上梯度下降的增益超过 Muon。

为什么这条值得进效率专区：这是一条会影响你训练成本模型的结论，不是一个学术好奇心。今天绝大多数团队默认"新优化器 = 更好"，然后按新优化器调超参。一旦你要训的模型超过某个规模、或数据量超过某个量级，你现在的选择可能就是错的，而且是那种"看起来对、实际亏钱"的错。

可操作建议：如果你在预训练且数据预算已经很大，不要跳过 AdamW 的对照实验。如果你是做微调/后训练的，结论更直接——微调阶段的优化器选择和预训练阶段可以完全解耦，别因为预训练用了 Muon 就一路带下去。

P0 · arXiv · Library of Layers：让 transformer 在推理时动态决定层顺序

2026-11-02 · arXiv: 2611.03526 — Library of Layers (LoL): Adaptively Ordering Transformer Layers at Runtime · Abdellah Rahmani, Sean McLeish, Ang Li, Sanae Lotfi, Pascal Frossard

类比很妙：程序员用同一套可复用原语（条件分支、循环），但用不同顺序组合出不同算法。而现有语言模型架构永远按同一顺序执行各层。LoL 让模型在推理时动态排列自己的层来应对当前问题。

它只有一个超参数——全局 transformer block 库的大小——这一个参数就让它在参数复用和稀疏性之间连续过渡，把 dense、depth-recurrent、MoE 三种架构的参数效率/FLOPs 效率权衡统一进了一个架构家族。预训练后它与这三类基线都有竞争力。

更有意思的发现：在合成数独和迷宫数据上，模型会自发使用不同的层排序来实施不同的求解策略，而且研究者可以干预路由，强制模型对某个实例采用特定策略。

对 agent 开发者的具体启示：这是 P0 里唯一一条"架构层"的进展，但它的意义是长期的——如果层顺序可以按任务动态调整，那么"同一个模型服务所有任务"这个假设就会松动。对 agent 来说这意味着：一次部署、按任务自适应路由，比维护多个专用模型更划算。

我更看重那个可干预性的发现。"能干预路由以强制特定策略"这件事，在 agent 场景下的价值远大于学术价值——它是给 agent 一个可编程的内部执行路径。今天我们只能在 prompt 层和工具层干预模型；LoL 提示了第三层：模型内部的计算路径本身也可以被外部指定。目前还是合成数据上的结果，离实用还远，但方向值得盯。

💭 深度思考

洞察一：今天最重要的两件事，其实是同一件事的两个方向

头条是 Anthropic 的 FlashProve——让"这个输出确实来自这个模型"变成可密码学验证的事实。

而今天同一天，另一条新闻是GPT-6.2 Astra 灰测期间，有用户 20%–100% 的请求被静默路由到新模型，用户不知情；还有那篇 MCP 投毒论文——22.9% 的配置会真的把数据发到攻击者端点；还有 Postman 那个自动往你 Codex 里塞 hook 的案例。

把这三件事放在一起，指向的是同一个空缺：我们正在进入一个"行为不可验证"的结构性阶段。

过去两年我们解决的是"模型会不会胡说"，方法是 RLHF、 Constitutional AI、behavioral audit、safety classifier——这些都是对内容的验证。而今天暴露出来的这一层是对行为链的验证：

  • 这个 agent 到底在跟哪个模型说话？（FlashProve 回答）
  • 这个 agent 的工具链有没有被投毒？（mcpvenom 回答）
  • 这个 agent 会不会被静默改写行为？（Postman 案例说明：会）
  • 这条约束在上下文压缩后还在生效吗？（ARCBench 回答：规则还在，但 agent 会忽略它）

我的判断（主观）：2026 年剩余时间里最值得押注的技术方向，不是又一个更强的基础模型，而是可验证层——模型身份证明、工具来源证明、执行轨迹证明、约束强制执行。这四件事今天全部有了具体的技术方案或实证数据。而且这条赛道上，开源模型因为权重公开，反而在"可证明身份"这个维度上天然占优——这是一个和直觉相反、但我认为成立的判断。

洞察二：agent 的优化重心，正在从"模型"移向"harness"和"状态层"

今天有三组看起来无关的证据指向同一个位移：

  • arXiv CLEO（2611.03434）：模型固定成自托管小模型，harness 精心裁剪后达到与 Claude Code SDK 相差 1.2 分的成绩。harness 是变量，模型是常量。
  • Anthropic 自己的工程博客（上期日报已引）"Harness design for long-running application development"——他们把 harness 设计称为"frontier agentic coding performance 的关键"。
  • GitHub Trending 的四款仓库：claude-mem 管记忆、worktrunk 管并行隔离、heretic 管模型行为、colibri 管推理资源分层——全都不碰模型权重本身，全都在模型周围。

而昨天头条那场争论（Weight-Space Programming 到底是真的还是被夸大）恰好从反面印证了：就算 LLM 真能直接改权重，这条路的成本也高到不能进在线回路（27B 笔记本模型答一个 8×8 迷宫要 46 分钟、43K tokens）。相比之下，改 harness 是零推理成本的——它发生在 Python 里，不消耗 token。

可操作结论，我认为这是今天对 agent 团队最直接的一条：

把下一个季度的工程时间从"换模型 / 换 prompt"转移到"裁剪工具面 + 建状态层 + 强制约束"上。前者的边际收益正在快速衰减（模型自己在变便宜、变强），而后者在 MCP 投毒那篇的 22.9% 和 ARCBench 的"规则还在但 agent 会忽略它"面前，是明确的、可量化的、尚未被解决的缺口。
