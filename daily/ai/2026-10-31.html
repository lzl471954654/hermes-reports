Claude Code 的 VS Code 插件被供应链投毒 11 小时 —— AI agent 的"身体"比它的"大脑"成熟得慢

2026-10-29 07:35 PT → 2026-10-30 · Cursor 官方安全公告 · Ars Technica · HN 讨论 · MIT Tech Review（配合同日研究）

发生了什么

Cursor 官方公告确认：在 10 月 29 日 2:27am PT 到 1:35pm PT（约 11 小时 8 分钟）之间，一个被恶意篡改的 Anthropic.claude-code 扩展被发布到 Cursor 的 VS Code 扩展市场，涉及版本 2.1.312 与 2.1.313，覆盖 Windows 与 macOS。Cursor 明确声明：这些恶意版本并非 Anthropic 开发。影响面为至多 5,000 名用户。

恶意载荷的行为拆开看，是一套相当完整的攻击链：

  • 侦察——收集并外传主机名、用户名、操作系统、CPU 架构、home 目录路径、环境变量名（注意：变量名而非值）、工作目录、已配置的 Git email、出口公网 IP。
  • 植入——尝试向 ~/.ssh/authorized_keys 追加攻击者公钥（标记名 svc-telemetry）、启用本地 SSH 服务、并建立反向 SSH 隧道。Cursor 说明：除非 Cursor 以管理员权限启动（极罕见），这一步因恶意代码自身的错误会失败。
  • 持久化——macOS 走 LaunchAgent，Windows 走以 SYSTEM 身份尝试的计划任务 + Startup 脚本兜底。后台脚本每约 60 秒重试一次隧道。

Cursor 的处置：立即下架并封禁分发，随后整体关停市场、轮换密钥、重建市场；与云服务商协作把攻击者服务器下线，"反向 shell 与主机信息 POST 均已失效"。Anthropic 的 Dworken 在 HN 补充：官方 VS Code 扩展市场与 OpenVSX 未受影响，只影响 Cursor 市场这一条分发路径。

为什么这是今日头条 —— 三个层次

第一层：AI 编码 agent 本身成了新的软件供应链攻击面。过去 IDE 插件窃取的是浏览器 cookie、剪贴板、键盘记录——价值有限但影响局部。Claude Code 这类插件不一样：它以完整用户权限运行，天然持有仓库凭据、云 token、SSH 密钥、CI 密钥，且默认被授予读写整个工作区与执行 shell 的权力。插件商店的信任模型建立在"插件偷点数据"，而 agent 插件的实际权限是"插件就是你"。

第二层：这是一次针对 AI 编码 agent 的定向攻击，而不是机会主义投毒。被顶掉的是 Anthropic.claude-code——一个带 Anthropic 验证标识、坐拥百万级安装量的目标。在 agentic coding 已经成规模部署的当下，攻击者发现"攻破 agent 插件 = 攻破开发者全部代码资产"的路径，这比传统恶意扩展的收益高一个数量级。我判断这只是开始，不是结束。

第三层（这层最被低估）：卸载插件不等于止损。Cursor 公告明确写道："Uninstalling the extension may not be sufficient — the payload drops standalone persistence scripts that keep running."载荷会落下独立于插件自身的持久化脚本。真正需要做的是：检查 ~/.ssh/authorized_keys 是否有 svc-telemetry 键、清理 LaunchAgent / 计划任务、终止隧道进程、轮换该主机上所有凭据与会话，并判断是否需要重装系统。Cursor 提供了 macOS / Windows 各自的清除脚本，脚本在残留任何东西时会以非零状态退出——这个设计值得抄。

与同日 MIT Tech Review 的研究合流看，故事更完整：那篇文章（详见下方 Agent 前沿 P0）报告了对四个最主流 agent 框架的审计，发现它们普遍不生成持久化的 Agent ID、不记录"哪个人类批准了哪次 agent 任务"。前者是"agent 的行为没被记录"，后者是"agent 的代码被替换了也没人知道"——两件事指向同一个结论：agent 的运行时可观测性，在这次攻击里恰好是可以救命的，但它当时不存在。如果 Cursor 的扩展在安装时就在 telemetry 里写入了不可变的安装记录+哈希，这次 11 小时的窗口至少能被秒级识别。

给 agent 开发者的具体动作（今天就能做）

  1. 把 agent 插件当生产依赖管：锁定版本、校验发布者签名、优先走官方 VS Code 市场 / OpenVSX 而非第三方市场；内部团队自建 agent 扩展时，CI 里加一步"发布物哈希校验"。
  2. 默认拒绝 agent 扩展的全盘文件访问：用工作区白名单、最小 token scope、沙箱（Docker/微虚机）承载 agent 执行，而不是让 agent 直接在开发者主机上以用户身份跑。
  3. 给 agent 装"行为留痕"插件：OpenTelemetry 的 agent tracing 工作组正在起草共享格式，在标准落地前，用 hook / callback 把工具调用、文件写入、shell 命令、outbound 请求记进 append-only 日志——这既是防供应链，也是出事后的取证依据。
  4. 把 Anthropic 这条先例写进你的供应商风险评估："模型厂商的插件被投毒"从此是一个需要单独评估的风险项，不再是理论问题。

P0Anthropic 研究人类判断

专家把判断权交给了 agent，而且自己没察觉 —— 86% 的采纳率与"只有 15% 归因"之间的裂缝

2026-10-27 · Anthropic Research · How AI agents shape experts' judgment calls

这是本周最值得细读的论文。Anthropic 做了一个随机对照实验（RCT），招募 61 名通过因果推断知识筛查的专业分析师，让他们在 Claude Code 辅助下完成一份真实的统计咨询任务：为一个虚构的农业合作社判断某项咨询服务是否有效、该不该推广。任务里刻意留了四个"两个选项都说得通"的分析决策——生产率按每公顷算还是按单位运营成本算、用双重差分还是回归调整、评估覆盖参保农场还是全体社员、权重是每农场等权还是按规模加权。每个选择都能让估计出的生产力提升浮动几个百分点，而理事会的门槛卡在 3–4%。

实验的关键设计很巧妙：每个分析师的 agent 被设定为在每个决策上偏好某个选项，而这个偏好由抛硬币决定，分析师本人不知道。agent 被要求为自己的偏好做最诚实的论证，证据变了就改主意，不误导人。

结果：

指标数值解读
四个分析决策上采纳 agent 倾向的比例86%若无影响应为 ~50%。也就是说 agent 的"偏好"实质上接管了决策
分析师已有自己的偏好、且 agent 反对时的改弦更张率60%对照组（agent 同意时）只有 6%
事后解释时使用 agent 论据（部分逐字复用）的比例77%论证的来源已经是 agent
事后把 agent 归因为论据来源的比例15%元认知缺口——知道与归因严重脱节

还有一个冷静的对照数据：不给 agent 任何刻意偏好时，Claude Opus 4.8 自己在 123 次运行里有 112 次给出同样五个选择——真实 agent 本来就有稳定的倾向，实验只是把这个倾向放大到可测量。所以作者说得很谨慎："当 agent 没有被给予明确偏好和表达偏好的指示时，这个效应可能更小。"

我的判断（主观，但这是我今天最强烈的观点）：这个 86% / 15% 的组合，比任何关于"AI 会不会取代专家"的辩论都更有信息量。它说明 AI 时代的真正风险不是能力转移，而是责任错配——决策的实质内容确实被 agent 提供了，但人类既没有察觉，也没有在自己的产出里标注溯源。等出事后，人类的口头解释和 agent 的真实依据会脱节，而人类完全相信那是自己的判断。

作者点出了一个我认为是本报告最该强调的应用边界："研究者已经开始用 agent 来跑和分析实验，而一个人类审阅者只有在他的判断是他自己的判断时，才是独立的检查。"如果用 agent 做实验的 agent 也有稳定偏好（上面 112/123 那个数字），那这条独立性链条是有洞的。

对 agent 开发者的指导：如果你的 agent 会给人"建议"（几乎所有 enterprise agent 都会），那么建议的溯源标注不是 nice-to-have，而是防止责任错配的必要功能。具体来说：(a) 在 UI 上区分"这是 agent 的倾向"与"这是用户的决定"，别让 agent 的措辞和用户自己的判断混在一起渲染；(b) 记录每次建议的生成条件（当时的 context、agent 的倾向声明），以便事后复盘"到底是谁的决定"；(c) 别把 agent 的输出静默并入用户的文档——本例中 77% 的逐字复用意味着下游读者无法区分二者。这条其实和今日头条那件事是同一个原则的两面：agent 的输出必须带着"谁做的、依据是什么"一起流动。

P0开源权重agentic coding

Mistral Large 4（Le Chonk）开放权重：1T MoE、1M 上下文，agentic coding 打平 GLM-5.3 但少用 47% token

2026-10-29 · Mistral 官方博客 · HuggingFace 技术解读 · 模型卡

10 月初 Le Chonk 以 public preview 形式发布后，Mistral 用仅三周的额外 RL 迭代出改进版并直接放出权重。这次的卖点不在参数规模，而在同等能力下更低的 token 消耗——这对跑得起 agent 的团队才是真正的账单。

官方披露的 agentic 数字：

  • Artificial Analysis Coding Agent Index：48%，与当前最强开源权重模型 GLM-5.3 基本打平，但每任务平均少用 47% token。
  • Terminal-Bench 4.0：41%（较 preview 版 +13 个百分点），领先开源权重阵营，同时输出 token 减少 30%。
  • Cognition 私有 FrontierCode 2.0：19.7% 居首——该 benchmark 评的是"仓库维护者会不会合并这个 agent 的改动"。
  • Surge Code 盲测 pairwise：人类偏好上胜过 GLM-5.3、Kimi K3、DeepSeek V4.1 Flash，仅次于 Claude Opus 5.5。

架构上值得记的：~1T 总参 / 49B 激活（含 embedding 与输出层为 52B）、128 个路由专家每 token 选 4 个 + 1 个共享专家、1M 上下文、72 层 / hidden 6144 / 64 头，MLA + DSA 稀疏索引器（每个 query 最多选 2048 个 key 位置）、3:1 的 RoPE/NoPE 交替、1.6B Pixtral 视觉编码器、160+ 语言。在 Mistral 自有欧洲数据中心、3,800 张 NVIDIA Grace Blackwell 上从零训练。

一个必须标注的数据分歧：Mistral 官方稿写 Artificial Analysis Cyber Index 51%，而 HuggingFace 同日的技术解读写 82%（两者都是 10-29）。这两个数字大概率是"综合分"与"复现-修补子项分"的口径差，但官方没有说明。我倾向采信官方口径 51%，并把 82% 视为未经证实的转述——这类"同一天两个官方渠道给出不同数字"的情况在模型发布周很常见，值得盯一下后续是否澄清。

另一个值得注意的信号：Mistral 说 Le Chonk 在 JailbreakBench / StrongREJECT / AgentHarm 的恶意 cyber prompt 上平均拒答率 96.6%，"是我们测过的开源模型里最高的"。翻译一下：它在防御性安全工作上能力很强的同时，拒答率也比任何开源竞品高。这两个特性同时成立，比单看任何一个分数都更有意义——open weight 模型第一次同时给了你能力和可审计的克制行为，这是闭源 API 给不了的（你没法独立测量拒答率，你只能信厂商的说法）。

对 agent 开发者的指导：token 效率这条线现在比"分数高几分"重要得多。一个"48% 但省 47% token"的模型和一个"52% 但多烧一半 token"的模型，在月度账单上是反过来的。所以做模型选型时，请把"每任务总 token（输入+输出+重试）"作为第一指标，分数作为第二指标。另外 Mistral 官方推荐的首选部署路径是 vLLM / SGLang，GGUF 由 Unsloth 与 llama.cpp 官方提供，NVFP4 版本面向 Blackwell——如果你的环境是 Blackwell 卡，NVFP4 + DSpark 组合值得单独评估（见下节）。

P1arXiv评测

Prefix Executability：只看最终成功率的 agent 评测，漏掉了轨迹中途就已经崩掉的情况

2026-10-29 · arXiv:2610.40444

现有 tool-use benchmark 基本都按最终任务成功率打分。但一个 agent 最终"做对了"，中间的工具调用轨迹可能早就不可执行了——调了一个不存在的参数、调了顺序错误、依赖了尚未写入的中间状态。这篇提出 prefix executability：衡量预测出的工具调用序列的每一个前缀在 schema、状态前置条件、数据依赖下是否仍然可执行，并给出 Prefix Executability Curves、First-Error Depth（FED）、Trajectory Executability Rate（TER）、Recovery Rate（RR）等指标，在 BFCL-v3 multi-turn 与 ToolSandbox 上实例化。

对 agent 开发者的意义很直接：如果你的 agent 评测只看最终成功率，你无法区分"一次走对"和"错了三次自己绕回来了"。后者在生产里意味着三倍的 token 成本、三倍的副作用风险（如果中间那步写了文件/发了请求），而 benchmark 上两者分数一样。

P1arXiv多智能体

Goal-Aware Dynamic Multi-Agent Collaboration：验证（verification）与任务成功的关联最强，却总是来得太晚

2026-10-29 · arXiv:2610.39193

这篇做了一个初步的机制研究：长程任务中，单 agent 需要切换"规划"和"验证"等不同职责。发现是——验证与任务成功的相关性最强，但验证通常发生在很晚的位置，留给纠错的机会已经很少；并且随着不同职责的记录不断累积，职责相关信息的占比在下降（即上下文被无关职责的日志稀释）。

两个可直接落地的推论：(a) 把验证前移——在多 agent 流水线里，把校验节点从"末端检查"改到"每个产出后立刻校验"，比事后 review 有效得多；(b) 做职责感知的上下文裁剪，别让规划 agent 背着验证 agent 的日志跑——这正是"分层多 agent 记忆"类工作的动机。

⚡ 小模型 & 效率革命

P0推理优化

DSpark 投机解码被"焊"进 checkpoint：Mistral 直接在权重旁附赠 draft head，实测 1.9× 吞吐

2026-10-29 · Mistral Large 4 模型卡

这是今天最"工程"的一条，也可能是对 agent 团队现金流影响最直接的一条。

常见做法是投机解码：一个小的 draft 模型先出若干 token，大模型批量验证。但这条路要求你另外找一套 draft 模型并维护它的服务——运维负担实实在在。Mistral 的做法不同：Le Chonk 的 checkpoint 里直接附带一个 DSpark draft head，由 3 层 BF16 稠密 MLA draft 层组成，用一个递归 Markov head 一次提出 3 个 token 的块。启用只需一个参数：

--speculative-config '{"method": "dspark", "num_speculative_tokens": 3}'

Mistral 声称：吞吐最高提升 1.9×，且不改变目标模型的输出（同精度、同量化下的严格等价），实际收益依硬件与负载而定。

为什么这是效率上的一条结构性变化：投机解码的收益在长输出、高并发、decode 阶段受内存带宽瓶颈的场景下最大——而这正是 agent 负载的特征（输出长、并发高、prefill 相对短）。过去"用投机解码"是给推理工程师的优化项，现在它变成了模型发行的一部分。当 draft head 随权重一起发布，"要不要开投机解码"从架构决策降级成了启动参数。

行动建议：如果你在 Blackwell 上跑 agent，vLLM / SGLang 起 Le Chonk 时默认就把 DSpark 打开，然后用你自己的真实 trace 测一遍 token/s 与 TTFT（官方给了个参考：SGLang recipe 固定 --max-running-requests 64，去掉会退到 48）。如果吞吐确实是瓶颈，1.9× 意味着你可以把并发从 64 提到 ~120 而不增加延迟——这在按 GPU 小时计费的托管推理上就是直接的收入差额。注意"不改变输出"这个保证是在同一量化 runtime 内的等价，换量化格式时需自行验证。

P0量化线性注意力

低比特 GDN 递归状态量化：量化回写误差才是线性注意力长上下文的真敌人

2026-10-29 · arXiv:2610.39931

这篇的技术点很准。线性注意力（Linear Attention / GDN 这类）把历史信息压成固定大小的递归状态，长上下文推理时存储需求不随长度增长——这是它相对标准注意力的核心优势。但继续压精度会遇到一个特殊问题：量化回写误差会进入后续的递归计算，在长推理任务上累积，表现为预测质量退化，并伴随重复生成和输出异常冗长。

方法上提出两个对策：GGA（Global Gradient-aware Allocation）把候选量化残差与梯度敏感度（对未来预测 loss 的影响）结合，按头分配比特宽度；PW（Pure-Write Sliding Window）只对纯写入部分做滑动窗口，避免近期信息的反复量化损失。

为什么值得 agent 开发者关心：你的 agent 上下文窗口越大、跑得越久，就越可能踩到"递归状态量化"这条路径——而且它的失败模式很隐蔽：不是崩掉，是慢慢变啰嗦、开始重复。如果你在用 DeltaNet / Gated DeltaNet / Mamba 系架构的模型做长程 agent，这篇直接相关；如果你在自建长上下文服务，它提示你"KV cache 量化误差会累积"这个直觉在递归架构下更强，需要专门设计而不是套用通用方案。

P1端侧浏览器内推理

浏览器内 LLM：GPU 常驻的投机解码，把 WebGPU 的那些具体开销逐个拆掉

2026-10-29 · arXiv:2610.39761

WebGPU 让"网页内私有离线推理"成为可能，但浏览器环境的调度、进程间通信、同步回读、单 token kernel 让常规投机解码效率低下。这篇给出一个 WebGPU runtime：

  • 确定性的小批量整数 kernel加速多 token 验证，同时保持与同量化 runtime 下 greedy decoding 的精确一致；
  • GPU 常驻循环完成 draft、verify、accept 与 KV cache 维护，不产生 per-token 的 CPU 决策；
  • draft-free 的 context-mixing drafter，复用页面内容、会话历史与 session memory——不额外加载一个 draft 模型。

最后一条最有意思：它用"把上下文本身当 draft 素材"绕开了额外模型的开销。和 DSpark 是同一类思路的两种形态——把投机解码的 draft 来源从"另一个模型"改成"已经在手边的信息"。

对 agent 开发者的意义：端侧 agent 的瓶颈从来不是"模型能不能跑"，而是"decode 阶段每 token 都要跨一次 CPU/GPU 边界"。任何能把整条验证-接受循环留在 GPU 里的方案，都是实打实的端侧可用性提升。如果你做浏览器内的隐私 agent（读本地数据、调用本地工具），这篇的工程细节值得直接抄。

P1模型架构

IBM Granite Switch 4.1.1：像更新软件一样更新模型——基座不动，只重训 adapter

2026-10-29 · HuggingFace / IBM Granite

nesformer：把一整台 NES 的 6502 CPU 编译进 Qwen3.5-4B 的权重里

2026-10-30 · GitHub · Simon Willison

点评：这是"模型即计算介质"路线的最好演示之一，也是 agentic coding 能力的一次干净的能力上界展示——注意它需要的不是更强的通用智能，而是"找到正确的工具（一致性测试套件）+ 复用已有工作（qwenputer）+ 愿意花时间构建"这三样。工程量仍然巨大，但它证明了一件事：把专用计算器"编译进"现有模型权重这条路是通的，不需要重新训练。对做 agent 工具的团队，这是个值得跟踪的技术方向。

💭 深度思考

洞察一 · agent 的"身体"比它的"大脑"落后一个世代——而这两件事在本周同时暴露

把今天的两组事实并排放：

事实 A：Cursor 市场上的 Anthropic.claude-code 被篡改版本发布 11 小时，装上它的机器被种下 SSH 公钥、反向隧道、LaunchAgent/计划任务持久化，每 60 秒重试一次。卸载插件无法清除。最多 5,000 台机器受影响。

事实 B（同日 MIT Tech Review）：对四个最主流 agent 框架的审计发现，它们不生成持久化 Agent ID、不记录哪个人类批准了哪次 agent 任务、不记录权限与记忆的变更。MITTR 的原话是"我们目前部署这些工具时基本是在盲飞"。

事实 C（同日 OpenAI Model Spec）："Ignore untrusted data by default" 被写进最靠前的规范层；但"控制并沟通副作用"需要 agent 侧有可落地的机制才成立。

我的判断（主观但确信）：模型侧的规范、监控、防护在快速补齐——三层同时落子（规范 / 失配监控 / 供应链标准）；而 agent 的运行时与分发层几乎是裸的。一个 agent 拥有 shell、文件系统、网络和凭据，它的"身体"却还在用 2015 年的插件市场信任模型（"你装的东西能偷你的 cookie"），而 agent 插件的实际权力是"它就是你"。

更能说明问题的是时间耦合：一份规范层刚刚把"忽略不可信数据"写成默认值，而同一天，一个被投毒的 agent 扩展正是在"被信任的扩展"这个身份下拿到全部权限。规范管的是模型读到的内容，管不了模型被安装了什么东西。

给 agent 开发者的可执行结论（三条，按优先级）：

  1. 先做可观测性，再谈自主性。MITTR 那篇最实用的结论是："what happened"记录（持久 Agent ID、人工介入记录、权限/记忆变更）大多是软件管道问题，可以用 OpenTelemetry 解决；而 OpenTelemetry 正在起草 agent tracing 的共享格式（持久身份 + 人工介入的标准正在被补进工作组）。现在按这个方向埋点，比等标准落地再返工便宜得多。今天这件事的教训是：出事时你没有那份日志，你连"哪些机器被装了"都只能靠用户自查。
  2. 把 agent 的执行放进沙箱，把 agent 的分发放进供应链管理。容器/微虚机承载执行 + 锁定扩展版本并校验发布者 + 最小权限 token，缺一不可。今日头条的载荷之所以能建立持久化，正是因为它跑在开发者的主账户下。
  3. 给 agent 的输出加溯源标记。这条今天有两份独立证据支撑：Anthropic 那篇 86%/15% 的研究（人类用了 agent 的论据却只有 15% 承认来源），和 Model Spec 的"控制并沟通副作用"。"谁做的、依据什么"必须跟着输出一起走，否则责任无从归属，出事也无从取证。

洞察二 · 开源权重的竞争维度已经从"能不能"变成"每 token 多少钱"，这正在重写 agent 的经济账

今天最被低估的一组数字，来自 Le Chonk：Artificial Analysis Coding Agent Index 48%，与最强开源竞品 GLM-5.3 打平，但每任务平均少用 47% token；Terminal-Bench 上分数更高（41%）而输出 token 再少 30%。

把这件事和另外几条放在一起看：DSpark 投机解码作为 checkpoint 的一部分随权重发布（1.9× 吞吐）、NVFP4 版本面向 Blackwell、GGUF 社区版本下载量是原始 BF16 版的 2.5 倍、以及 IBM Granite Switch 演示的"基座不动、只重训 adapter"。

结论（主观）：开源权重模型的能力差距已经小到可以由推理工程而非模型本身来决定胜负。token 效率 + 投机解码 + 量化格式 + adapter 热更新这四件事叠加，让一个"能力略低但便宜一半"的模型在 agent 场景里击败一个更强的模型——因为 agent 的成本结构里，token 数是乘数，不是加数。

由此推出三条我认为市场还没完全定价的方向：

  • "token 效率"应当成为一级选型指标。现在大家比的是 benchmark 分数，但 agent 的真实账单是"每任务总 token × 单价 × 重试次数"。一个 48% 且省 47% token 的模型，在生产里可能比 52% 而多烧一半 token 的模型便宜得多，而两者在排行榜上看起来差不多。建议你的模型选型表里第一列是"每任务总 token"，第二列才是分数。
  • 投机解码正在从"推理优化项"变成"模型发行物的一部分"。DSpark 随 checkpoint 发布、WebGPU 那篇用 context-mixing drafter 免掉额外 draft 模型——两条路都在把 draft 的来源从"另一个模型"改成"已经在手边的东西"。如果你的推理栈还没开投机解码，这件事的优先级应该高于换模型。
  • 可审计性正在成为开源权重相对闭源 API 的真实差异化优势，而不只是价格优势。Le Chonk 在恶意 cyber prompt 上 96.6% 的拒答率是可以被第三方独立测量的——闭源 API 做不到这件事，你只能信厂商的说法。当"这个模型会不会在关键时刻拒绝我"变成一个合规/审计问题（尤其是本文提到的 Anthropic 那类"人的判断其实来自 agent"的场景），"我能自己测量它的克制行为"就是一个企业级采购理由，而且随着能力提升会越来越重要。

最后一个提醒：今天所有关于开源权重"追平"的判断，都建立在厂商自报的 benchmark 上。Mistral 与 HuggingFace 在同一天对同一个 Cyber Index 给出 51% 与 82% 两个数字，就是一个现成的提醒。在做成本模型时，请务必用你自己的任务集实测 token 数，而不是抄榜单。
