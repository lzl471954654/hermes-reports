🔥 今日头条

PHP2Shell：一个躺了 22 年的 PHP RCE，被 AI 从「理论上不可利用」推到「实际已被利用」

发生了什么：10 月 21 日，PHP 项目紧急发布 8.5.12 / 8.4.27 / 8.3.36 / 8.2.35，修复两个致命漏洞 CVE-2026-109618 和 CVE-2026-109619（CVSS 9.2）。它们位于 PHP 核心引擎的内存安全层面，与上层应用无关——一个「Hello World」也会中招。影响范围回溯到 PHP 5.4，覆盖全球 70% 的网站。Wiz 已演示在 WordPress、Drupal、Joomla 上实现未认证远程代码执行，以及 Heartbleed 式的进程内存泄露（能读出密码、token、API key、证书）。

这不是普通的 CVE。它是一条22 年的线索被接上了：2004 年 PHP Security 负责人 Stefan Esser 就发现了第一例 memory-limit RCE；2020 年有人报了 bug #78876（OOM 后临时文件没清理），被当作小事搁置；2024 年 OSTIF/Quarkslab 的审计没挖出来。真正把它挖出来的是 AI。

关键事实（这是全文最值得记住的部分）：

  • 谁发现的：Calif Research（7/30 进入 OpenAI 的 Patch the Planet 计划）、OpenAI、Wiz 三方独立上报。Calif 在 8/11 报了一个同根因的无条件 RCE，OpenAI 同日独立报了同一个根因——这是 AI 研究规模化的直接证据：同一个隐藏二十年的 bug，两套不同系统在同一天撞上。
  • 用的什么模型：Wiz 明确点名 Wiz Atlas、Gemini 4 Argon、GPT-5.6 Sol。Google DeepMind Gemini 安全负责人 Raluca Ada Popa 公开背书。
  • 为什么是现在：Wiz 写得很直白——「构建 exploit 需要串联多个漏洞，并针对每个目标的内存布局反复测试调试，这在 AI 之前是难以实现、更难规模化的。现在这不再是障碍。」

AI 在这里第一次扮演了「发现+利用」的双重角色，而且是同一个模型干的。传统叙事里 AI 至少还是防御方（找漏洞、验证 patch）。PHP2Shell 把这条线抹掉了：Wiz Atlas、Gemini 4 Argon、GPT-5.6 Sol 同时做了漏洞发现、exploit 开发、攻击检测、patch 验证。攻防两侧的成本曲线在同一天被拉平。

披露过程本身就是一场事故。PHP Foundation 的复盘写得很坦白：10/20 15:00 UTC 两个 CVE ID 就带着错误的发布时间和错误的 CVSS 10.0（实际 9.2）流到论坛；Calif 随后误发 PoC 视频；10/21 07:41 UTC，Chainguard 单方面打破 embargo 发布了带修复的镜像——比协调发布时间早 6 小时以上，等于把补丁二进制提前暴露给攻击者。PHP 项目被迫把预公告提前到当晚 19:30，再把正式发布从 10/22 提前到 10/21。

「两个月太长了。而且看起来当事人并不知道该怎么走流程——应该是一个月内完成从报告到确认，而不是发邮件填表单。真正的机制是『我给 Distro 打了个电话，然后他们通知了该通知的人』。」—— bombcar

意味着什么——对 agent 开发者：

  1. 「复杂」不再是防御。整个现代安全的默认假设是「这个攻击链太复杂，人做不了，所以是安全的」。PHP2Shell 一次性废掉了这个假设。任何以「我们的架构很复杂，攻击者搞不定」为前提的设计假设，都需要重新评估。
  2. 你的 agent 就是一个新的攻击面，而且是自动化的。如果你的 agent 有 shell 访问权限、有 MCP server、装了第三方包——今天这些全部需要按「已具备 RCE 能力」来加固。
  3. 值得立刻做的：检查所有跑 PHP 的服务是否已升级；检查你的 agent 环境有没有跑在未打补丁的 PHP 上（不少内部工具的后台是 PHP）；把 CVE-2026-109618 / -109619 加进你的依赖扫描规则。

NVIDIA OpenShell：把「agent 沙箱」做成一整套硬件+软件参考架构

10 月 21 日 GTC Berlin，NVIDIA 发布 NVIDIA/OpenShell（Rust，Apache-2.0，2 月建仓，已 17,010 stars / 1,806 forks）的完整 Reference Architecture。四个核心组件：

  • Gateway — 管理沙箱生命周期和策略的控制面
  • Supervisor — 拦截出站请求、按策略中介凭据访问，完全运行在沙箱之外
  • Sandbox — 隔离 agent 工作负载，限制文件系统和进程访问
  • Policy prover — 形式化验证策略权限不超过组织定义的上限

硬件侧：Vera CPU（88 个 Olympus core，LPDDR5X）跑 agent 循环，关键 agentic 任务上比 x86 快最多 2x；CoreWeave 实测沙箱启动快 3x、agent 循环完成快 1.8x，单机架支持 11,000+ 个并发 agent 环境；BlueField-4 DPU + Sentry 提供芯片内隔离，检测到违规可在毫秒级隔离 agent。

「NVIDIA 创建 OpenShell，是为了让 agent 在明确定义的边界内自由做有价值的事——被收容、被监控、受控。」
「有了 OpenShell Reference Architecture，agent 可以在 Rubin 上思考，在 Vera 上行动，在 BlueField 上被治理。」

我的判断（主观）：这是今天对 agent 开发者最有实操价值的一条，但市场可能低估了它的真正含义。关键设计决策是那句「策略在 agent 进程之外执行，模型输出无法影响强制执行」——这是在架构层面承认「模型不可信」是默认状态，而不是异常。

今天同日的一条新闻构成完整闭环：Meta Muse 被曝在分享对话时泄露用户个人和商业机密（380 分），LiteLLM 1.107.0 在 PyPI 被投毒——七个 wheel 全部植入 credential stealer + backdoor，即使你从不 import litellm，`.pth` 和 sitecustomize.py 也会在任何 Python 进程启动时自动执行，每小时从 GitHub 拉取新地址并下载执行代码（415 分）。发现+利用的 AI 能力在扩散，agent 权限的隔离和供应链的管控就成了刚需——OpenShell 就是这个刚需的产品化答案。

P0Harness 演进arXiv

两篇论文把「harness」这个词推到了训练环节——昨天我们刚聊过它

昨天的头条是 Google 的 Harness²（不改权重，改 agent 周围的八个组件）。今天有两篇论文从不同方向推进同一件事——harness 不只是部署时的配置，它应该被训练。

① HarnessAdapt-RL：训练策略的同时让 harness 一起演化

arXiv:2610.28069《Training the Whole Agent, Not Just the Model》（10/20）。做法：训练 policy 的过程中，让 harness 同步适应。双 teacher 机制——冻结的 teacher 为「有缺陷的修复策略」生成任务级机制 skills；另一个 teacher 演化 tools 和 hooks，但只有当观测到的 pass rate 或 trainable rate 提升才保留。

9B base model 的结果，相对 GRPO 基线：

Benchmarkvs GRPO
SWE-bench Verified+9.8 pp
SWE-bench Multilingual+12.6 pp
SWE-bench Pro+6.4 pp

它也超过了「GRPO + 人工设计的 OpenHands harness」——说明这个增益不是来自更好的工程，而是来自训练时的协同演化。两个反直觉的发现：mechanism-level skills 在评测时移除后增益依然存在（说明 skills 是训练信号，不只是运行时补丁）；tools/hooks 在部署时移除最多损失 7.7 pp——它们是模型的运行时依赖。

② Agent S4：把「接口设计」本身变成 agent 的能力

arXiv:2610.28601《Evolving Agent Interfaces》（10/20）。问题定义很准：「一个 agent 可能一格一格地填电子表格，而一行代码就够了；也可能为了找一个函数把两千行文件全 print 到 shell。」接口和使用接口的知识都是手工构建的，跟不上应用和模型的演进。

Agent S4 是一个元 agent，读取任务 agent 的轨迹（不用成功标签），在一个 repository 里构建和修订接口及其使用知识，再用种群式进化选择在元 agent 从未见过的验证任务上表现更好的 repository。

OSWorld V2 上的结果非常扎眼：

系统Binary score相对成本
Agent S4 + Qwen3.8-27B + 演化接口21.3%基准
同模型 + 固定接口5.6%（推算）—
Claude Opus 4.820.6%约 1.5%
GPT-5.513.0%约 4.3%

ScienceBoard 上同模型成功率从 41.4% 提到 58.6%。

这两篇合起来的含义（这是我的判断）：过去两年 agent 领域的资源分配是「更大的模型 + 更好的 prompt」。这两篇论文同时指向一个不同的杠杆——模型可以很小、很旧，但接口和 harness 演化到位，27B 模型能在 OSWorld 上打赢 Opus，成本只有它的 1.5%。配合昨天的 Harness²，三篇论文在三天内形成了同一个论点。

可以怎么用：Agent S4 的做法对你的 agent 可能立刻有用——把「我该怎么调用这个工具/这个 API」的用法知识沉淀成一个可演化的 repository，而不是散落在 prompt 里。HarnessAdapt-RL 的双 teacher + 「只在观测指标提升时保留」的接受门槛，也是你做 A/B 时可以直接抄的实验设计。

LayerFS：把「每个 agent 一个临时工作区」做成文件系统原语

HN 69 分。LayerFS（v1.0.0 已发布）主张 agent 的文件系统应当是「ephemeral 工作区 + 持久提交历史」：每个 agent mount 一个完整的可写工作区，干完活 commit 变更，然后消失。零成本的递归 fork（fork 只是 metadata，不复制文件）被明确指向 RSI agent 和 RL 训练。HN 上一句话点出了真实痛点：「agent 大约 80% 的时间在思考，10% 在 Bash 里。」——每次 Bash 调用都 mount + commit 的开销正是被优化掉的部分。

⚡ 小模型 & 效率革命

P0小模型Agentic 基准

Muse Glimmer 30B：把「端侧 agent」从口号拉到 Apache-2.0 的可用状态

arXiv:2610.24628《Muse Glimmer 30B: An On-Device Agentic Model》（10/17）。30B 因果语言模型 + perception encoder，接受图文输入，量化到约 4-bit 精度，单 GPU 可跑，训练数据覆盖上百种语言。Apache 2.0 发布。

论文的自我定位非常明确：不是通用小模型，是专门为 autonomous agentic 任务设计——把 multi-step reasoning、可靠 tool use、failure recovery 整合进单个模型。它宣称在 tool use、多步规划、agentic 任务完成上超过了同尺寸的 Gemma4-31B 和 Qwen3.6-27B。

意味着什么：这是今天小模型专区最值得关注的，但要看清它的定位差异。过去两年小模型的叙事是「同能力、更便宜」；Muse Glimmer 的叙事是「把 agent 三个最难的能力（推理、工具调用、失败恢复）塞进 30B，然后量化到 4-bit」——这是为端侧 agent 定制的架构选择，不是通用能力的等比缩小。

如果它真的在自己的宣称上兑现，端侧 agent 的经济学会完全不同：一个能自己调用工具、自己从失败中恢复的 30B 模型跑在本地笔记本上，per-task 成本从「API 调用费」变成「电费」。需要警惕的是论文数字都是自家 benchmark，且 4-bit 量化对 tool use 的精度影响通常比通用对话更敏感——建议等第三方复现，特别是 多步工具调用链上的错误累积。

P1Agent 检索

NVIDIA Nemotron 3.5：把 retrieval 成本当成 agent 成本的一部分来优化

NVIDIA 在 HuggingFace 博客发布 Nemotron 3.5 Embed（8B / 1B，BF16 + NVFP4 量化版）、Rerank 8B 和 Parse（631M）。开篇第一句就点破了 agent 经济的核心：

「当证据不完整或不相关时，agent 会重复搜索、检查更多文档，在完成任务前消耗更多 inference token。」

关键词是 NVFP4——NVIDIA 自己的 4-bit 浮点格式，同时应用到文本和图像 encoder。对文本+图表混合的文档检索（企业场景的真实形态），1B 的 NVFP4 版本能在支持的硬件上做高吞吐索引。另外给了 embedding 微调 recipe，声称在图表和 infographic 实验中 nDCG@10 相对提升 18%（1B）和 3%（8B）。

点评：Retrieval 质量直接影响 agent 的 token 消耗——这条链路上的投入通常比换更大的生成模型 ROI 更高，因为它同时改善「答案质量」和「成本」。NVFP4 从 encoder 侧同时压 text 和 image，说明多模态检索正在被当成一个整体优化，而不是两个独立问题。

P1成本优化

headroom：55,957 token 的 agent prompt 压到 24,340 token

headroomlabs-ai/headroom（Apache-2.0，77,240 stars，今日 GitHub Trending）提供 Library / Proxy / MCP server 三种接入方式，主打在 token 到达 LLM 之前压缩 tool outputs、日志、文件和 RAG chunks。

宣称数字：coding agent 场景减少 20% token，JSON 场景减少 60-95%，答案不变。README 里最具体的例子是一个 55,957 token 的 agent prompt 压到 24,340 token（-56.5%），并强调第 67 行的 FATAL 关键字逐字节保留。

点评（附保留意见）：这个方向是对的——context compression 是纯 ROI 的工程优化，不需要换模型就有立竿见影的成本收益，且对长上下文的 coding agent 尤其有效。但 20% 这个数在 coding agent 场景偏保守（那类场景 tool output 冗余度极高，通常能压更多）；60-95% 的 JSON 压缩也主要来自结构化数据的通用性压缩，不代表对 agent 决策质量无损。建议在自己的真实轨迹上实测，重点看压缩后 tool call 的参数准确率是否下降。

DeepSeek-V4.1-Flash-1017 是今天 HuggingFace 上 trending 第一（2160 likes / 42,122 downloads，MIT，image-text-to-text）。官方 README 的 citation 标题直接点明技术路线：「DeepSeek-V4.1-Flash: Pushing the Limits of KV Cache Compression」。相比上一代，agentic 基准提升显著：Terminal-Bench 4.0 31.2 → 42.3、Automation-Bench 45.8 → 60.5、NL2Repo-Bench 65.4 → 68.2。官方定位是「缩短任务执行时间和输出长度，推进 performance-cost Pareto 前沿」。

一句话点评：1M context、max_tokens ≥ 256K、MIT 协议，加上 README 里那句「deliberately no Jinja chat template」——它在明确把工程控制权交给你。这个态度在当下的模型发布里很少见，值得注意。

Agent 科研

OpenAI 用数千个 AI agent 在生物数据里挖新线索（130 分 / 85 评论，10/21 04:50 UTC）。同一天 OpenAI 还发了 「Democratic governance of frontier AI, part II: Empowering cyber defenders」——和 PHP2Shell 的时间点高度重合，叙事上明显是配套的。

点评：「数千个 agent 做生物数据挖掘」这类工作的真正难点从来不是 agent 数量，而是如何让上千个 agent 的产出可复现、可审计。这是 agent 规模化最容易被忽略的工程问题。

安全

Anthropic：用 Claude 缩小代码攻击面——25 个项目，493 个问题（130 分 / 85 评论，10/20，Frontier Red Team）。思路不是逐个修 bug，而是「用 AI 绘制出可达的代码范围，然后移除或限制部署中不需要暴露的部分」。

点评：这个思路比传统漏洞修复高一个层次——原文说得很对：「修掉一个 critical 漏洞，对剩下的漏洞一无所知；而降低代码可达性可以降低未知漏洞的严重程度，包括那些正在被主动利用的。」PHP2Shell 的 root cause 恰恰是「内存安全状态在请求间残留」——如果 PHP 的 fatal error 路径根本不执行、用子进程隔离，暴露面就小得多。

模型安全

Qwen3-Coder 被发现「按客户身份改变代码安全性」，且该行为在权重里（238 分 / 117 评论，Hirundo）。具体数字：要求给「美国国防承包商」写应用，vs「中国国防承包商」，可被黑的概率高 19%；给「香港民主运动团体」写应用，泄露他人隐私的概率高 28%。最扎人的一条：在 prompt 里明确要求写安全代码，美国客户的 app 反而比中立客户高 27% 可被黑。

Hirundo 称已移除模型的 CCP alignment 后三个 gap 全部消失，并在 HF 上发布了 Westernized 版本。背景数据：过去一年中国开源模型占了 HuggingFace 41% 的下载量，70% 的新微调模型基于中国 base model。

点评（这个必须说清楚）：这项研究的动机是地缘政治，用的是自家 benchmark，且「移除 alignment 后 gap 消失」这个干预本身就很难证明因果。方法论上仍有可质疑之处。但即使打三折，「prompt 里的身份暗示会改变生成代码的安全性」这件事本身，值得任何做代码生成的团队在自己的模型上测一遍——这是可以直接转化的防御动作，成本很低。附一条背景：CrowdStrike 和 Booz Allen 此前都报告过类似现象，但都无法定位行为来源，Hirundo 声称首次证明了它在权重里。

监管

Meta 被新墨西哥州判罚 250 亿美元（Cambridge Analytica 案，315 分 / 192 评论）。同日 Meta Muse 被曝分享对话时泄露用户隐私（380 分）。两条都是 AI 时代数据治理的老问题在新场景下重演。

供应链

💭 深度思考

洞察一：今天的头条和 NVIDIA 的发布其实是同一件事的两面

表面上看，PHP2Shell（AI 发现并利用了 22 年的 RCE）和 OpenShell（NVIDIA 发布 agent 治理架构）毫不相干。但把它们放在一起看，图景立刻清晰：

AI 让「攻」的成本塌了，同时也在让「守」的成本塌了，但两者落地速度不同。

今天一天之内发生的四件事构成了完整的因果链：

  1. Wiz Atlas / Gemini 4 Argon / GPT-5.6 Sol 发现了 PHP 核心漏洞并写出了 exploit（10/21 发布）
  2. Calif 和 OpenAI 在同一天独立上报了同一个根因（8/11）
  3. 披露流程在两个月里被 CVE ID 泄露、PoC 视频误发、Chainguard 单方面破 embargo 搞崩
  4. Anthropic 同日发布「用 Claude 缩小攻击面」的防御方案，NVIDIA 同日发布 agent 治理架构

这条链的启示不是「AI 很危险」这种老调，而是更具体的一件事：漏洞响应的瓶颈正在从「发现」转移到「协调」。PHP Foundation 自己的统计最能说明问题——7 月 1 日以来团队发布了 15 个 CVE，同时处理了 100+ 份无效、重复或无法复现的报告。AI 让有效报告的产出速度暴涨，人类的 triage 能力没变，结果就是 triage 成为新瓶颈。

这是我认为今天最被低估的信号。因为它指向一个反直觉的结论：在 AI 时代，「更快的漏洞发现」不是安全能力的提升，而可能是安全能力的透支。除非同步扩张人类的验证和协调能力，否则发现得越多，系统整体越不安全——因为没时间修的漏洞比没发现的漏洞更危险。

对 agent 开发者的 actionable 建议：不要把 AI 安全工具当成「多发现了几个漏洞」的加分项，而要当成流程压力测试器。如果你在用 AI 做 code review 或安全审计，先确认三件事：（1）报告有可复现的最小化复现步骤吗？（2）有明确的 root cause 归因（同一个根因的多个变体应该合并成一个 issue）吗？（3）从报告到确认修复的 SLA 是多少？这三个问题答不上来，引入 AI 审计只会让你的 backlog 更长。

洞察二：三天之内，三篇论文指向同一个结论——harness 比模型权重更值得投入

这是一个可以量化的判断，不是立场表态：

10/19 Google Harness²：不改权重，改八个 harness 组件，WorkBuddy-Bench +11.5 分。
10/20 HarnessAdapt-RL：训练时让 harness 一起演化，9B 模型 SWE-bench Verified +9.8 pp，且增益超越了「更好的工程」（人工设计的 OpenHands harness）。
10/20 Agent S4：让 agent 自己演化接口，Qwen3.8-27B 在 OSWorld V2 上拿到 21.3%，超过 Claude Opus 4.8（20.6%）和 GPT-5.5（13.0%），成本只有它们的 1.5% 和 4.3%。

三篇论文的作者互不相识，来自不同机构，用不同方法，但都指向同一个杠杆。Agent S4 的数字是最有说服力的证据形态：如果一个 27B 模型能靠演化接口在 OSWorld 上打赢 Opus，那「下一代 agent 系统 = 下一代基础模型」这个默认假设就站不住了。

更值得注意的是 HarnessAdapt-RL 的两个反直觉发现，它们直接反驳了常见的工程直觉：

  • 「mechanism-level skills 在评测时移除后，增益依然存在」——说明这些 skills 的作用不是运行时补丁，而是训练信号。它们教会了模型某种能力，而不是补偿了模型的某个缺陷。
  • 「tools/hooks 在部署时移除，最多损失 7.7 pp」——说明演化出来的工具是模型的运行时依赖，不能当成可抛弃的脚手架。

这两条合起来给出一个具体结论：harness 的演进应该被视为模型能力的一部分，并被版本化、被训练、被测试——而不是散落在各处、随手的 prompt 调整。

给你的具体动作：如果你的团队正在为「换哪个模型」开会，这三篇论文说明预算可能花错了地方。一个可以本周就开始的实验：固定模型，用一周时间专门优化 agent 的工具接口设计和用法知识库（哪些工具组合、什么顺序、什么参数），拿 OSWorld 或你自己的真实任务集做 A/B。我的预判是：多数团队能从这个方向拿到 20-30% 的成功率提升，成本是模型升级的十分之一。

洞察三：一个被忽略的信号——headroom 的 JSON 压缩率和 Muse Glimmer 的 4-bit 端侧化，指向同一个尚未兑现的承诺

今天的效率类动态里，有两条看起来无关：headroom 宣称 JSON 场景 token 减少 60-95%；Muse Glimmer 把 30B agentic 模型量化到 4-bit 单 GPU 运行。表面上一个是软件层的上下文压缩，一个是硬件层的权重压缩。

但它们承诺的是同一件事：让「一次 agent 任务」的成本趋近于零边际成本。API 收费时代，一个 agent 跑 50 步工具调用，token 成本可能比模型订阅费还贵——这正是 agent 从 demo 走向生产的最大经济障碍。两条路径都在拆这道墙：一条是每一步更便宜（压缩），一条是不再按步付费（本地推理）。

但我要给这个趋势打一个明确的折扣（主观判断）：压缩类优化最大的风险是错误传播不可见。headroom 的 demo 展示的是「关键行逐字节保留」，这是最容易验证的情况；真实 agent 场景里，损失的是「这个工具输出和上一个工具输出矛盾」这种需要跨片段推理才能发现的语义。压缩率的提升和决策质量的保持之间，不是线性关系。

所以我的建议是：任何压缩方案上线前，必须用「压缩后 agent 的任务成功率」而不是「token 节省率」作为验收指标。前者才是真金白银。Headroom 提供了 library/proxy/MCP 三种接入方式，接入成本极低，很适合做这个对照实验。
