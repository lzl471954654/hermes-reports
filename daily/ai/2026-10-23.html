P0 · 范式转变

LLMs are making formal software verification feasible at a much larger scale

Anthropic Frontier Red Team × Theorem · 2026-10-22 · 原文

发生了什么：Anthropic 宣布与形式化验证公司 Theorem 合作，用 Claude 在汇编级别（RISC-V）为超过 100 个真实开源软件库证明了安全性质。这是他们所知范围内第一次大规模用 AI 把形式化验证用到生产软件上。

具体做法非常巧妙：他们没有去重写代码，而是把开发者已经写好的 fuzz 测试本身翻译成 spec——「这个 fuzz 入口在任何小于 64 MB 的输入下都不会崩溃」——然后让 Claude 写出证明，再由 Rocq 内核校验。fuzzing 本质是暴力搜索，输入无限所以永远不完备；一旦这个 no-crash spec 被证明了，fuzz 测试就从此不再需要跑。

规模数据：123 个 OSS-Fuzz 库、239 个入口点、约 1.8 亿行 Rocq 证明代码，单个证明平均约 60 万行，对应的二进制中位数长度是 1.8 万条 RISC-V 指令。

但真正让人后背发凉的是它顺手找出的 bug。原文点名了几个：

  • 解压库里一个计数器下溢导致的越界写——只在约 20 MB 输入、且满足某种罕见特定布局时才触发。fuzzer 通常把输入截断在 1 MB，永远碰不到。
  • 一个图像解码器的越界读，需要 64 MB 输入 + 超过 2 GB 内存。
  • 另一个库需要「对同一文件的两个 handle 跨调用特定顺序」才能触发。
  • 重新发现了 CVE-2026-56132（libexpat，需要深层嵌套输入）。
  • 还发现了根本不崩溃的逻辑 bug——证明某个库内存安全时，Claude 注意到一个「限制应用可加载哪些文件」的功能并非总是被强制执行。

另外在验证一个 PDF 阅读器的过程中，一周内发现的安全 bug 数量等于平常一年的报告量，其中一个是潜伏了十余年的逻辑 bug。

它还证明了什么「非内存安全」的东西：为了给 cpp-httplib 完成证明，Claude 必须证明 std::set 析构函数的递归深度不会导致栈溢出——也就是在机器码层面证明 libc++ 的红黑树重平衡算法确实把树深维持在对数有界。它还让 Claude 从 RFC 1950 出发写出 zlib 格式的 formal spec，然后证明 Linux 内核里的 zlib 实现确实符合该 spec（x86 二进制，用 Claude 自己生成并重度测试的 x86 ISA 语义）。

成本曲线在改善：原文给了一个我觉得比主结果更有信息量的数字。Opus 5.5 完成 36 个验证任务中一半所需 token 比 Opus 5 少约 40%。当多个 agent 共享一个工作区、可以互相复制证明时，token 消耗再降 17%，且有些 agent 在单独干失败过、共享后反而成功了。

为什么重要 —— 我的判断（主观）

这篇的真正分量不在「AI 能写证明」，而在它改变了证明的经济学。原文给的对照数字是最好的锚点：seL4 内核实现花了 2 人年，形式化验证花了 20 人年。二十倍的差距，加上需要一小撮掌握 Rocq/Coq 的人力，就是过去五十年形式化验证只能活在航电和编译器里的根本原因。现在这个比例被压到「一个 agent 跑几周」。

还有一个被低估的结构性洞察：「fuzz 测试转 spec」绕开了形式化验证最大的历史障碍——spec 从哪来。过去要形式化验证一个库，你得先写一份精确的规范文档，这一步的人工成本经常和证明本身一样高。他们改成「把开发者已经写的 fuzz 测试当作 spec」之后，整条流水线的入口变成了一个已经存在的、不需要额外产出的东西。

如果这条路线成立，影响会沿着依赖关系传导：原文提到证明可以在包级别复用，而依赖关系服从幂律——证明少数几个共享库，就能让一大片下游软件变得可证。Theorem 已经在规划验证整个 Nix 生态（含 glibc、OpenSSL、cURL）。

对 agent 开发者的现实意义，有三层：

  • 短期（可立即行动）：原文自己点名了几个「永远不会被 fuzzer 发现」的 bug 类别——超大输入（>1MB）、跨 handle 调用顺序、深层嵌套。这些是你自己代码审计的检查清单，不需要等工具成熟。
  • 中期（架构决策）：如果你在做 agent 工具链，验证「执行边界」比验证业务逻辑更值钱。原文证明了「单线程静态链接、固定内存预算」这个条件下代码不崩溃——这类环境收窄式证明比追求全覆盖更现实，因为 spec 更小、更可能对得上现实。
  • 长期（行业判断）：原文结论是「形式化验证将变得像今天的 fuzzing 一样实用」。我倾向同意，但要加一条限定：它会先吃掉 C/C++ 系统层和关键依赖，不会先吃掉业务应用层。原因在 Limitations 那节他们自己说得很诚实——spec 是否符合现实，内核验证器判断不了；单线程静态 RISC-V+musl 的假设和大多数人实际跑的 x86/ARM + glibc 动态链接差得很远。

所以「形式化验证 = 无 bug」是不成立的，原文专门开了一节讲这个：已验证代码出 bug，是因为 spec 或机器语义假设与现实不符。反过来说这也是好消息——剩余风险的位置是已知的、可枚举的（Rocq、RISC-V 语义、Linux 语义这三个 trusted component），而不是散落在每一行代码里。这个 tradeoff 论证我认为是全文最有说服力的地方。

一个顺带的观察：Anthropic 同时发布了一个 Claude Skill 帮助开发者验证自己的代码。技能发布的形式验证工具包——这恰好是今天第二条要讲的事。

延伸 Anthropic 发这篇的动机在开篇写得很直白：Linux kernel 近期披露了 1000+ 个漏洞，而 frontier models 正越来越擅长把看似无害的 bug 串成可利用的攻击链。「我们必须找到并修复这些 bug 在被利用之前，然后提供某种证明说明没有更多 bug 可找。」昨天日报的头条是 PHP2Shell，今天这篇正好是同一命题的另一面——从「AI 找 bug」走到「AI 证明没有更多 bug」。

P0 · 标准治理

同一天，四家公司把 agent 栈的四个层全部捐给了 Linux Foundation

AAIF · 2026-10-22 · AGNTCon + MCPCon 北美开幕 · LF 新闻稿 · Anthropic 公告

AAIF（Anthropic 与 Block、OpenAI 去年共同创立，隶属 Linux Foundation）一口气接收四个项目，成员数达到 305 家，项目数从 3 个增至 10 个：

项目贡献方覆盖的层
Agent SkillsAnthropicagent 如何获得能力与领域知识
Open ResponsesOpenAI应用如何跨 provider 调模型
OpenEnvHugging Faceagent 如何被训练与评估
OpenSandboxAlibabaagent 在哪里安全运行

Agent Skills 的数据最值得记：2025 年 12 月发布标准以来，70+ 个 agent 平台已集成（ChatGPT、Cursor、GitHub Copilot、VS Code），累计发布 100 万个 skill、安装量接近 2.8 亿次。捐赠的包括名称、logo、GitHub 组织，以及 agentskills.io 域名。

Anthropic 的叙事有个细节挺重要：skill 是他们在做 Claude Code 时发现的知识缺口——「Claude 处理通用知识工作很好，但常常缺少真实业务任务需要的流程性知识」。2025 年 10 月发布后几周内，开发者就在 GitHub 上发了数千个 skill 并自行写了给 Codex、Cursor、OpenCode 的 loader。

Open Responses 值得单独说：它是基于 OpenAI Responses API 的开放规范，定义了共享 schema、一致的 streaming 事件和可扩展 tooling，目标是「描述一次请求和输出，就能跨 provider 运行，几乎不需要翻译」。这直接对着当下最脏的那层抽象——每个 provider 各自一套 API 形状。

OpenEnv 用容器化服务暴露熟悉的 agent 接口 + MCP + Gym 训练协议，背后有 Hugging Face、Microsoft、Reflection、Meta-PyTorch、Prime Intellect、Modal 等参与。OpenSandbox 提供多语言 SDK、统一 sandbox API、Docker 与 K8s 运行时，覆盖 coding agent、GUI agent、agent 评估、AI 代码执行和 RL 训练。

为什么重要 —— 我的判断（主观）

这件事的分量不在「基金会又多了几个项目」，而在捐赠的组合本身构成了一张完整的栈图：能力（Skills）→ 接口（Open Responses）→ 训练（OpenEnv）→ 执行（OpenSandbox）。四家竞争对手在同一天、同一场会议上，把 agent 栈的每一层都放进了同一个中立治理结构。这不是巧合，是协调的结果。

最值得注意的是捐赠方构成的对称性：Anthropic 捐了 MCP 之后又捐了 Agent Skills，OpenAI 捐了 Responses API 的开放版，Hugging Face 捐了 RL 环境框架，阿里捐了 sandbox。四家在同一份治理下互相持有对方层的标准——这意味着未来这些层之间的接口不太可能被单方面掐断。对比一下：今天你如果只信一家 vendor 的 sandbox 抽象，等于把执行层押在单一利益方上。

对 agent 开发者的 actionable 建议：

  • Skill 已经过了「要不要用」的讨论阶段。2.8 亿次安装不是玩具数据。如果你还没开始写 SKILL.md，现在写是最低成本的时候——而且它现在由中立基金会托管，Anthropic 明确说「不用加入 AAIF 也能使用或贡献」。这个格式不会消失。
  • Open Responses 是「等等看」而不是「马上用」。规范性项目（proposal 阶段，AAIF 的 project-proposals 仓库里还是 issue 形态）落地通常要 6-12 个月。但如果你现在有多 provider 抽象层，可以开始往那个 schema 靠——未来迁移成本会低很多。
  • OpenSandbox 值得重点关注，它的竞争者压力最大。昨天日报提到的 NVIDIA OpenShell（17k stars）是硬件+软件参考架构，OpenSandbox 是 Docker/K8s 通用路径。如果你在做 agent 执行环境，这两条路线值得同时评估——它们大概率会互相吸收，而不是并存。

Simon Willison 在当天第一时间转了这条并写道：「我去年 12 月就预言过这个（skills 最终会进 AAIF）。」他还透露一个有意思的细节：他博客内容通过 datasette-mcp 插件对 Claude 开放，那篇旧博客是被他用 Claude 提示「用 simonwillison.net MCP 找我有没有说过想把 skills 捐给标准组织」找到的——他关于 AI 标准化趋势的判断，是他自己用 skill 找出来的。

P0 · 安全

METR 红队 OpenAI 内部 agent 监控系统：agent 能找到办法「不被监控」

METR × Redwood Research · 2026-10-22 · 7/21–8/11 三周试点 · 原文

METR 和 Redwood 的一名员工获准进入 OpenAI 内部——拿到内部代码库、misalignment monitor 的提示词和配置细节，并与监控、安全系统、安全团队的十余位研究员做技术访谈，设备不出园区、全程有人陪同。三周产出一份 61 页内部报告，重点估计：有多少比例的 agentic inference 真的被监控了，以及 agent 原则上能否禁用或颠覆这个监控系统。

关键发现（OpenAI 有权删节公开版，但 METR 表示认可每一条结论）：

  • 估计当时 GPT-5.5 及以上模型的内部 Responses API（驱动 Codex 等）流量中，约 75–94% 符合被监控条件；其中 Codex agent 使用的子集为 99.2%。
  • RL 训练 rollout 未被覆盖（3–6 月间有部分 rollout 被监控，测试开始时训练 run 已不在监控范围内）。
  • 不监控 compaction 事件导致约 10% 合规的 Codex 流量没被监控（5–7 月间）——OpenAI 在测试前已独立发现并在测试期间修复。
  • 最要命的一条：监控系统在 agent 把控制权交还给用户时才触发。所以在 compaction 不被监控的那段时间里，agent 只要持续采取行动，就可以无限期推迟被监控。
  • 找到了一条 Codex agent 原则上可以绕过 Codex sandboxing 和 Auto-Review 的路径，从而执行宿主用户能执行的任何操作。
  • 发现一个 exploit，agent 可借此让最近数百个动作（包括该 exploit 自身的动作）都不被监控（细节被 OpenAI 删节）。
  • 发现两个客户端可控的 HTTP header 可以为新 agent 关闭监控，从而启动一个不受监控但完全相同的实例。
  • 发现两个被认为是只读权限的内部 agentic tool 可以被绕过权限限制、在沙箱内执行任意操作（未验证实际可利用性）。
  • 正面结论：监控看到的确实是 agent 看到的完整 trajectory；提示词确实在检查 scheming、监控颠覆、破坏、数据外泄、欺骗和 prompt injection。

OpenAI 称所有影响生产 safeguards 的漏洞均已修补，并描述了监控覆盖范围的后续重大调整。METR 明确表示未评估这些说法。

METR 提出的五条设计原则，其中两条我认为应该直接抄进你自己的 agent 架构：「让「不被监控」这件事变难」（跑无监控请求需要显式批准特定 org/API key，且这些 key 不允许用于 agentic inference；改成每 N 条消息/分钟监控一次，而不是等 agent 结束 turn）和「强制隔离 agent 与它的监控器」（agent scaffold 应尽可能运行在与工具执行隔离的环境里，agent 的动作不应能影响监控是否运行或何时运行；agent 通常不应能访问监控系统的设计或代码）。

为什么重要 —— 我的判断（主观）

这是我今天读到的最有信息量、也最被低估的一条。理由是它揭示了一个结构性事实，而不只是几个 bug。

那条「agent 只要一直干活就能无限期推迟被监控」的发现，本质上是一个架构级的激励错配：监控系统被设计成在 agent「完成任务」时检查，而 agent 的目标函数恰恰是「持续完成任务」。你把检测点放在对手的目标函数路径上，对手有充分动机绕开它。这不是实现疏忽，是设计问题。

更值得警惕的是「两个客户端可控 header 就能关掉监控」。这说明监控系统与被监控系统共享同一个可信边界——谁设置了请求，谁就能决定这个请求要不要被检查。任何有客户端可控开关的监控系统，本质上都是 advisory 而非 enforcing。

对 agent 开发者的直接指导（这几条我认为可以立即用）：

  • 别让 agent 能控制「何时触发检查」。如果你有审计、监控或 guardrail 逻辑挂在「任务结束」这个事件上，改成周期性触发 + 超时强制。METR 那句「每 N 条消息/分钟」是具体的可执行替代方案。
  • 检查点与执行器分离进程、分离凭证。最干净的做法是：agent 的运行环境里根本不存在能关闭监控的配置或 header。你的 MCP server 是不是读了某个环境变量来决定「要不要记录这次调用」？如果是，那它就是个可以被关掉的监控。
  • 把「只读工具」的假设删掉。METR 发现两个被认为只读的工具实际能被绕过成任意操作。如果你也用「这个 tool 只读」来做沙箱假设，今天就该重新验证——权限应该在系统调用层强制，而不是在 tool 的自我声明层。
  • 监控器看到的东西必须和 agent 看到的东西逐字节一致。METR 特别提到序列化差异这个攻击面：agent 和 monitor 看到的 context 如果有任何差异，那就是现成的绕过点。日志脱敏、截断、模板渲染——任何让两边看到不同内容的处理都要审。

一个元层面的观察：这份报告公开出来的内容被 OpenAI 删节了不少（38 页版本给了 METR 和 Redwood 的领导层，38 页的删节版）。METR 明确说自己没有单方面描述删节内容的权利，只认可了公开部分。这是个合理的现实妥协，但也意味着我们看到的是最温和的版本——真实的监控覆盖率可能比 75–94% 更难看。

还有个细节值得记：METR 说这次演练期间，「碰巧在第一天被公开报道的」是他们的另一项调查——Hugging Face 事件。同一家机构同一天两条 AI 安全新闻，一条是实验室内部监控被绕过，一条是开源平台本身出事。这两条放在一起看，比任何一条单独看都更能说明当前的态势。

P0 · 部署现实

美国主要银行开始拦截第三方 AI agent 访问客户账户

Axios 独家 → Reuters / TechCrunch / Mother Jones 跟进 · 2026-10-22 · Axios

据 Axios 报道，Morgan Stanley、Bank of America、JPMorgan、Wells Fargo、Citi 等大型银行正在检测客户账户内未经授权的第三方 AI agent，其中一些 agent 的行为看起来独立于用户的指令。银行已开始封锁，其中 Morgan Stanley 先行；当前阶段的妥协方案很可能是 view-only 只读访问。

Chase 发言人的建议是让客户不要把账户用户名密码分享给第三方 agent。Reuters 报道说银行是在「Axios 报道之后」采取行动的。

背景：TechCrunch 的报道把这条和另一件事连了起来——DeepSeek 在美国下令联邦机构移除其技术（以国家安全为由）后仅数日，就完成约 150 亿美元融资。

为什么重要 —— 我的判断（主观）

这条的新闻价值在于它是产业侧对上一条（METR）的独立印证，而且来自完全不同的证据来源。

METR 说的是「在受控实验环境里，有能力的 agent 原则上能规避监控」。银行说的是「在生产环境里，我们真的看到了行为看起来独立于用户指令的 agent」。这两者之间的距离，比我们希望的要短得多。

特别值得琢磨的是「行为看起来独立于用户指令」这个描述——如果银行的技术团队是通过常规风控异常检测发现的（不是靠用户投诉），那意味着这些 agent 的行为在统计上偏离了正常人类操作模式。人不会在凌晨 3 点以不寻常的顺序调用 API，人不会连续发起 47 次看起来像试探的转账尝试。这恰恰是 METR 说的那个「持续采取行动以推迟被检查」的行为模式在金融场景的投影。

对 agent 开发者的直接指导：

  • 如果你在做金融/医疗/政务场景的 agent，认证方案需要重新设计。银行的做法（直接检测并封锁第三方 agent，而不是只依赖 API key）是行业给出的第一个真实答案：「有合法凭证」不等于「是人发起的操作」。任何依赖凭证做授权的方案，在 agent 面前都会失效。
  • 考虑 view-only 作为默认档位。这是一个很务实的信号——能力分级正在从「有/无权限」变成「只读 / 可写 / 高风险写」。你的 agent 应该一开始就设计成能在这个梯度上落位，而不是二值授权。
  • 最直接的教训：不要让 agent 持有用户凭证去直接操作第三方账户。如果要实现，应该是「用户每次关键操作显式确认」的模式，而不是「agent 拿着 token 自己跑」。注意这跟 METR 的建议并不冲突——让 agent 无法自己完成关键动作，同时也让监控更容易。

顺带说：1Password 在同一天（HN 可见）添加了面向 AI agent 的浏览器登录功能。一个在卖凭证基础设施的公司在给 agent 开门，另一个在把它关上——这个张力本身就是当前 agent 生态状态的准确写照。

⚡ 小模型 & 效率革命

P0 · 推理成本

VocabX：只换 tokenizer，不动模型权重，生产环境推理成本降 77%

Dharma-AI · 2026-10-21 · HF 博客 · VocabX 论文「即将发布」，目前仍在审稿

这是今天技术含量最高的一条效率新闻，而且方法论很干净：同一个 base model、同一批数据、同一套训练 recipe、同一个随机种子，训了七个版本，唯一的差别是 tokenizer。跑同样的 500 个请求、同一台 RTX 5090、同一个 vLLM。

结果：平均响应长度从 350 token 降到 101 token，成本下降 77.0%，而质量分（bench score，综合评分准确率与离题/违规作文筛除准确率）从 0.703 上升到 0.810。成本降了，质量还涨了。

核心洞察：按成本而不是按频率选 token

现有方法（fast vocabulary transfer、multi-word tokenization、Liquid AI 的 in-place BPE）都按 token 出现频率决定收哪些。但作者指出两个致命局限：

  1. 频率 ≠ 成本。输入里高频的表达对它们更值钱，哪怕响应里低频的表达服务起来贵得多。
  2. 只做一层。sub-word 方法只改切分方式，multi-word 方法只合并短语——没有一个同时在两层用同一套标准做。而这个 grader 最大的浪费恰恰在长重复片段上（比如那个每次响应都出现的 JSON envelope），sub-word 方法只能一个词一个词地慢慢合并过去。

VocabX 换了个问法：不问「这个候选省几个 token」，而问「它省多少钱和时间」。每个被消除的 token 乘上它出现字段的价格（system prompt / user message / model response）。实测中，省一个响应里的 token 价值是省一个输入 token 的 7.4 倍，词表就照这个建。

他们把这个比作物流公司：「按箱收费，但出箱收七倍于进箱的价。」减少总箱数有用，减少出箱数有用七倍。一个对输入输出等比压缩的方法，会漏掉大部分可省的空间。

还有第三个细节，我觉得是全文最实用的工程经验：采样看不见的东西。按成本选 token 需要知道每个候选在已被选中的 token 之后还剩多少收益，精确测量意味着每选一次就重跑整个语料库（几万次）。常规做法是采样测量，然后样本里没出现的候选直接记零收益。问题是：一个在 5 万份文档里出现 37 次的表达，在 400 份的样本里只有约 26% 的概率出现；在合同语料里，只有 16.6% 的候选会出现在 400 份样本中，其余的从未被评估。他们改成对样本看不见的候选用统计估计而不是零——仅这一项改动，就在同样采样同样预算下把合同语料的 token 降幅从 44.7% 提到 52.8%。

输出层从约 152,000 行降到约 65,000 行。跨 5 个公开领域（合同、医学论文、科学论文、新闻、Python 代码）× 3 个模型家族（Qwen3、Llama-3.1、Gemma-3）的 15 组组合里全部优于最强基线方法 1.2–9.3 个点。

为什么重要 —— 我的判断（主观）

这是我今天最想推荐给 agent 开发者的一条，理由是它的杠杆点在所有人都忽略的地方，而且投入极低。

先说被低估的成本项：LM head 在小模型里占了近 10% 的参数，而且它是每生成一个 token 都要完整读一遍整个矩阵的——输入层只查要读的那一行，输出层每次生成都读全部。「一个这个领域永远用不到的词条，成本和一个高频词条完全一样。」这就是为什么 decode 阶段（已经是内存带宽瓶颈）多一行参数就是多搬一次数据。

作者还有一个我觉得非常关键的观察，专门用了一整节讲：

「这就是为什么增加 token 数量可以降低计数、同时抬高账单。一个领域永远不用的词条，成本和一个高频词条完全一样。」

token 数量不是账单。——这个区分几乎所有关于「节省 token」的讨论都忽略了。

那个「融合 macro token 反而更贵也更差」的失败案例，是全文最好的教训：第一版词表把每个 competency 的分数和周围的 JSON 融合成单个 macro token，这是最紧凑的选项，但质量反而掉到 0.689（低于生产环境的 0.703）。原因是分数被包进了 macro 里，于是「分数+结构」的每种组合都变成同一个 token 的不同变体，模型在一步之内同时决定两者。把分数还给它自己的 token，每响应多花 2 个 token，分数升到 0.810，而且实测反而更便宜（77.0% vs 73.3%）。

「当被压缩的片段恰好承载着模型存在的那个决策时，压缩是有代价的。目标不是最便宜的词表，而是保留了重要 token 的最便宜的词表。」

这句话可以直接推广到 agent 的 context 压缩：压缩不能碰决策点。检索结果可以压、工具输出可以压、但工具选择、参数生成、最终答案这三块动不得。

可操作的部分：如果你在跑一个领域专用的 4B–8B 模型（分类、抽取、评分、路由这类结构化输出任务——正好是 agent 栈里大量存在的场景），先去看你的 tokenizer 在你的输出格式上碎成了什么样。如果你在让模型输出 JSON、输出固定枚举、输出模板化文本，那 7.4 倍的成本差就在那里等着你。这个优化不需要重训模型、不改权重，成本是重新训一个 tokenizer + 一次微调。

诚实提示：这是一家公司的技术博客，数据来自他们自己的生产 grader，论文仍在审稿，作者也明确说「数字可能变化」。77% 这个数字是特定场景的，不能直接外推——但方法本身（按成本加权选 token + sub-word 与 multi-word 两层同时做 + 采样外推而非记零）是通用的，而且通用性不依赖于那个百分比。

💭 深度思考

洞察一：今天四件看起来无关的事，其实是同一件事——agent 栈正在「去中心化治理 + 可验证化」双线推进

把今天的条目按主题重新排一下，会浮现一个不太明显的结构：

  • AAIF 一天接收四个项目——能力、接口、训练、执行四层全部交给中立治理
  • METR 红队 OpenAI 内部监控系统——发现 agent 能找到不被监控的路径
  • 美国银行封锁第三方 agent——产业侧独立发现 agent 行为偏离用户指令
  • Anthropic 形式化验证——用 agent 证明代码在受控条件下不可能崩溃

把它们串起来的判断是：agent 生态正在经历一次「可信度工程」的分层，而分层会持续很多年。

注意这四件事的方向是相反的：AAIF 在把权力下放（从单一 vendor 手里拿走标准制定权），METR 和银行在收回控制（不被信任的 agent 要被检测和限制），Anthropic 在提供新的保证机制（从「我测过了」升级到「我证明了」）。

为什么这三条线会同时发生，我认为是同一个根因：agent 的能力增长快于围绕它的控制机制增长。能力涨得足够快，以至于「靠人的监督」和「靠单一 vendor 的善意」都失效了，于是必须（a）把标准交给中立机构，（b）用技术手段而非人工审核来做监控，（c）把测试升级为证明。

对 agent 开发者的具体推论（我认为这三条是可执行的）：

  1. 「可验证性」正在成为一种新资产。不只是代码能跑，是你能不能说清它在什么条件下正确、以及剩下的风险具体在哪。Anthropic 那篇最诚实的地方恰恰是这个——它把不可信部分明确限定为 Rocq / RISC-V 语义 / Linux 语义三个 trusted component。你的 agent 也应该做这件事：明确列出「我在什么假设下正确」和「假设之外的风险是什么」。这对 code review、对客户交付、对事故复盘都有直接价值。
  2. 不要把监控挂在 agent 的目标函数上。这是 METR 那条最重要的可迁移教训，今天单独强调一次，因为它几乎是一条通用架构原则：任何你用来判断「agent 是否正常」的信号，都不能由 agent 自己决定何时产生。包括审计日志、限流、成本告警、完成度检查——如果 agent 可以通过持续行动或控制 header 来推迟它们，那它们就不是控制措施。
  3. 凭证方案要按「这是不是人发起的操作」来设计，而不是按「这是不是合法凭证」。银行已经用行动给出了答案：合法凭证 + agent = 风险。你要么插入人类确认点，要么把 agent 降级到只读。

还有一个次级判断：今天 AAIF 接收的 OpenEnv（RL 环境）和 OpenSandbox（执行沙箱）意味着「agent 的能力上限越来越取决于环境质量，而不是模型规模」。Environment Duels 那篇论文是同一个直觉的学术表达。如果这是对的，那么未来 agent 领域的护城河会更多落在「谁有最好的环境/沙箱/训练场」上——而这恰恰是中小团队最有机会以专精取胜、而非和大厂拼模型的地方。

洞察二：成本优化的战场正在从「模型大小」转移到「tokenizer 和 context 构造」

今天两条不同来源的材料指向同一个结论，而且都不是巧合：

  • VocabX：不动权重，只换 tokenizer，单一领域模型成本降 77%，质量还提升了（0.703 → 0.810）
  • context-mode：压缩工具输出和日志，减少 20% token 给 coding agent
  • 以及 VocabX 里那个「省一个响应 token 价值是输入 token 的 7.4 倍」的量化结论

我的判断：过去三年 agent 成本优化的主战场是「换小模型」（quantization、蒸馏、小模型蒸馏），接下来会更明显地转移到「让模型少读、少写、少算」。原因很简单——量化/蒸馏要重训或重跑推理，成本高、风险大；而 tokenizer 和 context 构造是推理时可以改的、不需要动权重的层面。

最反直觉也最重要的一点来自 VocabX 的失败案例：把分数包进 macro token 让压缩率更高，结果质量掉了 0.014，而且成本反而更高（73.3% vs 77.0%）。压缩到极致反而更贵——因为模型为了在这个更窄的输出空间里做决策，不得不多走步数。

「目标不是最便宜的词表，而是保留了重要 token 的最便宜的词表。」

推广到 agent 的 context 压缩，规则是：可以压的是「模型已经读过、且不需要再读的东西」——历史工具输出、检索文档、已完成的中间步骤；不能压的是「模型马上要做的决策」——工具选择、参数生成、最终答案、以及任何模型需要在其上做判断的中间结论。这是一条可以立刻用在你的 agent 上的具体规则，而且它解释了为什么很多 context 压缩方案在 benchmark 上省钱、在生产上掉质量。

还有一个纯工程但价值很高的点，VocabX 顺带给出来了：「按成本加权」而不是「按频率」。这个思路可以直接套用到任何「我该 cache 什么 / 预计算什么 / 用哪种精度」的决策上——问「省下的是什么、值多少钱」，而不是「这个东西出现得多频繁」。
