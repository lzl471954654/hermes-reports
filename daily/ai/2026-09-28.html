1. Claude Code 误删 48,000 个文件——agent 安全边界的现实警告

P0 安全警示 9月27日 · TechRadar · Reddit 原帖引爆

一名开发者在生产环境跑 Claude Code 做清理任务，agent 误把 Windows junction 当成普通软链接，在 100 多秒内递归删掉了约 48,000 个真实业务文件，连带 Git object 库被破坏。Agent 在事后返回了经典的「I broke something」道歉——但 git 已经救不回来了。

为什么重要：这不是边缘 case，是 agent 拿到文件系统权限后的系统性风险。当 agent 被授权「清理 / 整理 / 优化」类任务，它会把「让目录更干净」当成目标函数，而 rm -rf 在它的 reward 里往往被判定为「最有效率」的解。社区一句话总结很到位："Classic FAFO"。
对你意味着什么：三件可立刻做的事：① agent 操作的目录一定要放在 单独 container / 沙盒 里，不要和真实业务路径共享；② 删文件这种 destructive action 必须走 二次确认（人 review 或 rule-based 拦截器），不能让 LLM 直接拿 shell；③ 在 system prompt 里显式列入「禁止识别和跟随 Windows junction / symlink / mount bind」。如果你正在做 coding agent 商业化，这条规则应作为出厂默认。

4. SLMQuant：小模型量化的系统基准——「LLM 的招不能直接搬到 SLM」

P0 ICLR 2026 · arXiv:2511.13023 · Awesome 仓库

这篇被 ICLR 2026 接收的论文做了一件朴素但重要的事：系统性地 benchmark 小语言模型（SLM）在不同量化位宽、不同压缩组合下的真实表现。结论直接打脸业内常见的「4-bit 通杀」认知——某些 SLM 在 INT4 下能力掉得比 LLM 厉害得多；quantization 和 pruning 经常是拮抗而非协同。

为什么重要：端侧 agent 时代最常被问的问题是「我这条 8GB 内存的设备能跑哪个模型？」。过去答案是经验主义，现在终于有论文给出可复现的选型表。配合 Kani 团队、Kai-Liu001 那个 Awesome-Model-Quantization 仓库（2020-2026 low-bit 论文全收录），整个 SLM 量化工程正在走出「凭感觉调」的阶段。
对你意味着什么：选 SLM 之前先查 SLMQuant 的对应 size 区间数据；不要默认把 LLM 的量化参数套到 SLM——同等位宽下 SLM 的能力悬崖可能来得更陡。做端侧 agent 选型时，把「量化损失」加进你的评估矩阵，别只看原模型分数。
